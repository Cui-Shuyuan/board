# 05 — 请求账本与程序调度，减少机械性模型往返

依赖：01–04。目标：在 legacy 的自然工具调用流程上接管重复确认、读取复用和结束条件。不是再建一个强制两阶段问答器。

## 修改入口

`backend/BoardAI.Api/Services/ChatOrchestratorService.cs` 的工具循环、`ShouldRequestCandidateConfirmation`、结果 collector 和结束处理；对应工具 schema、候选提示字段、客户端结果解析及测试。

## 目标流程

```text
模型：理解用户，提交查询，或直接请求必要澄清
  ↓
程序：校验 → 解析/检索 → 正式读取 → 依赖导航 → 去重交付
  ↓
模型：基于证据回答 / 必要澄清 / 说明无资料 / 提交补查
  ↓
程序：检查协议与引用，返回结果；确有错误才有界修复
```

简单规则题通常一次查询、一次回答即可，但这不是强制调用次数。纯指代澄清可以直接结束；真正复杂问题可补查。延迟最终按 06 验收。

## 工作包 A：请求账本

以请求为边界维护 query、target、read、delivery、candidate、continuation 和调用预算。身份键至少包含游戏、规则版本、规范路径、操作、范围、参数绑定、投影类型；未解析的自然语言查询保留原输入，禁止把语义相似但未证实相同的输入合并。

每个正式单元分别记录：已读到、已交付、在当前模型上下文仍可见、引用状态。candidate 另记“已读取”和“已消歧”，不可共用一个 confirmed 布尔值。

同一请求的精确重复查询复用结果。读过但当前上下文不可见时重新交付内容。版本变化、不同 owner.slot、不同关系/绑定不能复用错误结果。

## 工作包 B：替代一律确认候选的门禁

删除“只要存在 unresolved/pending 就要求再确认”的通用行为，按账本事实处理：

- 已自动正式读取的候选：无须模型再发一次同 ID explain 来证明读过。
- 未确定身份但不影响当前问题：可回答一般规则，不为了消除无关候选追加往返。
- 身份差异会改变答案：允许简短 clarify；不能先给未经确认的实体特定结论。
- 用户缺少必要状态：可给简短条件式答案，或只问一个决定性问题；不能因某条无关规则还缺人数而强制追问。
- 资料未覆盖与预算未读完区分：后者优先合法续读，前者诚实 unavailable，不能把“请确认人数”作为资料缺失的替代。

是否影响答案属于语义判断，模型以明确结果类型表达。程序只验证结构/已知事实，不通过“是否含问号/如果/可能”正则判断回答或澄清。

## 工作包 C：轻量结束协议

沿用同一工具循环，添加一个轻量的终态提交能力或等价结构化响应。最小字段：

```text
outcome: answer | clarify | unavailable
text: 面向用户的简短自然语言
evidence_ids: 本请求模型可见的正式证据引用
clarification?: {missing_kind, requested_information}
unavailable_reason?: no_rule_coverage | unresolved_identity | budget_exhausted
```

`execute_plan`/续读本身表达补查，不再附加一份繁复 need_more 子问题账本。多问输入可以自然分点回应；不强制模型输出每个子问题的多个状态和重复证据正文。

终态提交与生成答案是**同一次模型调用**；不加一轮“检查答案”的模型。程序校验 evidence ID 存在且内容确实交付、状态字段合法、调用预算未越界。answer 涉及规则断言必须引用正式依据；clarify 可以无引用。引用验证只能证明来源存在，不证明全文被该来源蕴含；答案质量仍由离线评测衡量。

无论采用工具或响应格式，都写实际 messages/schema 的捕获测试，更新 Android 对结果状态的解释。不要把证据已读/已引用显示为“规则裁判认证正确”。TTS 只读取 text。

## 工作包 D：全请求预算和循环退出

保留基线已有总轮次/超时硬上限，再统一计数模型调用、程序读取和输出大小；实施前在报告列出实际默认值。不要照搬 program 的固定四次作为未经实验的新限制。

- 机械性展开只耗程序预算；补查与协议修复共享总调用预算。
- 同一查询重复不再实际读库；相同结果不得无限纠错循环。出现重复无进展时交付明确的已读/缺失摘要并受总预算约束退出。
- 修复只解释具体协议错误，不要求把合法 clarify 改成回答。
- 超预算返回明确限制，保留已确认的局部答案时不得补造其余部分。
- 请求取消/超时向所有读/搜索/模型调用传递，不能后台继续消耗。

## 行为测试与验收

模拟 LLM 的可执行轨迹至少包括：

1. 口语 query → 候选 → 程序读正式内容 → answer：无需额外确认调用。
2. 两个会影响答案的候选 → clarify：不触发候选确认纠错。
3. 一条已足够的一般规则 + 无关 pending：可正常结束。
4. 重复相同 query：底层搜索/读取不增加；不同 scope/参数不复用。
5. 历史被裁剪：再次交付正文，不能只返回旧 evidence ID。
6. 包外引用、伪造 ID、非法状态：有界修复；合法无引用 clarify 不被拒绝。
7. 多轮补查/修复/重复查询触发统一硬上限，无无限循环。
8. 用户只问“从盒里选哪三个”：回答选取方式，不为附加人数计算先追问；用非 Splendor 合成规则验证同样行为。

本阶段必须证明模型少做了哪些机械动作、程序实际调用次数如何变化。随后进入 06；若实际回答质量下降，保留独立可用的去重/读取修复，不强推新的终态协议。
