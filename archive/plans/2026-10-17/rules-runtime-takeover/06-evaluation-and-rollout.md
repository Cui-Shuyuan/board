# 06 — 跨游戏验收、性能归因与默认版本升级

依赖：01–05；本计划的题集、指标和预算在 01 时预登记，不能看完结果再改门槛。

## 要回答的问题

1. 程序到底接管了哪些工作，是否减少机械性模型调用？
2. 规则依据和回答质量是否保住，正常口语是否仍然好用？
3. 时间花在模型服务、输入输出体积、工具、序列化还是纠偏？
4. 能否在新增游戏时仅接入内容，不增加游戏专用问答代码？

## A. 三层验证，避免每步全量重跑

### 第一层：确定性行为

每个计划运行所改服务测试，并在阶段完成时跑后端全套：

```powershell
dotnet test backend/BoardAI.Api.Tests/BoardAI.Api.Tests.csproj
python -m unittest discover -s tools/eval -p 'test_*.py'
git diff --check
```

实际工具环境不支持某命令时记录并解决环境问题，不能把未执行写为通过。仅改文档不要求跑上述代码测试。

若修改内容 JSON，执行 `python tools/content/validate_rules.py`；若改 Android 协议，按仓库现有流程跑 JVM 测试及聊天/TTS 冒烟。不得为了本史诗顺手改动画或重合成 TTS。

合成夹具必须覆盖卡牌、工人/行动格、资源变换、阶段循环和同名 slot；引擎不能依赖 Splendor 词汇。真实游戏测试检查当前内容的支持范围，不把测试预期注入线上规则。

### 第二层：开发诊断与单变量消融

31 题集合继续作为开发诊断集；133 题历史集合已经参与分析，均不再称作留出集。

优先使用冻结查询、捕获模型轨迹、旧产物重新分析。需要真实聊天时，每个候选节点先用覆盖主要能力的开发小集，同题同配置重复三次。小集出现明显退步先查原因，不直接烧全量。

分别保存 02/03 导航、04 交付、05 调度的可比较提交。对相同冻结查询测工具层，对相同固定证据测回答层，最后才端到端。禁止同时改模型、Thinking、提示、工具、预算后把收益归给某一个因素。

### 第三层：最终同轮对照

基线使用计划 01 冻结的 legacy。候选使用已通过开发验收的累计改动；不能选一个表现更差的中间版本当基线。

默认最终预算：历史 133 题 + 新封存 36 题（9 款游戏各 4 题），每题每版 3 次，最多 **1,014 次聊天**，另计离线 judge。缺失的旧题需按原文件恢复或明确记录，不能静默改总数。运行前按实际配置估算 token/费用并写入实验清单；使用既有授权与凭据，不扩大服务权限。

36 题在主线调参前封存，覆盖口语改写、局部顺序、枚举、同名对象/必要澄清及正常无需澄清的情形。每题事先写清语义判分标准、可接受的条件式答案及若干可用证据组合。运行实现不读取题目 expected 字段。查看留出结果后继续针对这些题调整，必须承认它已变开发集。

两版本交错、随机化顺序，同规则、索引、模型、Thinking、采样参数、请求并发；记录缓存状态及限流/重试。温缓存和冷启动成本分开，不让一个版本独享预热。HTTP 错误与协议失败如实报告，重试不能覆盖原失败记录。

## B. 指标与门槛

下列为本史诗的默认预注册门槛；若业务预算另有决定，只能在正式结果揭盲前改，并留档。

| 维度 | 指标/验收 |
|---|---|
| 答案正确性 | 双独立盲评严格共识；候选点估计不低于基线，配对问题级 Bootstrap 95% CI 下界高于 -3pp |
| 编造/错规则 | 点估计不增加；逐条复核候选新增的错误，不以总通过率抵消明确的系统性错误 |
| 真实使用 | 正常问题的多余澄清、无关扩展分别报告；需要澄清的问题单列，不能用过度 unavailable 换准确率 |
| 证据 | 精确解析、候选、正式读、交付、引用分层；合法替代证据可通过；出处命中不是答案正确认证 |
| 延迟 | 同轮聊天 P50 至少降低 10%，P95 不增加超过 5%；报告区间与分布，检查是否来自异常服务抖动 |
| 程序接管 | 机械确认次数、重复底层查询次数下降；支持的重复查询契约测试中底层执行一次 |
| 稳健性 | 九款游戏及新留出集单列，人工核查集中退步；样本小不宣称各游戏都统计显著 |

以问题为聚类单位抽样，保留同题三次和两个版本配对；不能把 507 次回答当完全独立样本虚增置信度。 judge 分歧、两个 judge 各自结果、人工抽查结果同时提供。

样本无法排除劣化时结论为“证据不足”，不能把不显著解释为等效。不要自动超预算扩大实验直到得到想要的结果。-3pp 是本次统计保护边界，不是允许明知质量下降仍切默认；点估计和新增错误复核同时约束。

## C. 性能归因

每个请求输出一条可对账时间线，并汇总：

- 模型调用次数及用途：首次查询、回答、语义补查、机械确认、协议修复。
- 每类调用输入/输出 token、provider 可提供的 reasoning token、总时长、首 token 时长（实际可观测时）。
- 搜索/向量化、正式读取、结构导航、装配/序列化、排队/重试时间。
- 发送给模型的工具正文体积、重复正文体积、最大上下文、答案长度。
- 程序冷启动索引和热查询的时间、内存；不能只报告热路径而隐藏每请求重建索引。

固定查询旧/新交付对照用于检查输入量；固定证据旧/新回答协议对照用于检查生成长度和格式负担；端到端配对用于检查实际收益。这些对照只能隔离可控因素，模型服务内部排队与未公开计算仍可能无法分开。

不要从 reasoning 文本推断“模型花了 X 秒思考某规则”。可以抽样归类可见行为：消歧、规划下一查询、整理证据、格式修复；报告客观 trace 中发生了什么，未暴露的信息写未知。最终必须回答用户关心的：减少的调用被哪些程序步骤替代，剩下的模型时间主要出现在哪一类调用。

## D. 发布与停止条件

1. 代码与确定性测试通过，但真实效果未知：保留为候选，不切默认。
2. 02/03 局部能力修复通过同轮验收，而 05 新协议失败：保留已验证工具修复，撤回/隔离失败协议，不整包回滚所有工作。
3. 正确率改善但性能不达标：报告质量收益与时间代价，不能宣称性能目标达成；保持当前已验证默认，另行决定是否接受代价。
4. 质量、性能及客户端行为全部通过：升级默认 legacy 实现，更新提示/schema 指纹与接入文档。
5. 清理只为本次实验设置的临时开关，不长期维护六组开关的任意组合。保留 program 实验入口的事实状态，不顺手推广。

预算上限内仍不达标时，提交阶段成果、根因证据和未完成项；不再启动第三套问答架构，也不声称史诗完成。

## E. 多游戏接入交付

生成一份内容接入能力检查表，区分：

- 规范路径和引用合法性；
- 流程位置、分支、循环是否有明确结构；
- 成员集合是否有完整性依据；
- 条件/费用/结果/计分能否被现有查询操作读取；
- 哪些规则只有完整自然语言描述，可以解释但不能确定性计算；
- 哪些规则缺失，哪些只是本轮预算未交付。

新增游戏只运行同一套检查并补内容，不新增该游戏专属 runtime 分支。检查表应生成 actionable 缺口，不要求把所有游戏立刻形式化成完整裁判。

## 最终交付清单

- 各阶段独立提交、结果契约与查询能力文档。
- 默认路径实际 messages/tool payload 的匿名化样例。
- 跨游戏/合成夹具测试与必要 Android/TTS 验证。
- 同轮质量、分层证据、延迟及调用类别报告。
- 原始实验产物保持在忽略目录，仓库提交题集、脚本、manifest 指纹与报告，不提交密钥/大型生成物。
- 更新当前状态文档；明确哪些能力已上线、哪些仍实验、哪些未知。
