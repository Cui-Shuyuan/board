# 03 — 把对象查询转为规则操作，由程序完成导航

依赖：01、02。目标：模型表达“想查什么”，程序完成定位后的正式读取和结构导航，不再要求模型逐条发送机械性确认查询。

## 修改入口

`backend/BoardAI.Api/Services/RulesPlanService.cs`、`RulesReferenceService.cs`、`RulesConceptCatalog.cs`、`RulesFactService.cs` 及现有搜索服务。复用规范路径与 snapshot，不另建第二套检索库。

## 工作包 A：有限的查询能力表

先列出当前 schema 真正支持的能力，将自然语言 intent 与可执行操作分开：

| 能力 | 输入 | 程序职责 |
|---|---|---|
| describe | 对象路径或待解析名称 | 读取完整定义及必需限定 |
| flow | 流程范围 | 调用 02 的局部结构查询 |
| catalog / members | 类型/集合范围 | 浏览目录或有依据的成员枚举 |
| rule_lookup | 对象线索 + 用户原问/意图 | 找与问题相关的规则节点，正式读取并说明候选身份 |
| relation | 已确定对象 + condition/cost/target/boundary 等 | 按 schema 读取关系及来源 |
| compute | 已支持公式 + 有来源的输入参数 | 使用现有确定性求值，缺参显式返回 |

不要一次新增十几个相似 relation。能力表须与实际工具实现一致；能力未支持时明确返回 unsupported，不把操作名称写进提示就当作完成。

`rule_lookup` 解决“水晶怎么获得”被简化成“水晶是什么”的问题：完整原问/intent 进入既有检索，精确对象身份与待找规则操作分别保留。不能因为对象 exact hit，就跳过用户所问的规则；也不能用意图候选替换用户明确指定的对象身份。

模型仍需理解“如何获得”和“定义是什么”的区别。程序负责执行选择后的操作，不用更多正则猜意图，也不假装能确定所有候选相关性。

## 工作包 B：有类型的导航策略

每种操作声明其依赖选择器，而不是“把相关节点都读进来”：

- condition/cost/target：读所属节点的对应字段、引用的正式定义及实际绑定；保留约束的作用域。
- flow：按 02 返回局部步骤、必要父条件和位置。
- rule_lookup：结合完整意图检索；可使用结构化反向索引发现引用该对象的规则节点，但标记关系类型。
- compute：只读取所求公式、变量来源和适用边界；不具备完整公式时交回有依据的规则解释。

例如“某动作获得资源”与“某动作支付资源”都可能引用资源节点。只有 schema 中明确的效果/费用关系才能确定方向；任意文字引用只生成候选，不能自动推导收益。

每次展开记录父路径、边类型、理由、深度和是否必要。设定全请求读次数、节点数、深度、序列化预算，循环检测，必要依赖优先。预算初值先根据冻结查询分布制定并写进配置；禁止用 expected ID 改优先级或无限扩大预算直到答对。

## 工作包 C：自动正式读取候选

候选检索之后，程序可以在预算内读取候选正式内容，避免模型仅为“把候选 ID 再问一遍”占一次调用。

必须保持两个独立事实：

```text
candidate_read = 正式内容已读到、出处可验证
target_resolved = 当前对象/操作身份已确定
```

前者不能自动推导后者。exact 路径可确定身份；多个近似候选在正式读取后仍可保持歧义。相似度不作为“已确认”阈值，也不能把 top-1 自动升级为结论。

自动读取数量可配置且有 trace；目标是给模型少量足以判断的正式候选，不是复制整个候选描述加完整子图。04 负责交付形态，05 负责避免随后再做一次相同读取。

## 工作包 D：计算的边界

盘点 `RulesFactService` 当前支持的数量、计分和公式能力。将其输入表达为可校验参数，参数记录 user/context/rule 来源；不靠问题包含某个字就宣称满足公式条件。

本阶段不引入任意脚本执行，不把自然语言规则自动编成裁判。公式输入齐全才计算；用户状态缺失只返回该计算所需的变量。问一般规则时不得为了计算一个用户未问的值而追加澄清。

## 行为测试与验收

- 同一对象 describe 与 rule_lookup 返回不同的有据可查结果；对象 exact hit 不吞掉规则查找。
- 合成夹具中获取资源、花费资源、仅提到资源的三条规则不被当成同一效果。
- 正式读取到两个候选后仍保留身份歧义；没有额外模型调用也能完成正式读取。
- 引用环、缺失依赖、预算耗尽都有可追踪结果，不静默成功。
- 同模板但不同参数绑定不复用错误值；缺参不编造默认人数/回合/数量。
- 至少三个非同构游戏覆盖 flow、资源/行动规则、费用/计分之一；另有合成非卡牌夹具。

输出能力矩阵：每项“已实现 / 部分支持 / 不支持”，以及各游戏结构是否具备所需关系。仅有 description 的规则仍可阅读解释，不为补齐矩阵强行改写全部规则。

确定性验收要求：冻结查询下，程序能独立完成依赖选择和正式读取，并输出可对账的导航轨迹；候选内容已读却仍未确定指代的状态不丢失。端到端收益由 04–06 测量。
