# 程序控制的问答编排：DeepSeek 实施计划

日期：2026-10-17。

执行对象：DeepSeek V4.1 Flash。请阅读项目规范与本计划后完成代码、测试、对照实验和文档，不要只返回另一份设计。普通实现选择自行决定；遇到外部环境阻塞，完成不依赖该环境的工作并准确记录未验收项。

## 1. 目标与边界

保留现有结构化规则库、检索、事实计算和版本快照能力，重构问答的控制流程：由程序管理查询、事实读取、补充检索和结束条件；模型只承担问题理解、必要的语义消歧、依据选择与口语表达。

正常规则问题目标为两次模型调用：理解一次、回答一次。复杂问题可进行一次有界补充检索和第三次模型调用。减少模型在内部查询协议上来回决策的成本，不以牺牲正确性换取调用次数达标。

本次是编排层重构，不是重写整个规则系统。禁止：

- 游戏名分支、特定规则 ID 加权、针对测试问句的正则或答案模板。
- 恢复数量必须复述、提到人数就重答、按句长判定意图等已删除逻辑。
- 将用户现场状态视为已验证事实，或将动画演示状态自动视为现场棋盘状态。
- 把所有桌游规则改造成完整裁判引擎，新增视觉识别、实时棋盘管理或第二套检索基础设施。
- 为了降低延迟而取消来源验证、减少测试难题、修改规则描述迎合答案，或只比较成功请求。

个人项目不要求保持旧接口兼容；必要时可更新客户端相关模型与展示，但应保持当前问答、TTS、取消请求和教程上下文功能可用。不要顺带重构动画或内容同步模块。

## 3. 关键设计：分离来源真实性与问题相关性

当前候选确认混合了两个维度：

1. **来源是否已读取并验证**：程序能确定该规则条目真实存在、版本一致、路径有效、内容已读取。
2. **条目是否适用于用户问题**：涉及自然语言含义、对象指代和已知条件；通常需要模型选择，有时需要问用户。

新流程中，程序根据检索候选主动读取正式规则。候选不再必须经模型重新发出同一个 ID 查询，才能获得可引用事实。

但“已读取的真实条目”不等于“已确定用户就是指它”。模型从多个正式条目中选择依据；目标仍有歧义时允许澄清。不得为了消除 unresolved，把所有候选标成问题已解决。

程序校验引用、版本、路径和协议结构，不宣称可以确定任意自然语言回答都被引用蕴含。模型仍有解释错误的可能，必须通过答案级评测监督。

## 4. 目标流程与调用预算

```text
请求进入，绑定同一规则快照与取消/时间预算
  → Understand：模型输出结构化问题计划
  → Retrieve：程序检索并读取正式条目，生成有界事实包
  → Respond：模型返回 answer / clarify / unavailable / need_more
      answer      → 校验引用与结构 → 输出
      clarify     → 校验结构 → 输出澄清，正常结束
      unavailable → 校验结构 → 说明未查到，正常结束
      need_more   → 程序执行一次受限补充 → Respond 一次
  → 记录执行轨迹与结果类型
```

控制要求：

- 模型不能控制任意次数的工具循环；补充、重试和结束由显式程序状态管理。
- 普通规则回答两次调用；一次补充后最多三次。整个请求另允许一次格式/协议修复，因此硬上限建议四次，需包含所有重答调用，不可藏在 helper 中绕过预算。
- 修复和补充共用总时间、取消、调用次数限制。补充用完后再次 need_more 不再循环，应有明确的未完成出口；不可伪装成已回答。
- 闲聊可由第一阶段返回简短回复并结束，不检索规则。不能把具体规则问题误标闲聊作为提速手段。
- 第一阶段可以标记对象指代含糊，但规则问题仍按有效信息查阅一次；第二阶段可直接澄清，不必为了“确认候选”选择无依据的对象。
- 不同阶段使用精简、互不冲突的提示。删除新路径对旧 execute_plan 自由循环提示的依赖；不要把旧循环套进新类后宣称完成重构。

## 5. 内部契约

以下字段表达必须具备的语义，具体 C# 命名可依项目风格调整。使用 typed DTO、枚举和校验，避免依赖自然语言 Message 或答案正则驱动状态机。

### 5.1 问题计划

第一阶段输出 `request_kind`（rules / conversation）和若干子问题：

- `question_id`：由程序分配或校验唯一性，跨本次请求稳定。
- `entity`、`relation`、`intent`：复用现有含义。
- `user_context`：必要时保留用户明确提供的条件及原文来源；不是已通过规则校验的棋盘状态。
- 单一疑点默认一个子问题，只有确实需要不同事实才拆分。不让模型生成推测答案、额外规则或不必要的状态清单。

复用当前模型 API 的 function-call/结构化输出能力，使每阶段只能提交其指定结构。先确认实际服务支持情况，不假设 provider 支持尚未接入的 strict schema。程序解析、校验，允许一次有界修复；不靠截取任意大括号或吞错将坏 JSON 当成功。

### 5.2 正式事实包

建议单独的 `RuleEvidencePackBuilder`，复用现有 catalog/plan/fact/reference 能力。事实包至少包含：

- 包 ID、game、rules version、关联的子问题 ID。
- 每条证据的请求内稳定 `evidence_id`，规范实体路径 `canonical_path`，源文件/节点定位信息。
- 可引用的正式规则字段和必要语境，如 definition、condition、cost、target、ordering、boundary、flow context、Facts。
- 角色区分：检索目标、必要关联规则、程序计算事实。保留关联关系，避免不同候选的条件被混合套用。
- 内容读取结果：成功、缺失、读取失败、因预算未装入；不能把截断/失败写成“规则不存在”。
- 检索候选与分数主要用于程序日志；纯候选摘要与已读取内容必须可区分，摘要不能获得正式 evidence_id。

实现要求：

1. 对少量高相关候选按规范 ID/路径主动读取正式规则，不再让模型为同一目标补发确认请求。
2. 局部 slot 以 `owner.slot` 等完整路径寻址。底层 JSON 节点缺少普通顶层 id/description 时，只要正式内容已读取，也应能作为独立证据；不能因为 Matched 提取为空把它判为无数据。
3. 同名/同局部 id 的不同 owner 必须隔离；不同游戏或版本不能混用证据。
4. 对 relation 的实际信息需求读取必要字段，不能只取对象定义后宣称已回答动作前提、顺序或计分。
5. 对 limit、例外、时点和否定条件保留完整语义。避免只截取一段有利于回答的描述，或把目录项当成规则正文。
6. 所有读取基于同一快照。不要从模型生成的路径读取任意文件，也不要让它扩大到其他游戏。

预算：候选数、关联深度、总包大小必须有配置和日志。可先试每子问题前三至五个候选、一层必要关联，但这些是起始参数，不是写死的正确性标准。总预算满时优先减少低相关的完整条目，而非截断 JSON/规则句子；标记 omitted。多子问题共享预算并保留覆盖信息，不能由第一项独占。

不另加 LLM 做事实包摘要。优先做确定性的字段投影、去重、依赖展开；大条目可按已有语义节点切片，不能凭字符长度切断规则。

### 5.3 回答结果

第二阶段输出一个结构化结果：

| kind | 必需信息 | 程序行为 |
|---|---|---|
| answer | reply、各子问题处理结果、实际使用的 evidence_ids | 校验后返回；未使用候选不产生 pending |
| clarify | reply、需要确认的对象/现场条件、影响的子问题 | 作为正常结果结束，不强制选候选 |
| unavailable | reply、受影响子问题、未查到/读取失败/预算不足等原因 | 正常结束，禁止将检索未命中写成实体绝对不存在 |
| need_more | 子问题、具体缺失信息、受限的补充检索意图或包内引用 | 预算允许时补充一次；不把此内部结果播报给用户 |

`answer` 中有规则断言必须引用实际装入包中的正式证据；闲聊在第一阶段退出。纯澄清可以没有引用，不应为了空引用自动调用模型修复。部分回答可以带澄清，但应明确哪些子问题回答了、哪些还缺信息，不能标成完整解决。

一个规则可能覆盖多个子问题。允许用同一证据说明覆盖，不要求每个初始 query 都经独立精确查询。模型拆出的无关重复项可以标记 `not_needed` 并给出与用户问题的关系说明；不能据此悄悄删除用户真正提出的子问题。覆盖判断的语义正确性纳入评测，不声称仅凭结构校验就能证明。

`need_more` 必须指出缺什么，不能只是“再确认一下”。程序对已装入的同路径、同关系、同版本读取去重；同一请求可以读取不同字段，但不能对相同内容反复访问。候选路径由服务端校验，补充搜索限定当前游戏及原问题范围。

## 6. 程序校验与 evidence 展示

新增结构化执行状态，分离以下维度：

- retrieval：候选是否召回、是否读取正式内容。
- source validity：路径与版本是否有效。
- model selection：模型选用了哪些正式依据；只是模型的相关性判断。
- outcome：回答、部分回答/澄清、未查到、预算耗尽、协议错误。

不要继续用一个 tier 或 pendingCount 同时代表这些含义。历史查询可用于审计，但不能因存在未使用候选而拦截正常结束。

校验失败时，返回有错误码的内部诊断；需要模型纠正的，使用一次共享修复预算。没有修复预算时返回可信的未完成状态。不得直接删掉非法引用后把剩下的回答当已验证。

更新 `ChatResponse`、评测适配和必要客户端消费代码，使 UI 中“证据已读取”与“答案正确”不混淆。保留面向用户的简短 reply 与 TTS 体验，内部 JSON 不播报。无需维持旧字段兼容，但必须让现有客户端编译并能处理新结果。

## 7. 先补齐的三类通用回归

在改新流程前先建立能暴露现有问题的行为测试，再修复或由新流程替换：

1. **局部槽位**：正式读取 owner.slot 后，可以成为有效依据，不因缺少顶层 id 被误判无数据；两个 owner 同名 slot 不串用。
2. **澄清被错误拦截**：对象指代不足时，合法 clarify 不应触发强制候选确认。不要靠检测问号、中文关键词修复。
3. **多余查询**：已读取依据覆盖问题时，未被选中的候选和重复的初始 query 不迫使模型补查。确实未回答的用户子问题仍要明确标识。

如果先对旧流程做独立修复，单独提交并标明它属于哪个实验版本。不得悄悄修改基线服务，再将差异归因给新架构。

## 8. 代码组织与观测

建议拆分可独立测试的协作者：计划解析与校验、事实包构建、回答结果校验、请求预算、编排状态机。适度拆分，避免引入通用 Agent 框架或大量只有转发功能的抽象。

保留 `GameRulesService` 及已有规则服务作为能力入口，优先复用服务 API。不要重复实现规则索引、路径解析或本体逻辑。

新增请求级及阶段级指标：

- request ID、版本/路径、阶段序号、understand/respond/repair/supplement 的原因。
- 每次模型调用完整耗时；若 provider 返回 usage，记录输入/输出/reasoning token 等可用字段。缺失为 unknown，不填零。
- 实际调用次数、补充次数、重复请求被去重次数、最终结果类别。
- 检索、正式读取、关联展开、事实计算、序列化与最终校验耗时。
- 实际事实包大小、条目数、被省略数、每个子问题覆盖及引用情况。

耗时要覆盖响应体读取，不能把响应头到达当调用结束。即使有 reasoning token，也不直接将总请求耗时当纯思考耗时。模型/工具并行时区分墙钟与累计时间，避免把相互重叠区间相加。

模型 reasoning 可在本地调试留档，但不是控制信号或正确性依据；不得为了观察而要求模型生成更长的思考说明。不要在日志中打印密钥、鉴权头。

## 9. 测试矩阵

确定性测试必须覆盖流程与边界，不能只检查方法被调用：

- 正常规则问句：两次模型调用，中间由程序完整读取所需事实，第二次可直接回答。
- 候选来源真实但指代不明：允许 clarify，不把高相似度当用户确认。
- 候选摘要看似有答案、正式读取失败：不可引用摘要，不伪造事实包。
- 明确实体、长短定义问句、同一对象不同动作：不依赖固定措辞或字数。
- 用户给出人数与数量、答案无需重复数字：不产生额外重答。
- 顶层对象、局部 slot、引用规则、程序计算 Facts 均可进入 evidence；关系和条件不丢失。
- 多子问题，共用证据、部分回答、未使用候选、必要信息仍缺失。
- 未知对象、无关候选、规则缺失、检索故障、事实包预算不足分别处理。
- 一次有效补充后完成；重复 need_more、重复查询、超过预算可确定结束。
- 非法/跨游戏/跨版本引用、包外引用、坏 JSON、不支持的结果类型必须拒绝或有界修复。
- 补充与修复交错也不突破总调用数和总时间；客户端取消能传递到全部 I/O。
- 聊天与真正规则问题的分流；多轮用户补充说明后可正常继续，不重复询问已提供信息。

测试包含不带真实游戏名的玩具规则与多款实际游戏。Splendor 可以作为回归案例，不能作为实现分支。改变游戏名或随机实体 ID 后，通用行为仍成立。

## 10. 对照实验与默认切换条件

### 实验隔离

冻结三类材料：基线提交/配置、规则内容/索引快照、题集与评分标准。新路径与 `a992cfe` 在同模型、同思考档位、同环境比较；先保持 `Thinking=low`。不要同时换模型、关思考、改规则内容，使收益来源无法解释。

保留旧路径只用于本轮对照，使用一个明确的实验配置，不长期维护“快速版/可靠版”两套产品。通过验收后切换默认并移除旧自由循环；若验收失败，保留基线默认并提交完整实验结论，不自行降低质量门槛。

### 题集与判分

- 原 117 题作为固定回归，不删除失败样本；复用每题每版三次的配对设计。
- 追加此前未用于提示或实现调参的跨游戏留出集，重点覆盖对象歧义、必要澄清、未知对象、slot、多问题、同对象不同动作、条件冲突。
- 开发集与留出集分开冻结。不可反复看留出失败后修改再称其为独立验收；修复后需如实标记并新增留出验证。
- 盲评比较答案事实正确、证据是否支持、是否回答所问、澄清是否必要、是否编造现场状态及无关扩展。引用存在率不能替代答案质量。
- 若两个 judge 都是 LLM，仍人工抽查争议样本和严重退步样本。judge 一致率与分歧保留。
- 同一题三次重复不是三个完全独立问题。按问题配对汇总，置信区间使用按问题聚类的 bootstrap 或等价方法；说明统计单位，不夸大样本数。

### 需要报告的结果

正确率、问题级稳定性、无依据规则断言、必要澄清/不必要澄清、未查到行为、逐游戏与逐类别结果，以及平均/P50/P95 延迟、模型次数、token/包大小、工具分项耗时和预算失败率。包含失败、超时和格式修复成本，不仅统计成功回答。

以下是本计划的默认验收门槛，须在运行最终留出实验前固定：

1. 所有确定性测试通过，已知 slot/澄清/多余查询回归闭环，不存在游戏特判。
2. 普通一次取证即可回答的问题实测两次模型调用；复杂问题和修复符合有界预算，没有隐藏重答。
3. 严格回答成功率点估计不低于基线，差值按问题聚类的 95% CI 下界高于 -5 个百分点；样本不足以支持结论时明确“证据不足”，不得写成已证明等价。
4. 无依据规则断言率、必要澄清表现不出现实质性退步；逐类检查，不以总体均值掩盖已知严重错误。如果评分有争议，先做盲审核实，不直接改 judge 迎合结果。
5. 平均模型调用数与端到端 P50 有实际下降，P95 不因事实包膨胀而明显恶化。预期目标是正常两轮，不预先承诺固定毫秒收益；报告具体数值及不确定性。

基线和新路径如共用环境，应采用配对交错请求和一致预热，保存原始响应、版本与阶段耗时。允许在冒烟阶段先小样本排错，最终结论不能只来自几条样本。

在架构路径通过后，再把 low/disabled 作为单独实验；本轮不要直接关闭思考作为默认优化。没有真实运行环境时，只能交付实现与静态验证，不得宣称性能和质量验收完成。

## 11. 实施顺序与交付

1. **冻结基线与补失败用例**：记录工作区、版本、配置和旧行为，建立三类通用问题的行为测试。
2. **实现契约与事实包**：统一路径/slot 证据，确定性投影与预算，确认真实性和相关性分离。
3. **实现程序状态机**：理解、取证、回答、四种出口、受限补充和统一修复预算；同步所需 API/客户端消费。
4. **可观测性与完整回归**：完成模型完整耗时/token、事实包和结果分类日志，运行测试及跨游戏冒烟。
5. **配对评测与切换**：按冻结门槛比较，符合条件时切换默认并删除旧循环；否则保留基线默认，解释哪些条件未满足。
6. **更新文档并提交**：更新当前架构、调用契约、运行说明和实验报告，保留 Git 可恢复版本，不提交原始大日志、密钥或无关文件。

最终报告必须列出：

- 实际提交、改动文件与最终流程，不只展示设计图。
- 四种回答出口及补充/修复预算的实际实现和测试证据。
- 事实包样例（至少一款非 Splendor），如何保留前提、例外与规范路径。
- 新旧调用轨迹对照：普通回答、slot、合法澄清、多余 query、未知对象各至少一例。
- 分阶段耗时与质量结果，区分历史结果、本轮实测和未执行项。
- 尚未解决的语义判断风险，以及引用有效不能证明答案正确的边界。

不要将“能运行”“两次调用”“引用全有效”任一单项当成任务完成。交付目标是：在跨游戏答案质量不退步的前提下，让程序掌握流程，减少不必要的模型决策与往返。
