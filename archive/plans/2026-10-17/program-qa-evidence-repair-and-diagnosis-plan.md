## 4. R2：正式证据身份必须来自实际条目

已发现：ReadCandidatesAsync 读取 related 时仍传父候选；AddFormalEvidence 优先用父 candidate.Path，导致不同 related 条目使用同一 canonical_path。直接查询 slot 时，question.Entity 的点路径也可能被套给其关联条目。

要求：

- 将“本条证据的规范路径”与“由谁引用/为何读取”分开传递。父候选路径只能用于关联边，不能成为子条目的身份。
- 正式读取结果携带解析后的 canonical path，不从用户措辞、角色或随机 evidence 序号伪造源路径。
- owner.slot 即使源 JSON 无顶层 id，也应以实际解析结果中的完整路径寻址；其 related 仍使用各自路径。
- 如果现有 GetConceptsWithExpansion 丢失了路径信息，最小化扩展其返回结构或新增内部读取结构，不靠 JsonElement 猜 owner。
- 明确证据去重键的语义：同游戏、同版本、同规范路径及同内容投影可以共享；不同字段投影不能互相覆盖。子问题/角色/父关联应是绑定信息，不应误替代条目身份。
- 同条目从多个父节点引用时，正文可去重，关联边必须保留。不同 source 内容不能静默落到同一键，遇到冲突要报内部诊断。
- 每条 evidence_id 对应一个稳定、可追溯的正式内容；相同父节点不能令多个子规则共用错误路径。

必要测试：两个不同 related 规则都保留内容与身份；同 related 从两个候选读取时不重复消耗内容预算；两个 owner 下同名 slot 隔离；直接 slot 的 related 不继承 slot 路径；相同条目的不同 relation 投影保留所需信息；无可验证路径时拒绝伪造来源。

## 5. R3：读取预算先保证主要候选覆盖，重复项不占额度

已发现：当前按“候选一→它的全部 related→候选二”读取，共用 read 计数；去重返回 existing 也会增加 read。前一个候选可占满额度，让后面的正确候选未进入事实包。

要求：

- 分两阶段：先按排名读取预算允许的主要候选，再分配关联读取额度。
- 多子问题共享总预算时先保证合理覆盖，不能让第一个子问题吃完预算。允许确定性的轮询或配额分配，规则应可解释、可测试。
- 区分读取尝试、成功读取、新增唯一内容、绑定已有内容、最终装包数。不要用一个计数混代所有含义。
- 已存在内容的复用不再消耗唯一正文额度；读取失败和未读取都不能伪装成已装入。
- target/candidate/related 是默认优先级，必要前提或例外的依赖不能因为叫 related 就随意剥离。如果无法完整容纳，明确标记该目标依据不完整，而不是当可完整回答的依据交给模型。
- 不简单扩大所有预算。先修复分配与重复计数，再用日志判断容量是否合理。

必要测试：首个候选有大量关联，第二/第三候选仍按额度被读取；多次重复关联不挤掉后续候选；候选读取失败不阻断其余候选；多子问题在紧预算下仍得到公平覆盖与明确 omitted 状态。

## 6. R4：修正预算裁剪及完整性保证

已发现：ApplyBudget 的字符超限分支按 RolePriority 升序删内容，candidate=1、related=2，结果先删 candidate，和注释要求相反。

要求：

- 条目数与字符预算使用一致的保留优先级，优先移除低相关、可选关联，再处理低优先候选。
- 不以 evidence_id 字符串排序代替排名/读取顺序，避免 e10 与 e2 的字典序改变保留顺序。显式记录稳定序号或检索排名。
- 记录 omitted 的条目路径、子问题、原因和依赖影响；重复 ApplyBudget 不重复累计同一项，补充取证后统计一致。
- 所有预算统计以最终实际发送的序列化包为准，包含元信息，不使用更新 omitted 之前的旧长度。
- 只有 target 剩余但仍超限时，不得 break 后继续发送超限包。采用完整语义节点投影/可验证切片，或返回显式预算不足状态。
- 配置下限和实际有效值要明确，不能让测试指定小预算却被隐式放大后仍宣称通过。

必要测试：candidate 与可选 related 同时存在时先删 related；e2/e10 顺序正确；单条 target 超大、多 target 超大、元信息本身超大均有确定行为；同包重复预算处理不改变统计；补充后总预算依然成立。

## 7. R5：验证投影和 relation 信息没有丢失

本项是必须核查的风险，不预设每个案例都已经发生：当前 ProjectSource 对大条目投影到固定字段集合；候选通过 GetConceptsWithExpansion 读取，与直接 ok 分支补入 Condition/Cost/Target/Facts 等的路径不同。

要求：

- 核对真实规则字段形式，包括本体限定字段、流水线、分支、时点、instant/continuous content、容量公式、计分表、局部槽位等。不能只保留 description 后宣称规则完整。
- 对同一规范目标和 relation，直接命中与从候选读取所得的必要语义应等价；不能一条路径有 Facts/ordering/boundary，另一条只剩对象说明。
- 复用现有解析/事实服务，避免在事实包里复制一套不完整的本体字段解释器。
- 投影保留回答所需的前提、例外、上限和时点。内容不足时显式记录缺失，不能让 essential_fields 标签冒充语义完整。
- 修复身份可能让原来被错误合并的内容重新出现、包变大。这是恢复数据，不得通过再次丢失事实来制造“压缩收益”。

必要测试：小于/大于投影阈值的等价规则回答依据一致；嵌套条件和例外保留；相同目标由直接/候选路径读出的关键字段一致；过大内容既满足预算也不伪装完整。

## 8. 修正评测口径：四层分别观察

现有 evaluator 把 legacy Matched 与 program 已装入的 target/candidate 都称为直接命中，语义不等价；top3 还受候选截取、输出字段和补充查询影响。

新增分层轨迹与指标，旧字段可保留供历史复现，但不能直接宣称可比：

| 层次 | 观察什么 | 不代表什么 |
|---|---|---|
| 检索召回 | 原始候选规范路径、排名、完整 intent、首轮/补充轮 | 不代表条目被装包 |
| 事实装包 | 已读取、实际发送的唯一条目、必要字段、omitted 原因 | 条目存在不等于能回答 |
| 模型引用 | Respond 实际选中的 evidence_id 和规范路径 | 引用存在不等于解释正确 |
| 答案 | 事实正确、回答所问、必要澄清、无依据断言、无关扩展 | 不能由 tier 或 pending 自动推导 |

记录“首轮计划后的召回”和“允许补充后的最终覆盖”，不要将 legacy 多轮累计命中与 program 首轮命中混比。计分路径有多种合法依据时，评测允许等价证据，不能只认唯一 expected ID。

补充取证的读取、关联、投影、装包耗时都要计入 trace；失败和超时也保留已消耗调用/token/阶段信息，不能重建一个空 trace 丢失开销。

## 9. 分阶段诊断实验：先定位，不急着再跑全量

### A. 冻结样本与失败归类

从已有 798 次运行中先梳理报告所说的“44 次 unavailable 且有 evidence”。这不是模型错误的判定，只是待检查集合。按问题去重审阅，同时保留每次运行差异。

每例至少标注：

- 计划是否保留了用户真正疑点。
- 目标规则是否被召回，排名如何。
- 该内容是否实际进入发送包，关键前提是否齐全。
- 有充分依据却未回答，还是只有无关/不完整条目。
- 引用与自然语言断言是否匹配。

允许多标签，并标出最早能够证实的失败阶段；证据不足就标 unknown，不能靠有 evidence 的计数填“模型拒答”。

形成约 24–32 个去重问题的开发诊断集，覆盖至少六款游戏，并覆盖已知退步类别、slot、歧义、未知对象、多问题。保留一批原本回答正确的对照题，避免只在失败样本上看见改善。

这批来自已观察结果的题是开发/诊断集，不称为留出集。此前新增的 16 题已经看过结果，也不能继续称为未见过的独立验证。

### B. 固定计划，离线比较事实包

冻结相同 question、plan、规则版本、检索结果，再分别运行原构建器与修复构建器。保存可读的正文/规范路径/关联/裁剪差异，不调用回答模型。

如果历史完整计划或事实包没有保存，明确缺失；可通过旧提交重新捕获输入，或选取重新生成后冻结的计划做受控比较，但不能把重建包伪装成历史请求实际见到的包。

报告：修复了哪些身份错配、漏装目标、必要字段丢失；哪些问题在计划/检索阶段就已经失败，修包无法救回。不能把诊断集的 expected ID 注入在线构建器。

### C. 固定事实包，单独测试 Respond

使用已经审阅为充分或明确不足的冻结事实包，直接运行 Respond，隔离 Understand 和检索随机性。

先保持原 program 的回答提示和相同模型/Thinking 配置，测修复事实包带来的变化。若充分依据仍频繁 unavailable，再单独做一个回答提示变体；不得同时改计划、字段投影、预算与提示。

重点观察：

- 充分且相关的证据能否被正确使用。
- 不充分证据是否仍能正常澄清/未查到。
- 规则陈述是否超出引用内容。
- reply 长度、结构化输出开销、reasoning/output tokens 与完整耗时。

不强制每题成功回答，不按题目硬编码出口；不因为有证据就拒绝 unavailable。正常语义判断失败不应以“一次额外重答”自动覆盖。

### D. 小规模端到端对照

R1–R5 和 B/C 验证通过后，在冻结诊断集运行隔离后的 legacy 与修复 program，每问每版重复三次。两版共享模型、档位、规则、索引、并发、预热和超时策略。

报告不同版本的有效配置指纹，至少区分：原 a992cfe 基线、原 program、仅确定性修复后的 program；回答提示变体若有，单独命名。不要把多个修改一起比较后将收益归给某一个。

小样本用于定位和筛查，不作架构优越性结论、不套用大样本显著性宣传。

## 10. 性能分析与进一步优化边界

原实验 Respond 单调用平均约 2801ms、输入 3674 tokens、输出 465 tokens，其中 reasoning 约 200 tokens。这些是旧 program 的历史观察，不能写成修复版结果。

本轮分别测：

- Understand / Respond 每次调用的完整耗时、输入、输出、reasoning tokens；字段缺失为 unknown。
- 首轮及补充轮的检索、正式读取、关联展开、投影、序列化、校验耗时。
- 正文 token、结构/元信息 token、重复正文比例、候选/必要关联/可选关联分布。
- 总墙钟时间、调用次数、修复和补充次数；并行区间不相加冒充墙钟。

若需压缩事实包，先移除冗余正文和不必要元信息、保留必要语义；将“身份正确性修复”和“包压缩优化”分开提交与测量。不要只把 MaxEvidencePackChars 调小。

没有旧路径同口径 token 数据时，不宣称已证明输入变大是唯一耗时原因。一次性修复多项后的收益是组合收益，不能做未经实验支持的细项归因。

本轮不改 Thinking=low。关闭思考的实验留待内容与流程正确后单独进行。

## 11. 门槛与停止条件

进入小规模真实模型实验前：

- R1–R5 行为测试均通过；实际发送包的路径、内容和预算可对账。
- 完整后端测试通过，涉及客户端协议时补跑 Android 相关测试。
- 默认 legacy 的有效提示与行为未被 program 配置污染。

进入下一次全量对照前：

- 冻结开发集上，已知确定性失效均已消除，未用题目特判。
- program 严格正确率点估计不低于同轮 legacy；充分证据却 unavailable 的问题得到可复核改善，未知/歧义的正确退出没有明显退步。
- 平均调用数仍低于 legacy，P50 不再呈现明显退步；报告实际差值和样本不确定性，不能只展示调用次数。
- 原本正确的对照题没有未解释的系统性回退。

满足以上条件可以继续原计划的完整配对验收，另冻结真正未参与调参的新留出题；全量默认切换门槛沿用上一计划，不因本轮修复而降低。未满足时，完成诊断报告并保持 legacy 默认，不循环重跑大实验、不改评分标准制造通过。

如果事实包已证实充分、精简、身份正确，而 Respond 仍显著退步，应明确记录“实现问题修复后，设计/模型匹配仍未解决”，再讨论架构调整；不能无限以实现问题解释所有失败。

## 12. 交付与提交顺序

建议分成可单独审查的提交：

1. 基线提示隔离与回归测试。
2. 证据身份、关联和重复计数修复。
3. 预算、公平覆盖、必要字段投影修复。
4. 分层指标与冻结输入回放工具。
5. 诊断报告；若存在单独提示变体，再单独提交和评估。

最终交付：

- 逐项 R1–R5 的复现测试、修改、结果、提交。
- legacy/program 实际提示与配置指纹，默认路径验证。
- 至少一例非 Splendor 的原/新事实包对照，展示规范路径、相关内容、必要条件和预算变化。
- unavailable 样本分类表和开发集选择依据，包括 unknown 与反例。
