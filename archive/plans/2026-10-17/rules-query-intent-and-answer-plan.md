# 问答查询意图保留与回答收敛：实施计划

日期：2026-10-17

执行对象：DeepSeek V4.1 Flash。请先阅读项目当前规范和本计划，然后完成实现、测试、实际问答回归与文档更新；不要仅回复另一份方案。普通实现选择自行决定，保持本计划的范围与验收标准。

## 1. 目标与产品原则

本次解决一个已经出现的真实问题：模型理解了用户的具体意图，却在工具查询中只留下宽泛名词；后端主要依赖这个名词检索，正确规则被排在后面；模型在候选未确认时结束回答，答案还扩展到用户没问的内容。

目标是让一次自然提问得到相关、有规则依据、简短的回答。改善发生在系统内部，不增加客人的表达负担。

遵循以下原则：

- 按正常交流理解用户，不逐字挑歧义。
- 能直接回答或用一句条件说明的，不追问无关状态。
- 保留规则查询，不把模型“自认为知道答案”当成跳过核实的依据。
- 模型负责理解意图和组织表达，程序负责检索、事实读取、引用验证和证据记录。
- 跨游戏通用，不给 Splendor、贵族或某个问句写特殊路由。
- 不新建完整棋盘状态采集、澄清对话引擎、通用规则裁决器或第二套检索服务。
- 本次不调整动画、音频、cue 和动画 QA 内容。

## 2. 真实案例与已确认原因

原问句：

> 呃这个盒里面有好多贵族，然后我选哪3个贵族出来呀？

当时模型提交：

```json
{
  "plan": {
    "queries": [
      {"relation": "explain", "entity": "贵族"},
      {"relation": "condition", "entity": "贵族"}
    ]
  }
}
```

工具返回的候选包含正确目标 `deal_nobles`，描述为“从游戏盒中随机盲抽 player_count + 1 枚贵族板块，放入贵族市场”，但排在贵族来访、贵族板块等概念之后。两项查询都是 unresolved；模型未按协议确认候选就回答，最终证据为 tier2。回答又列举三人、四人局数量，没有直接接住用户所说的三块。

源码已确认：

- `ChatOrchestratorService` 将原问题传给 `ExecutePlanAsync`。
- `RulesPlanService` 的语义召回主要使用 `entity`；explain 联合全文和名称，其他部分 relation 走名称检索。
- 原问题目前主要用于较弱候选情况下的名称线索补充，没有稳定参与动作/场景意图排序。
- 提示词同时要求“未确认候选要重查”和“信息够答立即停止”，两者边界不清楚。
- 当前回答证据统计反映查询状态，不等价于最终每句话正确；不得把 tier1 当作完整正确性证明。

因此不能归因于“规则库没答案”，不能只新增“贵族”别名，也不能把候选最高分直接当成正确概念。

参考回答的语义目标：

> 不用挑具体哪几块，把贵族板块背面朝下混匀，随机抽三块，再翻开摆到桌上就行。

不要求逐字一致；核心是随机抽取方式，承接用户给定数量，不无故询问人数，不展开三人/四人数量表。需要先确认当前规则数据支持最终使用的每项操作描述。

## 4. 改动 A：查询保留“用户要知道什么”

在现有 execute_plan 中增加每项查询的 `intent` 字段，表达当前子问题的动作、场景和疑点；`entity` 继续承担目标概念、准确名称或对象描述。优先扩展现有结构，不新增模型可调用工具。

语义约定：

- `entity`：查谁/什么。已知准确 ID 时可填写 ID，不要求模型凭空猜 ID。
- `intent`：针对它要知道什么。必须来自用户问题及有效上下文，不能写成模型已猜出的答案或包含尚未证实的规则。
- `relation`：需要解释、条件、顺序、边界等哪类规则信息。

本例合理计划示意：

```json
{
  "plan": {
    "queries": [
      {
        "relation": "explain",
        "entity": "贵族板块",
        "intent": "设置时从盒中取出三块贵族板块，应当如何选择"
      }
    ]
  }
}
```

重点是保留“从盒中取出、设置、如何选择”，不是强制以上字符串或字段值。不要让模型把 intent 改写成“随机抽三块是否正确”，以免用猜测污染检索。

单一疑点默认一个 query；只有确实需要不同事实时才拆分。不要机械地为每个名词生成 explain + condition 两项查询。真正的多问题仍需独立处理，不能为了节省调用合并丢失问题。

同步更新 SystemPrompt、工具描述、工具参数 schema、解析代码与日志，避免一个地方支持自然语言 intent，另一个地方仍要求只能填概念名。

intent 缺失时的降级规则要明确：单一子问题可以使用当前用户原问句；多子问题不能把整段问题不加区分地当作每项 intent。优先使用已提供的各自 intent，缺失项保守回到原有实体路径，不随意截词编造子问题。

## 5. 改动 B：结合意图召回、排序与读取事实

复用当前全文/名称检索和排序模块，在 plan 层把“实体定位”与“回答该问题需要的规则定位”区分开。

1. 实体词保留用于名称与身份定位；完整 intent 用于场景/动作的语义召回，候选按稳定概念身份去重。
2. 即使“贵族板块”精确命中对象，也不代表它的定义足以回答“设置时怎么选”。当查询带有具体 intent 时，应能补充检索相关动作/流程，而不是精确命中对象后立即结束。
3. 对候选使用完整 intent 的匹配信号，不让多个泛词/通道简单累加压过场景相关的候选。直接利用现有 ranking 能力，必要时小幅扩展并保留可解释分数来源。
4. 各 relation 的类型偏好不能把真正回答问题的流程节点排除；不要把所有关系一律改成无约束全文搜索。
5. 用户显式指定准确规则 ID 时保留其身份；补充意图检索不得悄悄把该 ID 替换成另一个对象。后续候选确认也不能被同样的宽泛检索再次打散。
6. 不预设“正确结果必须只有一个”。不同问题可能需要一个或多个相关规则；事实不足继续保守处理。

对比修改前后候选列表。先验证本例的完整意图能使 `deal_nobles` 显著前移，并通过同名对象的设置/获得/外观等对照问题证明改进来自语义区分。不要通过硬编码词表、Splendor ID 加分、放宽自动确认阈值、往 description 塞测试问句来达标。

默认不更换 embedding 模型，不重建数据架构，不增加额外 LLM 重排轮次。确需改变索引契约时再说明证据与成本；已有服务能完成则沿用。

## 6. 改动 C：统一“候选足够”与“确认完成”的协议

本轮保留现有的明确确认路径：

> unresolved 候选 → 模型选择相关候选的准确 ID → execute_plan 返回正式事实 → 回答。

候选描述用于选择目标，不能因为里面碰巧出现答案，就把未确认状态直接当成已完成。已有可靠自动解析路径可以继续使用；不要求所有查询机械增加一轮确认，也不自动确认最高分候选。

具体要求：

- 收到与问题相关的 unresolved 时，优先确认已有候选，不立即退到 list，也不先问用户内部概念叫什么。
- 完成确认后，不再为同一目标反复搜索。工具错误、候选不适合和新出现的实质问题按已有预算处理。
- 回答出口必须能识别“相关候选尚未确认却直接下结论”的情况。若仍有合理工具预算，进行一次有针对性的协议纠偏；不要无限重试或把所有规则问题一律拒答。
- 若某个多余 query 本就不属于用户需要解决的问题，允许明确终止它，并记录原因；不要为了清空 pending 强迫模型回答无关内容，也不能静默把它标成已验证。
- 调整提示词停止规则：已有充分且已确认的依据时立即回答；在候选阶段的信息用于选目标，不与正式事实确认混为一谈。

证据恢复需一并检查：历史 unresolved 若含多个候选，后续明确选择某个候选 ID，是否能够正确关联到原查询？不得把任何后续 ok 都用于清空所有 pending。

若现有证据结构不能表达这种明确确认，允许增加最小的服务端查询引用和确认关联字段。服务端验证关联存在、属于同一游戏/规则版本、选择对象确在对应候选中，并记录原问题与确认目标的关系。多问题或关系不兼容时保持未解决，不可仅因 ID 相同就合并。不要为此建设全新的工具调度框架。

用户最终不需要看到“正在确认候选”等内部术语。tier 仍只是证据状态，不能升级成回答真实性保证。

## 7. 改动 D：回答接住用户语境，只补缺失信息

更新简洁、跨游戏的回答原则，不把固定答案塞进生产提示词：

- 先回答用户正在问的方法、规则或判断，不从概念定义重新讲起。
- 用户给出了当前操作的数量，且只问选择方式时，优先承接数量。只有数量明显违反已确认规则或数量本身是问题时才纠正/解释。
- 不从“三块”反向断言实际一定是两人局，也不因此追问人数。
- 不主动罗列未被问到的其他人数配置、扩展规则或后续计分。
- 保持现有 TTS 简洁风格；必要的条件用一句话交代，只有影响当前结论且无法简洁解释时才追问。
- 所用规则事实来自已确认工具结果；工具提示、SystemPrompt 与最终回答约束不能互相鼓励“查不到就自行补规则”。本次仅统一直接涉及的提示协议，不扩大为整个回答系统重写。

## 8. 观测与回归样本

日志保留可检查的中间产物，而不依赖模型自然语言思考记录作为正确性证据：原问题、每项 entity/intent/relation、实际检索文本、候选排序及来源、选中 ID、确认关联、最终证据状态、工具轮次与耗时。

新增独立回归组，至少包括：

| 类别 | 示例/目的 | 验收重点 |
|---|---|---|
| 本次原句 | 盒里很多贵族，选哪三块 | 设置抽取规则，随机选，不询问人数 |
| 口语变体 | 开局这些贵族随便挑吗 | 与原句语义一致 |
| 显式步骤疑问 | 贵族是看正面挑还是不看抽 | 不误检索成来访条件 |
| 同对象不同动作 | 满足两位贵族，可以拿两块吗 | 获得/上限规则，不走设置抽取 |
| 纯对象问题 | 贵族板块是什么 | 保持对象解释能力 |
| 数量问题 | 三个人开局放几块贵族 | 此时应回答数量，而非只谈选择方式 |
| 多子问题 | 开局贵族怎么选，之后怎么获得 | 子意图隔离，分别获取所需规则 |
| 准确 ID 确认 | 选中候选后查询 deal_nobles | 不被再次宽泛检索带偏 |
| 候选不匹配/无依据 | 使用既有负例 | 不硬确认，不编规则，不循环查 |
| 非 Splendor 游戏 | 从已有规则库选至少两款游戏的自然问法 | 同对象的设置/使用/结算意图区分 |

非 Splendor 的标准答案、目标规则和可接受回答路径必须从实际数据核对，不凭空编造。保留现有外观识别、未知实体、数量计算和边界查询回归。

测试分三层：

1. 确定性测试：intent 解析/降级、检索参数传递、去重排序、准确 ID、确认关联、证据恢复及循环预算。
2. 检索评测：原有 gold/regressions 加新增自然问法，记录命中位置及错误确认。禁止只展示本例成功而忽略旧集合退化。
3. 实际 LLM 问答：固定模型与配置，保存实际 plan/结果/最终回复。对本次原句及若干变体重复运行，报告次数、通过数、失败样本；不要重试到成功后只保留成功日志。检查语义而非逐字匹配。

性能记录同一环境下的工具轮次、检索耗时和端到端耗时，给出中位数及较慢样本；小样本不宣传稳定的尾延迟。新增确认可能增加一次往返，必须如实记录，不为了速度跳过必要确认。自动解析在依据充分时可省往返。

## 9. 实施顺序与完成标准

按以下顺序完成，阶段性提交：

1. 保存当前行为基线：原句、实际工具参数、候选和回答；加入本次问题与对照回归。
2. 增加 intent，接通 schema/解析/日志及意图召回排序。先通过确定性测试，再对比真实检索。
3. 统一候选确认和停止规则，补证据关联及有界纠偏测试。
4. 收敛回答原则，跑实际模型回归及既有后端相关测试；发现失败先定位计划、检索、确认或表达层，不用盲目改提示词覆盖。
5. 更新当前架构/工具文档，提交实施报告。

完成应满足：

- 本例查询保留设置与选择方式，不再只查宽泛“贵族”并机械附带 condition。
- 正确设置规则被有效召回，经过明确确认或现有可靠自动解析后用于回答。
- 最终答复直接解释随机抽三块，不无故盘问人数或展开其他人数配置。
- 单对象不同意图、多问题、准确 ID、外观识别和负例没有因本次改动被简单牺牲。
- 证据状态与实际确认过程一致，无未确认硬升级、无重复确认循环。
- 新增及受影响的后端测试通过，既有检索回归结果和真实模型波动如实报告。

API、向量库或外部模型不可用时，继续完成不依赖它们的实现和测试，明确列出未执行验收与具体阻塞，不能将 mocked 测试写成真实端到端通过。

最终报告包含关键文件、实际执行命令、前后查询/候选/回答对比、性能代价、残留问题以及保留的无关工作区修改。不要把“增加一个提示词”或“把本题答对一次”当作完成。
