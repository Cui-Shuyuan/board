## 核心命题（用户原话）

> 所谓的动画，其实就是维护一组组件的状态。更具体一点说，在什么位置，以什么姿态。

> 从一开始我们就已经定义好了公共供应堆，这部分放宝石，那部分放牌堆。然后在 set 的时候，
> 这些宝石就从镜头外飞到了供应堆中，拿取，则是从供应堆移动至玩家保留区，这些都是最简单
> 不过的移动函数，如果设计得好，应该只需要填一个 source 和 destination 就够了。

由此推出：

1. **组件状态 = (zone, 顺位) + 姿态。** 世界坐标由 zone 的布局规则**推导**，
   动画数据里**不写坐标**。
2. **所有动画都是 zone → zone 的移动。** 设置阶段「从盒子里拿出来放进供应堆」和游戏阶段
   「从供应堆拿到持有区」是同一个操作，只是源 zone 不同（`offstage` 就是画面外的源 zone）。
3. **搬走要收拢。** 同一 zone 里排在后面的组件顺位前移，视觉上堆真的少一枚，而不是留空位。
4. **zone 是持久的逻辑容器。** 「公共供应堆」这类事实在设置阶段就确立，之后只是从中搬运。

## 运行时要维护状态（修正 2026-09-13 的「不跟踪历史」）

| 场景 | 做法 |
|---|---|
| 顺序播放 | 一条 cue 接着上一条 cue 的**终态**继续 |
| 重播当前 cue | 恢复到这条 cue 的**入口快照**（不重建对象） |
| 任意跳转 | 编译器离线复算每个 cue 的入口状态写进 runtime |

所以不是「运行端不跟踪历史」，而是**运行时维护连续状态 + 编译器负责跳转所需的入口状态**。
参见 [[tutorial-production-pipeline]]。

## 数据三层分工

| 层 | 文件 | 只负责 |
|---|---|---|
| 语义事实 | `games/{game}/flow.json`、`concepts.json` | 源、目的地、对象、数量 |
| 视觉绑定 | `games/{game}/tutorial/anim/_stage/{game}.table.json` | 语义区域画在屏幕哪里、颜色分几堆、模板外观、开局摆放 |
| 时间 | `games/{game}/tutorial/anim/{track}.json` 里那条 cue 的 `events` | 第几秒发生、强调、错峰 |

**cue 只写 zone，不写坐标也不重复 flow 的语义。**

```json

  "from": "gem_supply_diamond", "zone": "player_holding", "easing": "easeInOutCubic" }
```

## 动画 = 时间的函数（2026-09 重构）

**核心决定**：动画不靠「每帧推进一点」累积，而是 `Seek(t)` 直接采样算出画面。

理由不是优雅，是**可验证性**：批处理环境（`-executeMethod`）没有帧循环，
`Time.deltaTime` 恒为 0、`StartCoroutine` 的协程不会推进、`Time.captureDeltaTime`
也无效。因此只要动画依赖帧推进，就**无法离屏验证**，只能靠人肉截图——
这个盲区导致连续多轮「我这边通过、用户那边不对」。

重构后：
- 事件触发时，**逻辑状态立即到终态**（Store 是时间的阶跃函数）
- 视觉过渡登记为 `Clip`，由 `SampleClips(t)` 采样：位置/翻转/缩放/透明/洗混全部如此
- 暂停、跳转、倒放天然正确，不需要特判
- `CaptureTimeline` 可按任意步长逐帧出图，离屏就能看到完整动画

### 自检入口
```
Unity.exe -batchmode -projectPath <client> \
  -executeMethod BoardGameTutorial.Editor.TutorialFrameCapture.CaptureTimeline \
  -captureCue setup.cards.002.1 -captureFrom 4.0 -captureTo 7.6 -captureStep 0.2 \
  -logFile <log>
```
输出到 `client/CaptureOut/timeline/t<毫秒>.png`。

## 反复踩过的坑（都属「静默失败」）

| 现象 | 真因 |
|---|---|
| 字段永远读不到 | `JsonUtility` 不支持 `int?`/`float?`，静默留 null |
| move 从不执行 | `from` 写成字符串，而模型是 `List<string>`，静默丢弃 |
| 牌堆里出现宝石 | `from`+`take` 按位置取件，盒子里宝石排在卡片前面；需用 `template` 筛选 |
| 牌停在原地 | 补间终点取了「当前 zone」位置，而牌的归属还在盒子 |
| 牌被后续事件拉回起点 | 只动画面、不记录格位；逻辑归属必须同步落到目标格 |
| 牌堆看似正面朝上 | 停在牌堆上的市场牌未标记 `Flipped`，正面盖住了卡背 |
| **跳跃/重播/上一条进后面的 cue，画面空了** | 「不带状态进入」以前是 `Reset + ApplyInitial` —— 等于**回到开局**，前序 cue 里 `create` 出来的组件全没了（用户报的"跳进 cue 11 什么都看不到"：那三张卡背是 cue 10 create 的）。现在改成**从根重放到本条之前**（`stateOnly`，复用采样工具早就在用的入口链重放），于是"跳转"与"顺序播放"是**同一条状态路径** |
| **跳跃进后面的 cue，背景还留着上一张整幅图（盒面）** | **整幅图是播放器级状态，却不在入口状态里** —— `ZoneSnapshot` 只记「件 → (zone, order)」。以前的做法是"沿用当前那张图"，于是从有图的 cue 跳进没图的 cue 会把旧图带过去。现已按 track 复算入口整幅图（从 `board.default_picture` 出发，把本条之前的 `showbox` 走一遍），并且**采样也会导出 `picture`**，契约可以断言它 |
| **本地编译检查报 OK，Unity 报编译错误** | 检查器**没定义 `UNITY_EDITOR`**，而 `Assets/Editor/*.cs` 整段包在 `#if UNITY_EDITOR` 里 → 编译成空文件，里面什么错都查不出来（2026-09-18：`Items.Count`（LINQ 方法组）漏到 Unity 才发现）。已在 `check_unity_scripts.py` 的 csproj 里加 `DefineConstants`，并收录 `Assets/Editor/` 全量 |

**规律**：这些都不报错，只表现为「画面不对」。所以每遇到一种，
都要**把它变成观察工具能报出来的事实** —— 能静态查的进 `validate_cue_anim.py`，
只能运行期知道的进 `DumpState` 的导出字段（例如 `Showing` 就是为"牌到底显示哪一面"加的），
**不要再写 `SelfTest*` 自检**（已全部删除，见文末）。

## 入口状态是一棵树（2026-09）

**核心规则**：每条 cue 的入口状态由它自己声明的 `entry` 决定。

```
entry 未写      → 继承「上一条有动画数据的 cue」的终态（顺序播放的默认）
entry = "initial" → 牌桌初始状态
entry = "<cue id>" → 那条 cue 的终态
```

### 为什么需要它

对照教学的两条 cue 必须是**兄弟**，不是父子。例如：

```
        玩家区（0 张）
        ├── cue A「可以抽一张」：1 张 → 保留区 + 对勾
        └── cue B「不可以抽两张」：2 张 → 保留区 + 叉
```

如果 B 以 A 为父，演示 B 时手里已经有 A 留下的 1 张，画面就错了。
两条都声明 `entry: "initial"`（或同一个共同祖先），各自从同一张桌子出发。

### 实现

- `TutorialCuePlayer.ResolveEntryCueId(index)`：解出入口来自哪条 cue。
  没有显式声明时，**跳过没有动画数据的 cue**（它们不改牌局）继续往上找。
- `TutorialCuePlayer.ApplyEntryState(anim, entryCueId)`：
  用**独立**的草稿播放器，从 `stage.initial` 起沿祖先链把每条推到终态，
  再把结果整体交给正式播放器。
- 顺序播放下一条时走快捷路径（直接用当前画面），不重新解。

### 踩过的坑

| 现象 | 原因 |
|---|---|
| 牌堆消失、发牌方向反了 | 独立重建实例**没把组件交接过来**（只复制了 zone/order） |
| 牌背叠在牌堆上 | 重放时 `start.set` 又生成一份；且隐藏逻辑漏了「无片段」的分支 |
| 片段累积到 90+ | `clips` 只在回退时清空，换 cue 从不清理 |
| 市场牌与牌堆数量核对错乱 | `CountIn` 只判 palette，而市场牌与牌堆共用 `card_level_1` |

**共同规律**：这些全都只在「连续播多条 / 跳转」时才出现，单条 cue 的隔离测试永远看不到。
所以自检必须走真实路径（`SelfTestEntryTree` / `SelfTestLivePath` / `CaptureSequence`）。

## 洗混是通用方法（2026-09）

任何 zone 都能洗，只要在 cue 里写一条事件：

```json
{ "at": 0.5, "dur": 0.7, "action": "shuffle", "zone": "deck_level_1" }
{ "at": 0.5, "dur": 0.7, "action": "shuffle", "zone": "gem_supply_diamond", "amount": 0.6 }
```

`amount` 是强度倍率（省略或 0 = 1.0），用于小棋子或大牌堆的差别。

### 实现要点（都在一处，改这里就够）

`TutorialCueAnimPlayer.Shuffle` 内部类集中了全部参数：

| 参数 | 值 | 说明 |
|---|---|---|
| `AmpMin/AmpMax` | 4.0 / 6.2 mm | 水平幅度区间 |
| `FreqMin/FreqMax` | 8 / 14 Hz | 抖动频率区间（接近人手搓牌） |
| `DepthMin/DepthMax` | 0.25 / 0.60 | 纵向幅度占水平的比例 |
| `EnvelopePower` | 0.45 | 包络形状（前 1/4 起振、中段保持、末 1/4 收住） |

**每张牌的四个量都由组件 id 散列决定**（`StableHash` + `Hash01`，不用 `Random`）：
幅度、频率、初相、纵向分量。所以同一瞬间有的向左有的向右、抖得也不一样快。
若所有牌同相摆动，看起来只是整摞在平移，不像洗牌。

### 断言

`SelfTestShuffleGeneric` 检查三件事：
1. 三个牌堆都被洗到（张数 40/30/20）
2. **同一 zone 内每张位移互不相同** —— 实测 40 张里 39 种（98%）
3. 同一方法可用于非牌堆 zone（宝石供应堆）

第 2 条是核心：它把「各张独立抖动」这个手感变成了机器可查的性质。

## 选择器规则：单件 vs 整组（2026-09）

**模型始终是平的：一张牌就是一个 item。** 牌堆不是"一个对象"，
只是 Store 里 40 个 item 恰好都归属 `deck_level_1`。
「整体」只存在于**操作层面**：操作可以作用于单个 item，也可以作用于一组。

事件用选择器指定作用范围，**全操作统一**：

| 写法 | 含义 |
|---|---|
| `target: "card_back_1#5"` | 单件 |
| `zone: "deck_level_1"` | 整组（该 zone 内全部） |
| 两个都写 | **数据错误**：报警告，以 `target` 为准 |

### 为什么这样分

- **发牌**要精确到单张 → 用 `target`（或 `move` 的 `from`+`slot`）
- **洗混 / 高亮一整摞** → 用 `zone`，一次说清"这一组"
- 两者不需要两套模型；同一份扁平数据既能单张操作，也能整组操作

### 整组操作怎么算

以**组内重心**为锚点，而不是某张牌的位置：

```
每张牌的位置 = 重心 + (原位 - 重心) × g
每张牌的缩放 = 基准缩放 × g
```

这与"把整组当作一个对象缩放"等价，且不要求组是规则形状 ——
牌堆（斜向错开）、宝石堆、玩家持有区都能用。

### 踩过的坑

| 现象 | 原因 |
|---|---|
| 高亮只让堆底那一张大了一圈 | 事件写了单张 `target`，走了单件脉冲 |
| 一级修好了，二三级没有 | 另外两条 cue 还是单张写法（断言也只验了一级） |
| 同一个事件在两类操作里选中不同东西 | `Resolve` 是 zone 优先，`highlight` 是 target 优先 |

## 容器：任意一组的命名集合（2026-09）

选择器现在有三档粒度，**同一套机制**，不是三套：

| 选择器 | 含义 | 典型用途 |
|---|---|---|
| `target` | 一件 | 发牌、翻某一张牌 |
| `container` | **任意一组**（点名的一组，不要求同 zone） | 卡 + 压在上面的宝石；跨区的一组 |
| `zone` | 该区域全部 | 洗混一整摞、高亮整摞 |

同时写多个 → 报警告，按 **target > container > zone** 取优先级最高的。

### 容器怎么定义（在 stage 里）

```json
"containers": [
  { "id": "level1_deck_and_top",
    "items": ["card_back_1#36", "market_card_1_emerald#1"],
    "has_center": false }
]
```

`items` 是组件 id 列表，**可以任意组合**（跨 zone 也行）。
`has_center=true` 时用 `x/z` 作为整组锚点，否则用组内重心。

### 为什么不用父子节点（Node 层级）

经典做法是给每组建一个父对象、操作父 transform。这里**没有采用**：

- 组内每件仍是**独立组件**，所以既能整组操作、也能单独操作其中一件；
  父子节点会让单张牌的位置变成「父变换 + 本地偏移」，发牌要算两层
- 父子节点引入层级与生命周期问题（销毁/重建顺序），本文件里那些坑大多源于类似的隐式结构
- 组的成员是**数据**（id 列表），可以随时改，不依赖场景结构

代价是整组操作要遍历成员（几十个对象的循环，可忽略）。

### 整组变换的算法

以组锚点为心，**位置与缩放一起变**：

```
位置 = 锚点 + (原位 - 锚点) × g
缩放 = 基准缩放 × g
```

等价于「把这一组当一个对象缩放」，且不要求组是规则形状。
另有整组平移（组内位移相同、相对位置不变），用于「把这一组挪到别处」。

## 第一节显示盒面，牌堆在第二节飞出（2026-09）

**树的根是盒面图，不是牌桌。** 第一节（背景介绍）只有盒面；
第二节第一条才让三摞发展卡从盒子里飞到桌面。

```
盒面（第一节，bg.intro.*）
└─ 三摞发展卡（第二节 setup.cards.001.1：从盒子飞到桌面）
   └─ 市场 3×4、宝石供应堆、贵族、玩家区……
```

所以 `stage.initial` 里牌堆**不在桌面**，而在各自的盒子区：

| 模板 | 数量 | 初始 zone |
|---|---|---|
| card_back_1 | 36 | `box_level_1` |
| card_back_2 | 26 | `box_level_2` |
| card_back_3 | 16 | `box_level_3` |

每个牌堆一个盒子区（而不是共用一个 `offstage`），这样「搬进牌堆」可以用
zone 直接指定，不必列出 36 个 id。

### 新原语

**showbox** —— 显示/隐藏一张整幅图：
```json
{ "action": "showbox", "picture": "media/box.png", "on": 1 }
{ "action": "showbox", "on": 0 }
```
- 图片**正对相机**并居中（不是像卡牌那样平躺 —— 竖图平躺会被压扁并跑到画面底部）
- 挂在播放器自己下面，**不是** animRoot；换节重建画面时随 ClearActors 销毁，
  所以"隐藏"不需要在数据里额外写
- 第一节的牌桌本来就是空的，不需要隐藏牌桌

**move 的 group 模式** —— 一组建件**同时、同长**地各自飞向目标：
```json
{ "action": "move", "group": true, "from": ["box_level_1"], "zone": "deck_level_1" }
```
- 逐件错开会把一整摞牌拉成扇形；同步移动才保持"这一摞"的整体感
- `group: true` 时 `take` 缺省 = **该 zone 全部**（曾缺省为 1，一摞只飞出一张）

### 踩过的坑

| 现象 | 原因 |
|---|---|
| 盒面后画面全空 | 曾用 `animRoot.SetActive(false)` 隐藏牌桌，盒面消失时忘了打开 |
| 一摞牌只飞出一张 | `group` 模式下 `take` 仍缺省为 1 |
| 高亮自检失败 | 牌堆已改为"第二节才上桌"，自检要先跑完 001.1 |

## 树的第一子节点 = 先介绍的那个东西（2026-09）

**原则**：树里谁排第一，取决于**讲解顺序**，不是"某类组件有特殊地位"。
先讲发展卡，三摞牌就是第一个子节点；若先讲宝石，宝石就是第一个子节点。

**推论（要守住的）**：搬运、分组、展示这些机制**不能对牌有特例**。
牌堆能整组从盒子搬到桌面，宝石堆、贵族、玩家持有区也必须能用**同一条代码路径**做到。

### 为守住这条原则做的两件事

1. **每类组件各自的盒子区**，理由相同：
   - 牌堆本来自带模板（card_back_1/2/3），但**宝石共用一个 `gem` 模板**（靠 palette 区分），
     不分成 `box_gem_diamond` 等就没法用 zone 指定"搬这一堆"。
   - 所以现在：`box_level_1/2/3`、`box_gem_diamond/.../box_gem_gold`。

2. **`SelfTestGroupMoveGeneric`** 用同一条 `move + group:true` 分别搬宝石和牌堆，
   证明机制没有对牌特殊化：
   ```
   PASS 同一套整组搬运可用于宝石：box_gem_diamond 7 → 供应堆 7
   PASS 牌堆用同一机制搬进桌面：deck_level_1=36
   ```

### 为什么值得写这些坑

这套动画系统的复杂度都花在"状态、分组、搬运"上。如果某一类组件走了特例分支，
以后换成"先讲宝石"就要再写一份。原则是：**换讲解顺序不该改机制**。

## 入口状态总是从根解（2026-09）

**规则**：播放任意 cue 前，画面都从**树根**解出来（根画面 → 沿 entry 链重放到目标前一条），
**没有「顺序播放就沿用当前画面」的快捷路径**。

那条捷径看起来只是省一次重放，但它让两条路得到不同画面：

| 操作 | 结果 |
|---|---|
| 按右跳到下一条 | 从根解 → 盒面消失 |
| 顺序播到同一条 | 沿用当前画面 → 盒面还在 |

用户就是这么发现的（"按右盒面消失、往回两次又出现"）。**同一个位置，两条路必须一致。**

代价是每次换 cue 多一次重放（毫秒级），换来的是可预测性。

### 根画面

`stage.board.default_picture`（例如 `media/box.png`）是树根的默认画面。
它必须在**入口状态应用完成后**才应用 —— `AdoptStateFrom` 会 ClearActors 重建画面，
在它之前显示盒面会被这次重建销毁（我踩过一次）。

### 断言

`SelfTestJumpMatchesSequential`：对前若干条 cue，分别用「直接跳转」和「从根顺序播到它」
求入口状态，要求盒面可见性一致：

```
bg.intro.*          跳转=True  顺序=True    ← 第一节显示盒面
setup.cards.001.1   跳转=True  顺序=True    ← 盒面还在，牌堆从中飞出
setup.cards.001.2   跳转=False 顺序=False   ← 盒面已收
```

### 顺带

`Sprite.Create` **不给 sprite 命名**，所以「当前显示的是哪张图」必须自己记
（`currentPicture`），不能靠 `sprite.name` —— 我曾经因此让盒面在交接时被当成"无图"。

## 【待办】编译器 + 入口状态快照（用户已确认要做，暂缓）

### 现在是怎么解入口状态的（运行期）

跳到第 N 条 cue 时：

1. `ResolveEntryCueId(N)` 沿 `entry` 声明解出祖先链（不写 `entry` = 继承上一条有动画的 cue）
2. `ApplyEntryState` 用一张**草稿播放器**从 `stage.initial` 起，沿链把每条 cue 用
   `Seek(时长)` 推到终态（**只改数据、不建画面**）
3. `AdoptStateFrom` 把结果整体交给正式播放器，再从 0 播第 N 条

这是**正确**的，也是毫秒级；但 cue 数到几百条、或依赖链很深时会变成不必要的开销。
用户问过"是不是把前面 34 条都过一遍"——按链走，不是 34 条，但确实是"过一遍"。

### 要做的优化：离线编译 + 快照

```
编译器（离线，一次）：
  对每个 cue，按它的 entry 链算出**入口状态**，写进 runtime
运行期（跳转）：
  读快照 → 直接用，零重放
```

快照要包含（即当前"入口状态"的全部内容）：

- 每个 item 的 `ZoneId` / `Order` / `Flipped`
- 三摞牌堆等 stack zone 的**实际张数**（厚度由它算）
- 当前根画面（`stage.board.default_picture` 或 cue 覆盖后的图片路径）
- 需要的话还有 `EntryAnchor` / `EntryFrom`（影响后续"从盒子飞出"的起点）

### 为什么顺带解决了视频导出

**两者需要的是同一个东西：每条 cue 的起始快照。**

- 有快照 → 每条 cue 可以**独立起播**（任意切换、任意跳转都是常数时间）
- 有快照 → 每条 cue 可以**独立离线渲染成视频**（起始画面已知，不需要重放）
- 分支（"可以抽一张 / 不可以抽两张"是兄弟）在编译期就固化成数据，
  运行期/渲染器都不需要理解树的结构

### 实现提示

- 编译器的算逻辑就是现在 `ApplyEntryState` 的离线版本，**接口不用改**
- 入口状态的语义必须保持"从根解"，不能退回"沿用当前画面"
  （那条捷径导致过"跳转与顺序播放画面不一致"）
- 现在的运行期机制**作为对照实现保留**，方便编译结果与它逐条比对

## 特写取景（camera 字段，2026-09）

事件可以带 `camera` 指定取景：

```json
{ "action": "wait", "camera": "showcase", "camera_padding": 1.6 }
{ "action": "wait", "camera": "board" }
```

- 写 zone id → 把镜头对准该 zone 的格位包围盒（特写）
- 写 `"board"` 或留空 → 回到整桌取景
- `camera_padding`：留白倍率，**越大视野越宽、物体越小**。
  在「这是发展卡牌」的特写里实测：1.4→48%、1.6→49%、1.8→47%、2.0→43%，
  所以取 **1.6**。注意它不是线性的（格位包围盒与 card 自身世界尺寸并不相等），
  **调这个值要用实测扫描，不要只靠推算**。

特写开关在 `Trigger` 里统一处理（所有动作路径都生效）。

### 为什么需要它

整桌取景下（ortho ≈ 2.79）一张 63×88mm 的卡只占画面约 24%，讲"这是发展卡牌"时太小。
特写把 ortho 降到 ~1.0，卡占到约 49%。

## 用名称和位置区分，不要靠颜色（2026-09 用户裁决）

讲解"三种卡背"时，**靠名称 + 位置区分**：

```
sample_back_1 = 一级 → showcase_1（最左）
sample_back_2 = 二级 → showcase_2（中）
sample_back_3 = 三级 → showcase_3（最右）
```

**位置即身份**：同一张卡每次出现在同一位置，观众靠位置认级别。
校验器强制这条：`sample_back_N` 若被放到别的 `showcase_M` 会直接报错。

### 为什么不用染色

我一度给三张卡背加 `tint` 来"一眼可分"，用户反馈"像加了一层滤镜，颜色不对劲"——是对的：
染色等于给画面糊一层色，把卡背画作弄脏了。

而且**根本没这个必要**：三张卡背扫描图本身的平均色差异就很大——

| 卡背 | 平均色 | 主色 |
|---|---|---|
| 一级 | (0.35,0.45,0.26) | 绿 |
| 二级 | (0.52,0.41,0.24) | 黄 |
| 三级 | (0.35,0.40,0.50) | 蓝 |

（渲染时它们看起来都偏蓝，是缩放后的视觉印象；原图差异是明确的。）
`tint` 机制已整体撤除，避免有人再误用。

### 排查时踩的坑

我在"为什么渲染出来都偏蓝"上耗了大量轮次，反复用像素采样验证，结论反复自相矛盾
（导出贴图是绿/黄/蓝，渲染像素却是同一组蓝）。**用户是对的：应该停止纠结工具，改用
名称+位置这种不依赖视觉判断的方案。** 教训：当验证手段本身变得不可信时，
先换一个不依赖它的方案，而不是继续加探针。

## 两个"状态漏复制"的坑（2026-09，用户报的乱码与牌消失）

### ① 洗混时的 NaN —— `Mathf.Pow(负数, 小数)`

`sin(kπ)` 在 k=1 处会因**浮点误差**得到极小负数（~-1e-8），而
`Mathf.Pow(负数, 0.45)` 在数学上无定义 → **NaN**。

NaN 一旦写进 `Transform.localPosition`，Unity 每帧报同一个错，
并且这一摞牌**不再被渲染**（看起来像"消失"，后续 cue 也修不回来）。

修法：底数先夹到非负 `Mathf.Max(0f, Mathf.Sin(...))`。
**教训**：任何 `Mathf.Pow` 的底数都要先确认非负。

### ② 发完牌后消失 —— `hide_until_animated` 是**模板级静态**标记

它只能表达"这一**类**组件还没出场"。但可见性判断每帧都在跑，
一旦场景重建（换 cue 时 `ApplyEntryState` 会重建画面），
**已经发出去的牌又被当成"没出场"而归零透明** —— 用户看到"12 张牌全消失"。

修法：加**每件**的 `ZoneItem.Shown`，出场（move/fade）时置 true；
判断改为 `hide_until_animated && !Shown`。

### ③ 反复出现的同类错误：新增字段漏进复制清单

这已经是**第三次**了（`hide_until_animated`、`from_zone`、`tint`，现在是 `Shown`）。
有两处复制清单，**新增字段必须两处都加**：

| 位置 | 作用 |
|---|---|
| `EffectiveTemplate` | 实例色板与模板不同时克隆模板 |
| `AdoptItemsFrom` | 入口状态交接时复制每件 |

漏掉的后果各不相同（有的表现为牌不可见，有的表现为染色丢失），都不好查。
**新增字段时先搜这两个地方。**

## hide_until_animated 已删除（2026-09）

### 它原本是干什么的

模板级布尔：让这一**类**组件"在被动画带出来之前完全不可见"。
唯一用途是那 12 张待发市场牌——它们由 cue 12 的 `start.set` **预先摆在各自牌堆位置**，
不隐藏就会在洗混前叠在牌堆上，看起来像牌堆厚了好几层。

### 为什么删掉

它是**旧模型（对象必须预先存在）的遗留**。现在有了 `create`：

```json
{ "action": "create", "template": "market_card_1_emerald", "palette": "card_level_1",
  "zone": "card_market", "count": 1, "slot": 0, "flip": true }
```

发牌时**直接创建到市场格位**，待发的牌根本不存在 → 不需要"藏起来"。
`start.set` 也不再预置市场牌。

**它还是上一个 bug 的根源**：可见性每帧都要判断，而它是**模板级静态**标记，
场景一重建（换 cue 会重建）就把已发出的牌重新隐藏（用户报的"发完12张牌后消失"）。

### create 补齐的两个能力（顺带）

| 字段 | 作用 |
|---|---|
| `slot` | 创建到指定格位。缺了它只会追加到末尾，发牌摆不成 4 列网格 |
| `flip` | 出场时翻到正面。与 move 的翻转共用 `FlipFromYaw`，但**新建组件从 0° 起翻、走满一圈回到 0°**；若沿用 move 的 `(from, from+180)` 会停在 180°，把正面贴图镜像掉，终态看起来仍是背面 |

### 现在的可见性模型

1. **还没出场** → 对象**不存在**（`create` 之前没有它）
2. **已出场** → 正常渲染
3. `ZoneItem.Shown` 只用于"预先存在、之后被动画带出来"的少数情况

不再有"建出来但藏起来"这个中间态。

## 牌堆是真牌，发牌是真搬运（2026-09 用户裁决）

**用户的原话**：「那 40 张的牌堆是应该真的由 40 张牌组成的，发牌，就是把最上面那张真的翻过来，
移动到右边，这样才对。而不是靠什么在展示前隐藏起来的这种方式。」

### 正确的模型

```json
// 牌堆：真的是 40 张牌（只是背面朝上；牌堆里的牌在发出去之前不知道是哪张）
{ "action": "create", "template": "card_back_1", "plain": true,
  "zone": "deck_level_1", "count": 40 }

// 洗混：把这 40 张真的搓一遍
{ "action": "shuffle", "zone": "deck_level_1" }

// 发牌：搬走最上面那张、边飞边翻面，翻过 90° 时换面成它真正的那张牌
{ "action": "move", "from": ["deck_level_1"], "take": 1,
  "template": "card_back_1", "zone": "card_market", "slot": 0, "flip": true,
  "to_template": "market_card_1_emerald", "to_palette": "card_level_1" }
```

发牌后牌堆**真的**从 40 减到 36（`SelfTestDealSync` 逐条断言 40/30/20 → 36/26/16）。

### 为此新增的两个原语

| 原语/字段 | 作用 |
|---|---|
| `create` 的 `plain` | 不指定色板。一摞牌在发出去之前**不知道是哪张牌**，整摞同色板即可 |
| `move` 的 `to_template` | **翻过 90° 时换面**："翻开才知道它是哪张"。这是 `swap` 的自动版 |

`swap` 原语也保留了（手动换面），但目前发牌用 `move` 自带的换面。

### 踩过的坑

| 现象 | 原因 |
|---|---|
| 发到市场的牌一直是卡背 | 翻转条件写的是 `ev.flip && actor.BackSprite != null`，而**牌堆的牌没有 back_image**（它的正面就是卡背图），整条翻转+换面都没发生 |
| 牌堆张数翻倍（40→80） | `create` 被触发两次（先解入口状态再载入）。现在 `create` **幂等**：只补齐差额 |

### 仍未做（用户明确暂缓）

**"真正定义 40 张牌分别是什么、按固定顺序排列"** —— 用户说：
「要想真的定义40张牌，就要知道这40张牌分别是什么，再把它们按固定顺序排列起来，
这在当前场景下没有必要。但不代表这个需求本身没用，以后早晚会用得上，那时用上再说」

将来要做时的入口：`create` 已支持逐张指定（`template` + `palette` + `slot`），
牌堆可以用 40 条 `create` 逐张摆出确定的牌序；那时 `shuffle` 与"抽最上面一张"
需要按真实牌序语义处理（现在的 shuffle 只是视觉抖动，不改顺序）。

## 12 张真牌 + 空白牌凑数（2026-09 用户方案，已实施）

**用户的原话**：「其实我们根本不需要真的定义40张牌，只需要定义12张左右的牌，
就能让牌堆看上去像是有好几十张牌一样。前4张是正常的牌，后面都用空白卡面……
正所谓欺骗的艺术，但这样做的好处在于**翻开一张牌是个天然的行为**。」

### 实现

```json
// ① 先建真牌 —— 占据牌堆顶（order 0..3），所以会先被发出去
{ "action": "create", "template": "market_card_1_emerald",
  "palette": "card_level_1", "zone": "deck_level_1", "count": 1 }
// ② 再补空白牌凑够张数 —— 它们永远发不出来
{ "action": "create", "template": "blank_card_1",
  "palette": "card_level_1", "zone": "deck_level_1", "count": 36 }
// ③ 发牌：搬走最上面那张并翻开
{ "action": "move", "from": ["deck_level_1"], "take": 1,
  "template": "market_card_1_emerald", "zone": "card_market", "slot": 0, "flip": true }
```

**关键**：`PickFront` 取 **`Order` 最小**的那件 = 牌堆顶。所以**真牌必须先创建**
（占 order 0..11），空白牌排在其后。

### 为什么这个方案好（用户说的"天然"）

- 真牌**一开始就是它自己**（真卡面 + 卡背都在）→ **不需要换面**
- 于是 `swap` / `move.to_template` / `SwapTo*` **整套都删掉了**
- 发牌就是"搬走最上面那张并翻开"—— 一个动作，没有任何生成代码
- 空白牌只是让牌堆看上去有几十张，它们永远不会被发到市场

### 踩到的坑

## 翻面 = 换面，不旋转（2026-09 已修）

**根因**：`card_back_*` 模板原本只有一张贴图（它的"正面"就是卡背扫描图），
于是"翻转"只能靠**旋转同一张贴图** —— 旋转 180° 必然产生**镜像**（用户看到的"镜像卡背"）；
再加上"转到一半换贴图"，前半程显示的又是卡面。换一条 cue 时场景重建、旋转复位，
镜像就"突然恢复正常"（不是修好，是被重置掩盖）。

**修法**：

1. **牌堆里的牌只有卡背**（`card_back_N` 的 `face_image` = 该级卡背，`back_image` 为空）——
   牌还没翻开，无所谓是哪张牌
2. 发出去时 `move` 的 `to_template` **换成市场卡模板**，那一面就是真卡面
3. 翻转采样**按"朝上/朝下"决定显示哪一面**，`localRotation` 恒为 `identity`：

   ```csharp
   bool faceUp = clip.Item == null || clip.Item.Flipped;
   var backSide = clip.Actor.BackSprite != null ? clip.Actor.BackSprite : clip.Actor.FaceSprite;
   clip.Actor.Renderer.sprite = faceUp ? clip.Actor.FaceSprite : backSide;
   ```

4. `SelfTestDealSync` 加了断言：市场牌与牌堆牌**都不许被旋转**（旋转 = 镜像）

**教训**：一张牌的两面应当由**两个贴图**直接切换。用旋转去表达"翻面"是错的 ——
它翻的是**同一张图**，必然镜像。旋转只有在**两面都在**（真正的双面渲染）时才有意义。

## 【已解决】翻转的实现方式（2026-09 用户实机截图）

### 用户看到的现象

- **cue 12 中途**：发出去的是**卡面朝上**的牌，而牌堆还是卡背；有一张显示的是
  **左右镜像的卡背**（"Splendor" 反写），像是翻到一半
- **cue 13 一开始**：那些镜像的卡背**突然恢复正常**

用户的判断（正确）：**如果牌堆真是 40 张牌、发牌就是把最上面那张自然地翻过来，
就不可能出现这两种现象。** 出现它们说明实现里有一堆补偿动作。

### 真实原因（我查出来的）

牌堆用的 `card_back_*` 模板**只有一个贴图**（它的"正面"就是卡背扫描图，没有独立的背面）。
于是我的"翻转"实际做了三件互相打架的事：

1. 把**同一张卡背图**绕 Y 轴转 180° → 必然看起来是**镜像的卡背**
2. 转到一半（超过 90°）时**换贴图**成市场卡面 → 于是**前半程显示的是卡面**
3. 换一条 cue 时场景重建、旋转复位到 0° → 镜像"突然恢复正常"（不是修好，是被重置掩盖）

### 根因与本该有的做法

**一张牌的两面应该由两个贴图直接切换表达**，而不是"一张图 + 旋转 + 中途换图"。

- 牌堆里的每张牌：一面是卡背、另一面是它的真卡面
- "翻转" = **显示另一面**；不需要旋转，也不该产生镜像
- 旋转只在需要"看到翻的动作"时才有意义，且那应是**真正的双面 3D 翻转**（两面都在）

所以明天讨论的不是调 flip 的参数，而是**重新定义牌的两面怎么表达**。
现在的 `flip` / `swap` / `to_template` 三个机制是在模拟一件本该自然的事，
这也是这套实现"一团乱麻"的来源。

### 这也和"40 张牌是什么"是同一个问题

不知道牌堆里每张是什么牌 → 就无法给每张牌准备"它的真卡面" →
只能整摞共用一张卡背图 + 发出去时临时换图 → 于是需要各种 trick。
**把"每张牌是什么"定下来，翻转自然就简单了。** 两件事应当一起解决。

## 分支：共享父状态 + 牌堆顶不同（2026-09 已验证支持）

**用户提出的场景**：「如果抽到了红色牌，可以加入手牌；抽到蓝色牌则必须塞回牌堆底」。
这是一个**两条兄弟 cue 共享同一个父 cue**、但**牌堆顶那张牌不同**的场景。

### 结论：支持，而且不需要新机制

每条 cue 的入口状态都是**独立**按 `entry` 链从根解出来的，所以：

1. **共享父状态**：两条兄弟声明同一个 `entry`（那个父 cue），各自重放都会得到**相同**的牌堆
2. **让顶牌不同**：在各自的开头用 `move` + `slot` 把不同的牌**换到牌堆顶**（order 0）
3. **抽牌**：`PickFront` 取 `Order` 最小那件 = 牌堆顶 → 抽到的就是各自摆上去的那张

实测（`SelfTestBranchDifferentTopCard`）：

```
PASS 分支A（抽红）抽到 market_card_1_ruby
PASS 分支B（抽蓝）抽到 market_card_1_sapphire
PASS 两条兄弟分支抽到不同的牌 —— 共享父状态、但牌堆顶不同
```

### 关键机制：zone 内换位是支持的

`ZoneStore.MoveToAt` **支持同 zone 换位**：先把该件从原格位释放，再抢占目标格位；
若目标格位已被别人占，**占用者被挪到下一个空位**（它的格号变了，但它本来就是"没被指定过"的）。

注意 `MoveTo`（不指定格位的那条路）对同 zone 会**直接返回** —— 换位必须用
`MoveToSlot` / `MoveToAt`（即事件里写 `slot`）。

### 这套模型为什么能成立

因为**牌是个体、格位是地址、抽牌取 order 最小**：
"牌堆顶是哪张"就等价于"谁的 order 最小"，而 order 可以被事件改。
所以"让不同分支抽到不同的牌"不需要任何新原语，只需要改顺序。

### 测试依赖

`SelfTestBranchDifferentTopCard` 依赖三条临时 cue
（`branch.shared.001` / `branch.red.001` / `branch.blue.001`），
它们**不在正式 runtime 里**。跑这条测试前需要先把它们注册进 `full.runtime.json`。
若要长期保留这条测试，应改成"自建场景"（不依赖外部 cue 文件）。

## 状态契约与对账工具（2026-09，用户提议）

### 为什么要做

以前判断"这一 cue 演得对不对"靠**看渲染出来的像素**。像素会骗人：
采样坐标算错、读到旧帧、离屏渲染里某些效果根本不发生（早期的 fade 是协程）。
而"谁在哪个 zone、几件、朝上还是朝下"是**数据**，可以用程序精确比对。

### 两个文件 / 三个工具

| 文件 | 作用 |
|---|---|
| `games/{game}/tutorial/anim/{track}.json` | **一个动画一个文件**：每条 cue 一段 —— `story`/`note`（人读）+ `enter`/`exit`/`timing`（对账）+ `start`/`events`（引擎执行）；`cues` 按轨道顺序排 |
| `games/{game}/tutorial/anim/{track}.exitstate.json` | **采样终态**：引擎生成，别手改（`DumpState -dumpCues`） |
| `scripts/dump_states.sh` | 采样终态：**一次 Unity 启动**从轨道头播到尾，每条 cue 记一笔 |
| `scripts/check_cue_script.py` | 对账：`--all` 整条查，`--chain` 只查跨 cue，`--cue X --which enter` 单条查 |

（2026-09 用户要求合并：契约原来一条 cue 一个文件，翻十几条要开十几个文件；
采样也一样，而且每条 cue 各启动一次 Unity、各自从头重放一遍 entry 链。
现在两边各一个文件、一次跑完。注意 `script.{track}.json` 是**口播稿编辑源**，
两条链路互不写对方。）

### 契约结构

```jsonc
// anim/full.json —— 顶层，cues 按轨道顺序（--chain 依赖这个顺序）
{ "schema_version": 1, "game_id": "splendor", "track": "full",
  "kind": "animation_contract",
  "cues": [ /* 每条一段，见下 */ ] }
```

```jsonc
{

  "entry_from": "setup.cards.001.3",   // 父 cue（树根写 null）
  "story": "自然语言：这一 cue 发生了什么（给人看、给我自己推理）",
  "enter": { "zones": { ... } },       // 第一帧状态
  "exit":  { "zones": { ... } },       // 最后一帧状态
  "timing": { "动作": "对应哪句口播的时间段" }
}
```

zone 的状态写成：`count` / `face_up` / `face_down` / `kinds`（**按身份统计**）。

### 关键设计决定

1. **契约里只放语义状态**，不放坐标/缩放 —— 那些是从 zone+格位推出来的表现层，
   写进去只会因为改布局而误报
2. **`kinds` 用语义名**（`一级绿`、`宝石红`），工具负责翻译成引擎的
   `market_card_1_emerald|card_level_1`。理由：契约是给**人**审阅的，
   写引擎的叫法看不出在讲哪张牌
3. **契约只声明它关心的 zone**。没提到的 zone（宝石盒、贵族）不算差异 ——
   否则每条 cue 都要把整张桌子抄一遍，契约会膨胀到没人维护。
   "无关区域有没有被动过"是**不变量**的职责
4. **`entry` 应当由工具采样父 cue 的出口自动填**，不要手写 ——
   手写的只是"我以为的父状态"，父 cue 错了它会跟着错，跨 cue 对账就失效

## 为什么对账没抓到「朝向」两个问题（2026-09 用户验收）

### 两个问题的真正原因（都是"取反"式语义造成的）

**① 牌堆最上面那张朝上**：牌堆里的 4 张真牌没有被声明成"背面朝上"。

```csharp
step.Item.Flipped = !step.Item.Flipped;   // 取反
```


## 牌堆外形与翻转（2026-09 用户定义）

### 牌堆错开模型（最终，2026-09，用户三次纠正后）

**底部 8 张各自错开，第 8 张往上的全部重合**（按 `order` 算，order 0 = 最下面）：

```csharp
float lift = Mathf.Min(slot, maxVisible - 1);
x += lift * display.dx;   z += lift * display.dz;
```

**判据（这才是"发牌看不出变少"的真正条件）**：
> **发牌后，没被取走的那些牌坐标完全不变。**

实测：`发牌后未被取走的牌坐标完全不变（变化的 0 张）`。

我前后错了三次，每次都把"错开"锚在错误的一端：

| 写法 | 后果 |
|---|---|
| `visible = Clamp(total,1,max)`，按可见层数错开 | 发一张少一层 → 越发越薄 |
| `lift = min(capacity-1-order, max-1)`（从顶部锚定） | 顶部 8 张重合、下面错开 → 一摞看不出台阶 |
| `lift = min(total-1-order, max-1)` | 张数一变整体平移 |
| **`lift = min(order, max-1)`** | ✅ 底部错开、其上重合，取走重合块里的牌外形不变 |

**教训**：我两次用自己的假设写断言（"顶部错开"、"跨度不变"），
于是断言"通过"但没实现用户要的效果。**断言必须对着用户描述的模型写，不能对着我的实现写。**

### 翻面：压扁-展开，不用旋转（2026-09 用户要求）

用户报"翻出来的正面卡牌都是镜像的，左右反了"。

**根因**：把一张平面贴图绕 Y 轴转到 180°，屏幕上就是**左右镜像**。
真实卡牌翻过去不镜像，是因为实体牌的两面是两个不同的面；我们只有一张平面贴图。

**修法**：用 2D 里表达翻牌的标准手法——**压扁-展开**，全程不旋转：

```
0 → 0.5：横向收缩到 0（牌"立起来"侧对镜头），显示背面
0.5 → 1：横向展开回原宽，显示正面
squash = max(|1 - 2k|, 0.02)   // 不要压到 0
```

断言：市场牌**没有被旋转**（旋转即镜像）、缩放已恢复原值。

### 牌堆错开模型（早期记录，已废弃）

**要点：错开量必须用 `capacity` 算，不能用当前张数。**

```csharp
int maxVisible = display.max_visible > 0 ? display.max_visible : 8;
int deckCapacity = zone.capacity > 0 ? zone.capacity : Mathf.Max(1, CountInZone(zoneId));
int fromTop = Mathf.Max(0, deckCapacity - 1 - slot);
float lift = Mathf.Min(fromTop, maxVisible - 1);
x += lift * display.dx;   z += lift * display.dz;
```

"第几格错开多少"是**固定的**（只跟 capacity 有关），与还剩几张无关：

- 靠近顶的格（lift 小）永远重合在一起
- 越往下错开越多，到第 maxVisible 格封顶
- 更下面的格全部落在**同一个位置**（重合块）

于是从顶上发牌时，可见外形**完全不变** —— 被发走的那几张本来就在重合块里。

实测：40 张与 36 张的跨度都是 `0.1120`，错开层数都是 8，
**牌堆顶那 5 张的坐标完全一致**。

**踩过的坑（三次）**：三次都保留了同一个共同点 —— **错开层数随张数变化**。

| 写法 | 后果 |
|---|---|
| `visible = Clamp(total, 1, max)` 再按可见层数错开 | 发一张就少一层 → **越发越薄** |
| 按 `order` 从底部锚定（`layer = min(slot, max-1)`） | 同上：张数一变整体就平移 |
| 按 `fromTop = total-1-order`（用当前张数） | 仍薄：发出的牌不在重合块里，抽走就少一层 |
| **按 `deckCapacity-1-order`** | ✅ 固定外形，"发 7 张只剩一张"的问题消失 |

用户的原话最准确：「发出的那4张牌，其实是连带着另外一部分牌是重叠在一起的。
只有最底部那8张牌是错开的，这样发出4张牌，牌堆的样子也不会改变。现在这个牌堆的话，
如果发出7张牌，牌堆看上去就只会剩下一张，然后这一张特别耐发，这是不对的。」

### 一条容易说错的结论（用户纠正过）

我一度写成"**布局不该依赖还剩几张**"——**这是过度概括，是错的**。
"张数 → 形状"是完备函数，用张数算完全合法。

准确的表述是：

> **不是"依赖张数"错，而是"让错开层数依赖张数"错。**

两种模型都依赖张数，差别只在依赖哪一个量：

```
张数 → 形状（错开层数固定，只有高度/位置变）   ← 用户要的，看不出变少
张数 → 形状（错开层数也变）                     ← 之前的，变薄明显
```

**可推广的判断标准**：不是"用不用张数"，而是
**"发牌后可见外形会不会变"** —— 任何会随发牌而改变的量，都不该进入牌堆外形。

### 牌堆错开模型（用户原话）

> 假如这一堆有20张牌，那应该是最下面一张牌放在那里，然后倒数第二张牌错开一点，
> 盖在最下面那张牌上，倒数第三张牌再错开一点盖在倒数第二张上，以此类推，
> 然后倒数第8张牌一直到倒数第20张牌，**一点都不错开，重合在一起**，

```csharp
int layer = Mathf.Min(slot, maxVisible - 1);   // 超过部分与第 maxVisible 层重合

```

断言（`SelfTestOrientationMatchesSprite`）：

- 底部 8 张逐层错开且间距恒定

```csharp
bool faceUp = item.Flipped;

```

### 【最终】牌堆外形：按"距顶容量"锚定（2026-09）

**真正有效的判据是"轮廓厚度"**，不是"某张牌自己的坐标"：

```
40张: 厚度=0.112  台阶数=8
38张: 厚度=0.112  台阶数=8   ← 发牌中
36张: 厚度=0.112  台阶数=8   ← 发牌后，完全不变
```

```csharp
int deckCapacity = zone.capacity > 0 ? zone.capacity : Mathf.Max(1, CountInZone(zoneId));
int fromTop = Mathf.Max(0, deckCapacity - 1 - slot);
float lift = Mathf.Min(fromTop, maxVisible - 1);
```

**为什么必须"距顶"而不是"距底"**：发牌取的是**离顶最近**的牌。
所以形状必须由离顶最近的那几张决定 —— 取走它们，外形才不变。
按 order 从底部锚定时，取走的正是形状最外层的牌，轮廓立刻缩短（实测 0.112→0.080→0.048）。

## 牌堆模型（用户定义，2026-09 定稿）

### 叠放与发牌顺序

用户对牌堆的完整描述：

> 先把一张牌放在桌上，它是 order 39，作为牌堆的最下面一张牌存在。
> 再把一张牌盖在 order 39 的左下一点点，作为 order 38，它是倒数第二张牌，
> 再把 order 37 盖在 order 38 偏左下一点点……一直叠到 order 32，倒数第 8 张牌，
> 这 8 张牌组成了牌库的形状。从 order 31 开始，倒数第 9 张牌就完整地盖在了
> 倒数第 8 张牌上，不再有任何偏移，一直到 order 0。

> 第一个被发走的肯定是 order 0。——**order 0 是牌堆顶，先被发走**。
> 越晚被发的越靠**右上**。

所以：

| | |
|---|---|
| **牌堆顶（先被发）** | `order` **最小**（0） |
| **最下面（最后被发）** | `order` 最大（capacity-1） |
| **错开方向** | 越晚被发的越靠**右上**（`dx > 0`、`dz < 0`） |

### 位置公式

```csharp
int fromBottom = deckCapacity - 1 - slot;     // order 越大 → 越靠"最下面"，错开越多
float lift = Mathf.Min(fromBottom, maxVisible - 1);
x += lift * display.dx;    // display.dx = +0.016（偏右）
z += lift * display.dz;    // display.dz = -0.016（偏上）
```

`order 0..7` 逐层错开形成台阶，`order 8` 及以上全部重合在 order 7 上。

### 为什么"发牌不改变形状"是天然的

发牌从 `order 0` 开始，而 order 0..7 在**重合块**里 —— 发走它们不影响台阶。
要发到 order 8（第 9 张）才开始动到台阶。**不需要任何"保持形状"的代码。**

### 断言（`SelfTestPileDealShape`）

```
PASS 发 32 张后形状不变（厚度 0.112、台阶 8，其中 0 次发生了变化）
PASS 发到有偏移的那几张时开始变小（台阶 8→7，厚度 0.112→0.096）
```

1. **`PickFront` 的取件方向与模型相反**：它取 `order` 最小，而当时位置公式是
   从"距顶"锚定的，两者凑成了"从牌堆底发牌"。
2. **反复用自己推断的模型写断言**，断言"通过"却没实现用户要的效果。
3. **两次读到上一次出图的残留文件**（没先 `rm -rf CaptureOut/timeline`），白查两轮。
4. 用户三次纠正我"哪端是顶"，而我每次都用新的推断去改，而不是**先确认再改**。

**教训：模型类问题必须先与用户对齐语义（哪端、哪个方向），再动代码。**

## 【已修】二级/三级牌堆重合 —— 两个根因（2026-09）

### 根因 1：容量写错

`deck_level_2` / `deck_level_3` 的 `capacity` 都写成了 **40**，而它们实际只有 30/20 张。
叠放台阶落在 `order = capacity-1 .. capacity-maxVisible` = **32..39**，
而这两摞根本没有那些 order → 全部落进重合块 → **看上去只有一张**。

改成 `capacity = 40 / 30 / 20` 后三摞都是 8 层台阶：

```
t=2.1   deck1: 40张 台8   deck2: 30张 台8   deck3: 20张 台8
```

### 根因 2：位置计算里读 `CountInZone` 造成自引用

`ComputeZonePosition` 曾经调用 `CountInZone(zoneId)`，
而 `CountInZone` **会去读格位表**，格位表又由 `ComputeZonePosition` 构建 ——
**自引用**（严重时无限递归、Unity 静默崩溃，日志只打一半）。

**规则：位置计算只准读 `zone`（配置）与 `order`（参数），绝不读任何"当前有几张"的状态。**

### 最终公式（按容量锚定，不可改）

```csharp
int deckCapacity = zone.capacity > 0 ? zone.capacity : 8;
int fromBottom = Mathf.Max(0, deckCapacity - 1 - order);
float lift = Mathf.Min(fromBottom, maxVisible - 1);
```

**为什么必须锚容量、不能锚实际张数**：发牌从 `order 0` 开始，若锚实际张数，
牌一被发走"距底"就变小 → 台阶被吃掉（实测 40张8层 → 36张4层）。
锚容量则是固定映射 → 发走任意张，其余牌的台阶位置都不变。

断言：

## 【已修】高亮不能暂停，而洗混能（2026-09）

用户："cue11 播放高亮动画时按空格暂停，高亮动画不会停住；对比之下 cue12 的洗混动画能停住。"

**根因是两套机制**：

| 动作 | 机制 | 暂停表现 |
|---|---|---|
| `shuffle` / `flip` / `scale` / `fade` / `groupScale` | **时间采样片段**（`clip`，`Seek(t)` 的纯函数） | 暂停即停 ✅ |
| `highlight` 单件（`PulseActor`） | **协程** `RunTween(ScalePulseRoutine)`，靠 `Time.unscaledDeltaTime` 自己跑 | 暂停照样放完 ❌ |

**修法**：`PulseActor` 改走时间采样 —— 直接复用 `HasGroupScale`
（它本来就是"以某点为锚点整组缩放、去程+回程"），把锚点设为该牌自身位置，
等效于**原地呼吸**，不必再造第三种脉冲机制。

```csharp
var clip = ClipAt(actor.Item, actor, synthetic);
clip.HasGroupScale = true;
clip.GroupCenter = actor.LivePosition;   // 锚点 = 它自己 → 原地放大
clip.GroupGrow = grow;
```

**验证方法（可复用）**：暂停的语义就是"**不再调用 `Seek` 时状态不变**"。
`TraceHighlightScale` 采样后**不再 Seek** 再读一次，两次必须相同：

```
[Hl] t=1.10 采样后=0.0974 暂停后再读=0.0974 一致
```

**规则**：任何"随时间推进的视觉"都必须做成 `Seek(t)` 的纯函数（片段），
**不要用协程** —— 协程与时钟无关，于是暂停、跳转、倒放都会不一致。


## 【规范】为什么会不停出现"脏动画"，以及怎么防（2026-09）

### 结构化原因（这才是它会反复出现的原因）

**取景（`frameZoneId`）是播放器级状态，跨 cue 保留。**
一条 cue 不声明 `camera` 就**沿用上一条**，而这件事**在单条 cue 的文件里完全看不出来**。

| cue | 声明的取景 | |
|---|---|---|
| cue9 | `showcase` @0.1 | |
| cue10 | `cards` @0.05 | ← 切早了（当时的 bug） |
| cue11 | （无） | 沿用 `cards` |
| cue12 | `board` @0.0 | |
| cue13 | （无） | 沿用 `board` |

### 脏动画的定义

> **某一帧上，"已经存在的状态"和"当前的取景/层次"不匹配。**

它必在两处发生：**跨 cue 边界**（取景是隐藏的延续状态）、
**同帧内多个事件**（顺序决定中间态）。

### 根子：我在写"步骤"，不是在写"每一帧长什么样"

步骤之间那段时间会发生什么，我没写，它就自己发生了。
**"同时发生" = 同一个 `at`**；只要把两件事放在同一个 `at`，中间态就消失了。

### 已加的防线：`check_framing_chain`（跨 cue 取景检查）

`scripts/validate_cue_anim.py` 现在会按轨道顺序走一遍，报出：

```json

```

**规则：凡是"改变画面内容"的动作，都必须与"改变取景"的动作同时或在其之后；
承接来的取景要显式写出来，不要靠推断。**

### 顺带修掉：cue12 事件未按 at 升序

## 【根因·必须记住】`what != null` 永远为真 —— JsonUtility 会给嵌套类字段造空实例（2026-09）

**现象**：`action.take.different.001` 里一条最普通的 transfer

```json
{"at": 3.35, "action": "transfer", "realizes": "<ontology::transfer>",
 "source": ["gem_supply_diamond","gem_supply_sapphire","gem_supply_ruby"],
 "destination": "player_holding", "stagger": 0.25}
```

（"从这三个供应堆各取一枚给玩家"）**一件都没搬**，画面上什么都不发生。引擎日志：

```
transfer 的 what 一个候选都没有（cue action.take.different.001）：concept=''
```

可脚本里**根本没写 `what`**。查脚本文件、比对 JSON、跑校验器 —— 都没问题。

**根因**：`JsonUtility.FromJson` 会给**嵌套的可序列化类字段自动造一个空实例**。
`CueAnimEvent.what`（`ConceptRef` 是 class）在"JSON 里没有这个键"时**不是 null**，
而是 `concept == null` 的空对象。于是引擎里那句

```csharp
if (ev.what != null)          // 永远成立
    cands = Store.ConceptCandidates(ev.what.concept, ...);   // concept 为空 → 0 个候选 → 报错返回
```

把"没写 what"当成了"写了空 what"，直接 `return plan`（不猜、不动）—— 对的行为用在错的前提上。

**修法**：加 `CueAnimEvent.HasWhat => what != null && !string.IsNullOrEmpty(what.concept)`，
所有"脚本有没有点名"的判断（`PlanMove` / `PickSelector` / `TriggerHighlight` 入口检查）都改走它。
`start.set` 那处**早就是对的**（写的是 `seed.what != null && !string.IsNullOrEmpty(seed.what.concept)`）
—— 所以这个坑只在别处，靠"抄旁边那段"能躲过去，但得先知道要抄。

**教训（可推广）**：
> 判断"脚本里有没有写"，要看**值**，不要看**引用**。
> 而且要看的是**引擎解析后的对象**，不是脚本文件 —— 文件写对了不等于引擎读对了。
> 契约（文件里写的）↔ 引擎读到的 ↔ 采样采到的，是**三层**，不是两层。

| "介绍完成后立即被销毁，然后镜头切回来" | 下一条 cue 开头 `destroy` + `camera: "supply"` |
| "介绍黄金时它也是几个宝石进入一个 zone" | 黄金样本进 `gold_display`，与宝石展示位**隔开一段距离**（"黄金不属于宝石"的视觉依据） |

> 样本与真件绑同一套概念 ⇒ "按概念点名"会同时命中两者。
> 凡是"要搬/要补一件真件"的判定（`transfer` 的 `what`、`start.set` 预置），
> 样本**不参与竞争**（`sample: true` 的模板排除掉）；

盒里的黄金被判成"说不清是哪一件"。

展示位 z=-2.85 时画面顶边到 -0.89，而发展卡市场最低 z=-1.06 **正好落在框里**。
写 `"camera_padding": 1.25` 收框后顶边到 -1.73，市场被排除干净。
（多 zone 同框 `"gem_display,gold_display"` 自带 1.25，不用另写。）

## 【新】取景 vs 契约：`check_cue_script.py` 的第三类检查（2026-09）

状态对账查的是"**该在的在不在**"，查不出**不该出现在画面里**的东西 ——
宝石介绍镜头里出现一级发展卡，状态**完全正确**，只是"入镜了"。

所以新增：**取景框 ∩ 有内容的组件 vs 契约声明**。

- 几何**镜像**引擎 `FitCamera`（`frame_bounds` / `visible_rect`）：多 zone / `supply` / `cards` /
  单 zone 的留白倍率、`orthoSize`、可见地面矩形（`halfW = orthoSize*aspect`、`halfH = orthoSize/sin(pitch)`）。
  两边一旦漂移，这条检查就开始撒谎 —— 所以写得和引擎一样笨，注释里互相点名。
- "在画面里"的判据是**组件本体与框相交**（按 zone 的 `size` 算半个宽高），不是"中心在框内"：
  只看中心会把"卡片下沿露在画面顶部"判成没入镜，而用户看到的恰恰是那一条边。
- 用采样的 `shows == "hidden"` 判"画面上看不见"，不另推一套 offstage 规则。
- 级别是**警告**（用户定的措辞就是 warn）：入镜的东西不一定是错的（供应区特写必然带上市场与牌堆）。
  处置办法两个 —— **改取景**，或**在契约里声明它**（声明了就是真的在比它）。`--strict-framing` 升成错误。
- `board`（整桌取景）不查：整桌本来就"什么都看得见"，枚举没有意义。

实测：宝石介绍加上 `camera_padding: 1.25` 后，001.1/001.2/001.3/002 四条**取景警告全部消失**；
供应区那几条（003.1→005.2、nobles.001.1）稳定报 `card_market` + `deck_level_1` ——
正是"供应区特写必然带上它们"，要不要处理由人决定。

这是既有那条规则的反方向，两条合起来才完整：

| 动作 | 与切取景的关系 |
|---|---|
| **新增内容**（create / transfer 进来） | 可以在切镜头**之后** —— 观众等着看它出现 |

（引擎在同一帧内先执行完所有 at 相同的动作再渲染，所以同 at 就够；

> **"同时发生" = 同一个 `at`**（这条早就写在规范里了）——

## 【工具·重要】把「引擎自己说的话」收进采样（2026-09）

`action.take.different.001` 里有三条高亮写成"点名这个供应堆第 0 格的那枚宝石"：

```json
{"action": "highlight", "what": {"concept": "gem", "parts": [{"key":"color","value":"<diamond>"}]},
 "zone": "gem_supply_diamond", "order": 0}
```

画面上**什么都没发生**。引擎其实报了：

```
what='gem' 在 gem_supply_diamond 没选中任何件（cue action.take.different.001）
```

但那句话只写在 Unity 日志里 —— **对账（比状态）看不见它**，因为那一动压根没生效、状态没变。
用户的原则是"这类问题应该一查就能查出来"，所以：

- **`TutorialFrameCapture` 采样时挂 `Application.logMessageReceived`**，把这条 cue 里的
  warning/error 收进采样的 `"problems": [...]`（去重、每条 cue 最多 20 条；`Debug.Log` 不收，
  所以"本条 cue 没有动画数据"这类正常信息不会进来）。
- **`check_cue_script.py` 见到 `problems` 就 FAIL**，把引擎的原话打出来。

这样"脚本要求的事没发生"这一类（点错选择器、未知 zone、未知模板、候选不唯一…）
**全部**进入对账视野，不必再靠人翻日志。

## 【根因】`order` 是**稳定地址**，不是"第几个"（别在脚本里点它）

上面那三条高亮点 `order: 0` 之所以没选中，是因为 **order 不会因为搬走而重排**：

```csharp
// ZoneStore.MoveTo：「从原 zone 释放自己那一格。**不重排其他格位**：别人的地址保持不变。」
```

所以 4 枚宝石在 `gem_supply_diamond` 里的 order 可能是 **3,4,5,6**（前面 0,1,2 被搬回盒子了），
"堆顶那枚"是**剩下最小的 order**，不是 0。

⚠️ 注意这里与另一条记忆的矛盾：早期写的是"搬走要收拢，顺位前移，视觉上堆真的少一枚"。
**实际实现是不重排**（`CloseGaps` 只补位置变化，order 不变 → 位置也不变 → 它基本是空转）。
对 `stack` 显示（牌堆、现在的宝石堆）来说两者看不出差别，因为摞起来以后中间的洞是看不见的；
但对 `count` 显示（市场、持有区）来说，**会留下空位**。

**规则：脚本里不要用 `order` 去点"第几件"。**
结构性落位才用它（`create` / `stack` 的 `slot`、`transfer` 的落位序号）。
"点某一类件"用 `what`；"点整堆/整片"用 `zone` —— 那次修正就是把三条高亮改成整堆。

## 【设计·用户定的】宝石供应堆要像牌库：**稍微错开压在一起**（2026-09）

用户：「后续的 4/5/7 枚宝石的动画效果很不理想。正确的效果应该是**和牌库类似**，
4/5/7 枚宝石**稍微错开一点压在一起**，而不是像现在这样子（摊成两行）。」

落法：把 `gem_supply_*` / `gold_supply` 的 `display` 从 `count` 改成 `stack`，
参数照牌堆那一套（`deck_level_*` 用的是 `mode: stack, dx/dz: -0.016, max_visible: 8`）：

```json
"layout":  {"type": "pile", "cols": 1, "x_step": 0.0, "z_step": 0.0},
"display": {"mode": "stack", "dx": -0.055, "dz": -0.055, "max_visible": 7}
```

- **每枚错开 0.055**（≈ 1/8 个直径，宝石 43mm）—— 比牌堆的 0.016 大，因为宝石要**数得清**：
  4/5/7 的差别靠"露出来几道边"读出来（这正是那一节的教学目的）。
- **方向与牌堆一致**（-x/-z）：order 0（最先被拿走的）在最前/最上。
- `stack` 模式下引擎的层次规则自动生效：`sortingOrder = 模板值 + (张数 - order)`，
  order 越小越盖在上面 ✓。

**顺手修的两件事**：

1. `GlowFor`（高亮底板）原来按 `layout` 的步长算尺寸 —— `stack` 模式下 layout 的步长已经不作数了，
   会算出一块盖不住堆（或大得离谱）的光斑。现在按 `|dx|*(可见层数-1) + 件宽` 算。
2. `validate_stage_layout.py` 的**包围盒警告从 25 条降到 11 条**：原来 `block` 布局算出来的
   包围盒（7 枚 = 两行，高 1.72）与邻居堆、市场、展示位全都"重叠"；改成一摞后不再打架。
   —— 这也是个信号：**摆成一摞本来就比摊成两行更省地方**。

## 【用户定的·重要】游戏盒是**抽象概念**，不做实体：从盒里拿出来 = `create`（2026-09）

用户：

**但在讲规动画里不实例化它**：不建 `box_*` zone、`initial` 也不往里摆件。

### 为什么这是对的（不只是"简单"）

那个 zone 的 `role: offstage` —— **观众完全看不见它**。于是它变成一个"能藏东西的地方"：
件可以在盒里躺着、被搬进搬出，而**状态对账也看不出来**（只是从一个看不见的 zone 挪到另一个）。
去掉它之后：**每一枚件都在被契约断言着的区域里**，没有藏身之处。

### 改了什么

| 层 | 改动 |
|---|---|
| stage | 删掉 9 个 `box_*` zone（3 个 `box_level_*` 本来就没人引用）+ **清空 `initial`**（开局桌上什么都没有） |
| 脚本 | 宝石/黄金入堆：`create`（"从盒里拿出来"）；收尾：`destroy`（"放回盒子"）；贵族也 `create` |
| 引擎 | `destroy` 支持 `count`/`quantity`（"放回 3 枚"就说 3）；预置不再"先搬后生"（没有盒可搬） |
| 校验器 | **stage 里不许有 `<game_box>` 概念的 zone**；**契约不许断言不存在的 zone** |

### 顺带抓出来的两个真问题

1. **契约在"对着空气断言"**：删掉 zone 之后，`bg.intro.001.1`、`setup.gems.001.1`、`005.1`
   的契约里还留着 24 条 `box_gem_*` 断言 —— 而**没有任何检查发现**（契约里多写一个不存在的 zone，
   采样里没有它、比较时按 0 算，或者干脆没人比）。已新增检查：契约声明的 zone 必须在 stage 里存在。
2. **`create` 的语义是"补齐到 N"，不是"再加 N"**：

   ```csharp
   int have = Store.CountInZone(zone, ev.template, ev.plain ? null : ev.palette);
   n -= have;              // ← 已有 4 枚时写 count:1 会算成 -3，直接 return（什么都不做）
   ```

   所以 4 → 5 → 7 要写**目标数量**（4 / 5 / 7），不能写增量（+1 / +2）。
   贵族同理：写三条 `create 1` 只会建出第一块（后两条被幂等吃掉），要写一条 `create 3`。
   **它为什么必须幂等**：`ResetToStart()`（回退/重播）目前**不能撤销 create**——它只把
   *还在* 的件摆回入口的位置，这条 cue 里新建的件不会被删掉、被 destroy 的也回不来。
   于是"事件重放一次"若不幂等就会翻倍。**这是个已知缺口**（见待办）：
   真要做到"Seek(t) 是纯函数"，快照得能**重建**被销毁的件（存 template/palette/face），
   重建之后再让 `create` 变成"加 N"就安全了。

### 账怎么算（去盒之后的取舍）

- **每一维仍然被断言**：每个 cue 的契约把该时刻有件的 zone 都断住（供应堆 0→4→5→7→4、
  黄金 5、贵族 3），所以"凭空多一枚/少一枚"照样会当场报出来。

  —— 待办。
- 那个"藏东西的地方"没了之后，覆盖面实际上是**变严**了。

### 用户那句"清场要与切镜头同帧"的检查，判据修正过一次

## 【用户报的·已修】看到一半按 →，下一条继承的是**半成品状态**（2026-09）

用户截图：cue12（发牌）看到一半快进，cue13 的三级市场**两张是卡背**，而且牌堆右下角

### 复现（`-advanceSkip 0.5`，先复现再修，这是规矩）

`DumpAdvancePath` 加了 `-advanceSkip <0..1>`：第一条 cue 只 Seek 到该比例，然后调
`Complete()`（= 玩家按 → 时播放器干的事），再进下一条。实测（**修之前**）：

```
setup.cards.002.1 播到 50%      : 市场 2 张 → 卡面 1 / 卡背 1；没落位 1 件
setup.cards.002.1 Complete() 后 : 市场 12 张 → 卡面 1 / **卡背 11**；没落位 1 件
setup.cards.002.2（下一条）      : 同样的坏状态，并且一路继承下去
```

### 根因：`Complete()` 用的是 `TriggerFinal`，而它是个"半成品"

```csharp
// 旧 TriggerFinal：只处理 transfer 的**位移**，其余原语只当"外观"
if (ev.action == "transfer") { MoveToSlot(...); ApplyCurrentPlacement(...); return; }
foreach (var actor in Resolve(ev)) { ...复位缩放/透明度... }
```

它**不套用 `to`（终态朝向）**，也不处理 `create` / `destroy` / `stack` / `showbox` ——
于是被"补完"的发牌落在市场却仍是**背面**；被快进打断的补间没人收尾，牌就停在半空。

### 修法：`Complete()` 走**正常播放同一条路**

```csharp
while (nextIndex < cueDoc.events.Count) { Trigger(cueDoc.events[nextIndex]); nextIndex++; }
clock = Mathf.Max(clock, TotalDuration);
clips.Clear();            // 补间作废：不该有"卡在半空"的件
StopAnimations();
SyncActorsToStore();      // 画面按 Store 摆到终态
```

按 → 时走的是 `Next()` → `Complete()` → 下一条 `continueState: true`，所以**状态不可能不一致**。

### 修完实测（同一命令）

```
setup.cards.002.1 Complete() 后: 市场 12 张 → 卡面 **12** / 卡背 0；没落位 **0** 件
后面每条 cue 也都正常
```

### 教训（可推广）

> **"跳着看"和"顺着看"必须落到同一个状态。** 任何"中途离开一条 cue"的路径
> （→、自动前进、将来的拖动进度条）都必须先把这条 cue **推到终态**，
> 而"推到终态"必须复用**正常播放的那套处理** —— 另写一份"只改状态"的简化版，
> 迟早会在某几个原语上漏掉（这次漏的是 `to` 和 create/destroy/stack）。

## 【用户报的·已修】按 ← 退回上一条，画面还是宝石（2026-09）—— 同一族的三处"状态与画面/顺序解耦"

用户截图：从 cue14（宝石介绍）按 ← 回 cue13（`setup.cards.002.2`），画面还是宝石。

### 复现工具（这次加了两个，都是"复现用户的按键"）

- `-advanceSkip 0.5`：第一条只播到 50%，再调 `Complete()`（= 按 → 时干的），然后进下一条。
- `-advanceBack "A,B"`：A 播完 → **按 ←** 回到 B（B 可以是"没有动画数据"的 cue）。
- `Report` 也补了「展示位件数 / 宝石堆件数 / 相机 orthoSize」—— "市场被留在镜头外"正是靠相机大小看出来的。

### 三处根因（一句话：**状态不能和"有没有画面对象/顺序对不对"绑在一起**）

1. **"本条没有动画数据"的提前返回不重建入口状态** ✗
   跳转进这种 cue 时，上一条的世界 + 镜头都留在原地。
   修：`!hasScene || !continueState` 时也走 `ReplayEntryChain` + 重新取景 + 复位整幅图。

2. **`TriggerMove` 把 `to`（终态朝向）写在 `if (actor == null) continue;` 之后** ✗
   入口链重放是 `stateOnly`（没有 actor）→ 重放出来的市场牌**全是背面**。
   修：状态（`Flipped`）先落，再管画面。**这是"状态与画面解耦"的第二次翻车**（第一次是 `TriggerFinal`）。

3. **入口链重放按"动画脚本的 cue 列表"找目标** ✗
   动画脚本里只有 17 条有动画的 cue，另外 **92 条纯口播 cue 不在里面** →
   跳到这种 cue 时找不到目标 → **一路重放到全片终态** ✗✗
   （实测：跳到 cue13 得到"全片终态"，宝石堆 17 件 = 20−3 —— 正是这个特征值暴露了它）。
   修：播放器把**整条轨道**的 cue 顺序交给动画播放器（`SetCueOrder`），重放按它走、遇到目标就停。

### 顺带修掉的两个"工具/判据"问题（都是它们让 bug 藏起来的）

- **`hasScene` 判据错**：原来用"画面上有没有对象"，而**介绍那几条桌上本来就是空的**
  → "空桌"被误判成"还没建桌" → **顺序播放时也在重建入口状态**（实测整条轨道状态被叠一遍：
  市场 12→24 张）。改成"**stage 载入过没有**"。
- **采样器没交出整轨顺序**：于是它对"没有动画的 cue"的入口状态**解错**（一路重放到全片终态）
  → 采样与真播放器走的不是同一条路 ✗。**采样必须和播放器同一条路**，否则对账比的是假状态。

### 修完实测

```
按 ← 回到 setup.cards.002.2 : 市场 12 张全正面 / 没落位 0 / 宝石堆 0 / 展示位 0 / 相机 2.79（整桌）
半途跳走 Complete() 之后     : 市场 12 张全正面 / 没落位 0
全量对账                     : 0 处不一致（109 条）
```

### 教训（写进规范）

> 三类东西必须**各自独立**：
> ① **状态**（谁在哪、朝向）—— 绝不允许依赖"有没有画面对象"；
> ② **画面**（补间/高亮/光晕）—— 可以随时丢，`stateOnly` 时一律不做；
> ③ **顺序**（一条 cue 的前后）—— 状态重建必须按**整条轨道**的顺序，不能按"有动画的那几条"。
> 违反任何一条的症状都是"看起来只是画面问题，实际状态已经错了"。

## 组件面片必须跟着相机转（billboard）：否则斜视会把组件压扁（2026-09 用户报"组件像被压矮了"）

**用户原话**：「我想去掉 50° 摄像机这个设定……结果现在摄像机还是 90° 的，只不过把所有组件的高给
压缩了，看起来很难看。还是恢复所有组件的原始尺寸吧。」

**根因**：不是谁在改 `localScale`（`LocalScaleFor` 只按 mm/PPU 做等比缩放，全程没有非等比缩放）。
是所有**组件面片都立在世界的 XY 平面**里（`localRotation = Quaternion.Euler(0,0,roll)`），
而取景相机是 50° 斜视的。正交相机没有透视，斜看一个立着的面片，高度方向按 `cos(pitch)` 投影
—— 50° 时只剩 **64%**。所以"摄像机是 50°，画面却像 90° 俯视 + 组件被压矮"这两件事是同一件事。
（`showbox` 的整幅图**早就**是 `tr.rotation = cam.transform.rotation` 正对相机摆的，注释里甚至写了
"俯视 50°，平躺会被压扁" —— 即当年只把盒面摆对了，组件漏了。旧设计文档里写的
"正交相机 + 微倾 billboard 保证可读性"本来就要求这么做。）

**修法**：`TutorialCueAnimPlayer.SpriteRotation(roll) = Quaternion.Euler(CameraPitch,0,0) * Quaternion.Euler(0,0,roll)`
—— 面片平面**平行于屏幕**，组件永远按原始尺寸/原始宽高比显示；`roll` 仍然是在面片平面内转（语义不变）。
9 处设置旋转的地方全部换成它（建对象、复位、翻面、洗牌、旋转补间），`CreateSpriteObject` 里也先摆正
（否则第一帧会以"立着的"姿态闪一下）。取景俯角 `camera_pitch` 默认值三处统一改成 **90**（stage /
`TutorialCueAnimData` / `framing_geometry.py` 的兜底值）。

**关键结论**：`camera_pitch` 从此是**纯观感参数** —— 改它只改布局的纵深压缩，不会再压扁组件。
想要"坐在桌边"的代入感就调小（比如 55~65），组件尺寸始终真实。

**验证（纯表现改动必须"状态一字不变"）**：

  文件字节数都一样 2281150）—— 证明这次只动了表现、没动状态。
- 新加 `ShapeReportForTest()`：断言每个 actor 的朝向 == `SpriteRotation(自己的 roll)`（面片平行于屏幕）
  且 xy 缩放相等；采样器每条 cue 打一行 `[Shape] <cue> 件=… 姿态不符=0 非等比缩放=0 相机俯角=90°`。
  **状态采样看不见姿态**，所以姿态必须单独断言 —— 这是这一族问题的通用教训。
- `validate_cue_anim.py` 17 cue 0 错 0 警；`check_cue_script.py --all` 0 处不一致，

  不会新增越界内容）。

## 卡牌"白边 + 扫描纹"：两个都不是素材脏，是几何与采样（2026-09 用户报）

用户：「能让卡牌也让模型重绘一下吗，四角有一点点白边，而且还有扫描纹」。查完发现两条都不需要重绘：

（原扫描里量到正面卡下角圆弧 21px @11.36px/mm ≈ 1.9mm），而矩形件铺满整幅后 alpha 全是 1.0
→ 角上那块纸留了下来。四角 20×20 块近白像素：48%/44% → 0%（1mm 圆角只降到 12%，
**2mm 才对** —— 半径别拍脑袋，按原扫描的圆弧量）。
修法：`matte_pipeline.process_rect` 的 `--card-corner-mm`（4× 超采样抗锯齿圆角）
+ `--card-rim-px`（收掉四周纸边再缩回，输出尺寸/mm 尺度不变）。只对卡开；贵族的角靠键台面

**"扫描纹"的主因是缩小采样走样，不是素材噪点**。卡面 748×1045，而画面里通常只有 130~560px，
但贴图一直是 `new Texture2D(..., false)`（无 mip 链）+ Bilinear：缩小只取 4 个像素，
印刷网点/纸纹不会被平均掉，反而变成**闪烁麻点**。改成 mip 链 + Trilinear（日志实测

**工作方法**（每批固定动作，值得保留）：
1. 读这一组的口播 + 时长 → 逐条定「有没有状态变化」；
2. 写 `/tmp/batchN.py`：**幂等**地把 cue 合并进 `anim/full.json`（按 runtime 轨道顺序重排 cues，
   `entry_from` 默认上一条）；契约写**整桌账**（特写镜头会入镜邻区，取景检查要求"画面里有的都要声明"）；
3. `validate_cue_anim.py`（数据/本体/取景链）→ `from-linux` 同步 → `dump_states.sh` 采样 →
   `check_cue_script.py --all`（契约 vs 引擎）→ commit。

**工具链上踩到的坑（都已修）**：
- **校验器读了上一条事件的 `what`**（`what` 在事件循环里比 `contains` 检查更晚才赋值，跨 cue 还会串）→
  把"往持有区搬一枚黄金"误报成"把发展卡搬进持有区"。修法：循环开头就 `what = ev.get("what")`。
- **`stack` 对同一模板在一个 zone 幂等**（`CountInZone>0` 就跳过）→ "每级多排 4 张真卡"实现不了，
  同一种牌在一个牌堆里只能有一张；且 `pad = capacity - len(real_templates)` 会被这个数直接改变垫牌数。
  正解：每级只多排**市场没用到的那一色**（一级黑/二级白/三级蓝）作牌堆顶真卡。
- **补丁必须幂等**：字符串追加式的补丁重跑一次就把真卡表从 4 张变 8 张、再变 12 张，
  连累 74 处对账不一致。写数据补丁一律"赋值成目标值"，不要"在原值上追加"。
- **校验器的身份别名**只认"一级黑"这种带"级"的写法（写"一黑"匹配不到，会报"契约未列出的身份"）。

## ★ 多棵树（用户 2026-09-21 提的架构点子）——**第 1 步已落地**

用户原话："我们应该允许一个动画有**多棵树**。比如说最开始那个盒面图，那就是一个孤零零的节点。
后面介绍牌，一棵树，可能有几个节点。然后镜头切到真实的桌面时（也就是那 3 个牌堆，实际操作镜头，
而非演示用镜头），又一颗树，而且是最重要的**主树**。一通操作后，开始介绍宝石。在那几个演示镜头中，
又是一颗独立的树，后面讲怎么设置时，就又回到了主树里，将那些宝石放在卡牌市场旁。
……这样处理就完全不用考虑什么'把镜头拉远'、'暂时让其他组件不可见'的问题了，
它**天然就是除了那些东西之外什么都没有**的状态。"

**为什么它对**：
- "该有的有、不该有的就没有" 从"每条 cue 手工维护"升级成**结构性保证** ✓；
- 每棵树**有自己的 extent** → 特写不再被主桌 10.6 的纵深顶住（"画面太小"根因消失）✓；
- 演示件（样卡/宝石样本/展示位）搬进自己的树 → 主树里不再需要 create/destroy 这些道具、
  也不再需要 `showcase`/`gem_display` 这类"假 zone" ✗✓（一批清理动作可以删掉）；
- 树之间是**切**（cut），不是状态操作 ✓。

**设计草案**：
- 数据：`full.json` 顶层加 `trees: [{id, stage, initial}]`（每棵树自带 stage：zones/templates/extent）；
  每条 cue 加 `tree: "<id>"`；**契约链在树内成立**（enter == 父 exit ✓），
  跨树的 cue 声明 `tree` + 该树入口状态（= 一次 cut ✓）。运行时轨道同步带 `tree` 与 `entry_from` ✓。
- 引擎：`LoadCue` 按 cue 的 `tree` 取对应 stage；**树切换 = 换 stage + 重放该树的入口链 + 原子换画面**
  （换树本来就是"换场景"，之前讨论的"重建会不会闪"在这里才真正有意义 ✓）；单棵树内保持现在的行为 ✓。
  跳转也必须只由 cue id 决定画面 ✓（每棵树各自的初始状态 + 树内父链 ✓）——
  这正是"不管怎么跳，那一 cue 的画面完全一样"的完整版 ✓（顺带解决现在 entry_from 读不到的问题 ✓）。
- 取景：extent 按树算 ✓；`camera` 语义不变（要入镜的 zone + fill ✓）。
- 检查：采样器要能"按 cue 跳进对应树" ✓；对账按树分别对 ✓；契约链/取景链检查按树分治 ✓。
- 迁移：把 109 条 cue 标 tree（盒面/介绍牌/主桌/宝石演示/贵族演示…）；
  样本件（`sample_*`）从主树搬进演示树；删掉主树里对应的 create/destroy 与展示位 zone ✓。

**没争议的部分**：这是"教学动画=若干独立演示场景 + 一棵主场景"的正确抽象 ✓，
用户已明确要（"这样处理就完全不用考虑拉远镜头/临时隐藏"）。**这是下一步的主工程**。

**追加（用户 2026-09-21）：树的维护要写进脚本，脚本要写成「文字版动画」** ——
"文字类型的脚本负责的工作越多，最终成品质量就越稳定，因为 LLM 比起图片明显更擅长文字处理"。
所以 `trees` 块里每棵树要用文字写清"叫什么/为什么要它/初始状态/范围"；

**cut 的语义必须写在数据里**，不能只靠 zone 列表暗示 ✗。详见 `tutorial-animation-todo.md` 第六节。

### 2026-09-21 追加：换树与镜头必须同帧

用户报 “cue17 结尾不干净”的根因：换树发生在 `LoadCue`，而本条 `at=0` 的 `wait camera` 要等

`camera`**（哪怕只是 `board`）。`validate_cue_anim.py` 的“换树镜头口径”检查会直接报 error，
不再依赖事后发现画面脏帧。
