## 核心命题（用户原话）

> 所谓的动画，其实就是维护一组组件的状态。更具体一点说，在什么位置，以什么姿态。

> 从一开始我们就已经定义好了公共供应堆，这部分放宝石，那部分放牌堆。然后在 set 的时候，
> 这些宝石就从镜头外飞到了供应堆中，拿取，则是从供应堆移动至玩家保留区，这些都是最简单
> 不过的移动函数，如果设计得好，应该只需要填一个 source 和 destination 就够了。

由此推出：

1. **组件状态 = (zone, 顺位) + 姿态。** 世界坐标由 zone 的布局规则**推导**，
   动画数据里**不写坐标**。
2. **所有动画都是 zone → zone 的移动。** 设置阶段「从盒子里拿出来放进供应堆」和游戏阶段
   「从供应堆拿到持有区」是同一个操作，只是源 zone 不同（`offstage` 就是画面外的源 zone）。
3. **搬走要收拢。** 同一 zone 里排在后面的组件顺位前移，视觉上堆真的少一枚，而不是留空位。
4. **zone 是持久的逻辑容器。** 「公共供应堆」这类事实在设置阶段就确立，之后只是从中搬运。

## 运行时要维护状态（修正 2026-09-13 的「不跟踪历史」）

| 场景 | 做法 |
|---|---|
| 顺序播放 | 一条 cue 接着上一条 cue 的**终态**继续 |
| 重播当前 cue | 恢复到这条 cue 的**入口快照**（不重建对象） |
| 任意跳转 | 编译器离线复算每个 cue 的入口状态写进 runtime |

所以不是「运行端不跟踪历史」，而是**运行时维护连续状态 + 编译器负责跳转所需的入口状态**。
参见 [[tutorial-production-pipeline]]。

## 动画 = 时间的函数（2026-09 重构）

**核心决定**：动画不靠「每帧推进一点」累积，而是 `Seek(t)` 直接采样算出画面。

理由不是优雅，是**可验证性**：批处理环境（`-executeMethod`）没有帧循环，
`Time.deltaTime` 恒为 0、`StartCoroutine` 的协程不会推进、`Time.captureDeltaTime`
也无效。因此只要动画依赖帧推进，就**无法离屏验证**，只能靠人肉截图——
这个盲区导致连续多轮「我这边通过、用户那边不对」。

重构后：
- 事件触发时，**逻辑状态立即到终态**（Store 是时间的阶跃函数）
- 视觉过渡登记为 `Clip`，由 `SampleClips(t)` 采样：位置/翻转/缩放/透明/洗混全部如此
- 暂停、跳转、倒放天然正确，不需要特判
- `CaptureTimeline` 可按任意步长逐帧出图，离屏就能看到完整动画

### 自检入口
```
Unity.exe -batchmode -projectPath <client> \
  -executeMethod BoardGameTutorial.Editor.TutorialFrameCapture.CaptureTimeline \
  -captureCue setup.cards.002.1 -captureFrom 4.0 -captureTo 7.6 -captureStep 0.2 \
  -logFile <log>
```
输出到 `client/CaptureOut/timeline/t<毫秒>.png`。

## 反复踩过的坑（都属「静默失败」）

| 现象 | 真因 |
|---|---|
| 字段永远读不到 | `JsonUtility` 不支持 `int?`/`float?`，静默留 null |
| move 从不执行 | `from` 写成字符串，而模型是 `List<string>`，静默丢弃 |
| 牌堆里出现宝石 | `from`+`take` 按位置取件，盒子里宝石排在卡片前面；需用 `template` 筛选 |
| 牌停在原地 | 补间终点取了「当前 zone」位置，而牌的归属还在盒子 |
| 牌被后续事件拉回起点 | 只动画面、不记录格位；逻辑归属必须同步落到目标格 |
| 牌堆看似正面朝上 | 停在牌堆上的市场牌未标记 `Flipped`，正面盖住了卡背 |
| **本地编译检查报 OK，Unity 报编译错误** | 检查器**没定义 `UNITY_EDITOR`**，而 `Assets/Editor/*.cs` 整段包在 `#if UNITY_EDITOR` 里 → 编译成空文件，里面什么错都查不出来（2026-09-18：`Items.Count`（LINQ 方法组）漏到 Unity 才发现）。已在 `check_unity_scripts.py` 的 csproj 里加 `DefineConstants`，并收录 `Assets/Editor/` 全量 |

**规律**：这些都不报错，只表现为「画面不对」。所以每遇到一种，
都要**把它变成观察工具能报出来的事实** —— 能静态查的进 `validate_cue_anim.py`，
只能运行期知道的进 `DumpState` 的导出字段（例如 `Showing` 就是为"牌到底显示哪一面"加的），
**不要再写 `SelfTest*` 自检**（已全部删除，见文末）。

## 入口状态是一棵树（2026-09）

**核心规则**：每条 cue 的入口状态由它自己声明的 `entry` 决定。

```
entry 未写      → 继承「上一条有动画数据的 cue」的终态（顺序播放的默认）
entry = "initial" → 牌桌初始状态
entry = "<cue id>" → 那条 cue 的终态
```

### 为什么需要它

对照教学的两条 cue 必须是**兄弟**，不是父子。例如：

```
        玩家区（0 张）
        ├── cue A「可以抽一张」：1 张 → 保留区 + 对勾
        └── cue B「不可以抽两张」：2 张 → 保留区 + 叉
```

如果 B 以 A 为父，演示 B 时手里已经有 A 留下的 1 张，画面就错了。
两条都声明 `entry: "initial"`（或同一个共同祖先），各自从同一张桌子出发。

### 实现

- `TutorialCuePlayer.ResolveEntryCueId(index)`：解出入口来自哪条 cue。
  没有显式声明时，**跳过没有动画数据的 cue**（它们不改牌局）继续往上找。
- `TutorialCuePlayer.ApplyEntryState(anim, entryCueId)`：
  用**独立**的草稿播放器，从 `stage.initial` 起沿祖先链把每条推到终态，
  再把结果整体交给正式播放器。
- 顺序播放下一条时走快捷路径（直接用当前画面），不重新解。

### 踩过的坑

| 现象 | 原因 |
|---|---|
| 牌堆消失、发牌方向反了 | 独立重建实例**没把组件交接过来**（只复制了 zone/order） |
| 牌背叠在牌堆上 | 重放时 `start.set` 又生成一份；且隐藏逻辑漏了「无片段」的分支 |
| 片段累积到 90+ | `clips` 只在回退时清空，换 cue 从不清理 |
| 市场牌与牌堆数量核对错乱 | `CountIn` 只判 palette，而市场牌与牌堆共用 `card_level_1` |

**共同规律**：这些全都只在「连续播多条 / 跳转」时才出现，单条 cue 的隔离测试永远看不到。
所以自检必须走真实路径（`SelfTestEntryTree` / `SelfTestLivePath` / `CaptureSequence`）。

## 洗混是通用方法（2026-09）

任何 zone 都能洗，只要在 cue 里写一条事件：

```json
{ "at": 0.5, "dur": 0.7, "action": "shuffle", "zone": "deck_level_1" }
{ "at": 0.5, "dur": 0.7, "action": "shuffle", "zone": "gem_supply_diamond", "amount": 0.6 }
```

`amount` 是强度倍率（省略或 0 = 1.0），用于小棋子或大牌堆的差别。

### 实现要点（都在一处，改这里就够）

`TutorialCueAnimPlayer.Shuffle` 内部类集中了全部参数：

| 参数 | 值 | 说明 |
|---|---|---|
| `AmpMin/AmpMax` | 4.0 / 6.2 mm | 水平幅度区间 |
| `FreqMin/FreqMax` | 8 / 14 Hz | 抖动频率区间（接近人手搓牌） |
| `DepthMin/DepthMax` | 0.25 / 0.60 | 纵向幅度占水平的比例 |
| `EnvelopePower` | 0.45 | 包络形状（前 1/4 起振、中段保持、末 1/4 收住） |

**每张牌的四个量都由组件 id 散列决定**（`StableHash` + `Hash01`，不用 `Random`）：
幅度、频率、初相、纵向分量。所以同一瞬间有的向左有的向右、抖得也不一样快。
若所有牌同相摆动，看起来只是整摞在平移，不像洗牌。

### 断言

`SelfTestShuffleGeneric` 检查三件事：
1. 三个牌堆都被洗到（张数 40/30/20）
2. **同一 zone 内每张位移互不相同** —— 实测 40 张里 39 种（98%）
3. 同一方法可用于非牌堆 zone（宝石供应堆）

第 2 条是核心：它把「各张独立抖动」这个手感变成了机器可查的性质。

## 选择器规则：单件 vs 整组（2026-09）

**模型始终是平的：一张牌就是一个 item。** 牌堆不是"一个对象"，
只是 Store 里 40 个 item 恰好都归属 `deck_level_1`。
「整体」只存在于**操作层面**：操作可以作用于单个 item，也可以作用于一组。

事件用选择器指定作用范围，**全操作统一**：

| 写法 | 含义 |
|---|---|
| `target: "card_back_1#5"` | 单件 |
| `zone: "deck_level_1"` | 整组（该 zone 内全部） |
| 两个都写 | **数据错误**：报警告，以 `target` 为准 |

### 为什么这样分

- **发牌**要精确到单张 → 用 `target`（或 `move` 的 `from`+`slot`）
- **洗混 / 高亮一整摞** → 用 `zone`，一次说清"这一组"
- 两者不需要两套模型；同一份扁平数据既能单张操作，也能整组操作

### 整组操作怎么算

以**组内重心**为锚点，而不是某张牌的位置：

```
每张牌的位置 = 重心 + (原位 - 重心) × g
每张牌的缩放 = 基准缩放 × g
```

这与"把整组当作一个对象缩放"等价，且不要求组是规则形状 ——
牌堆（斜向错开）、宝石堆、玩家持有区都能用。

### 踩过的坑

| 现象 | 原因 |
|---|---|
| 高亮只让堆底那一张大了一圈 | 事件写了单张 `target`，走了单件脉冲 |
| 一级修好了，二三级没有 | 另外两条 cue 还是单张写法（断言也只验了一级） |
| 同一个事件在两类操作里选中不同东西 | `Resolve` 是 zone 优先，`highlight` 是 target 优先 |

## 容器：任意一组的命名集合（2026-09）

选择器现在有三档粒度，**同一套机制**，不是三套：

| 选择器 | 含义 | 典型用途 |
|---|---|---|
| `target` | 一件 | 发牌、翻某一张牌 |
| `container` | **任意一组**（点名的一组，不要求同 zone） | 卡 + 压在上面的宝石；跨区的一组 |
| `zone` | 该区域全部 | 洗混一整摞、高亮整摞 |

同时写多个 → 报警告，按 **target > container > zone** 取优先级最高的。

### 容器怎么定义（在 stage 里）

```json
"containers": [
  { "id": "level1_deck_and_top",
    "items": ["card_back_1#36", "market_card_1_emerald#1"],
    "has_center": false }
]
```

`items` 是组件 id 列表，**可以任意组合**（跨 zone 也行）。
`has_center=true` 时用 `x/z` 作为整组锚点，否则用组内重心。

### 为什么不用父子节点（Node 层级）

经典做法是给每组建一个父对象、操作父 transform。这里**没有采用**：

- 组内每件仍是**独立组件**，所以既能整组操作、也能单独操作其中一件；
  父子节点会让单张牌的位置变成「父变换 + 本地偏移」，发牌要算两层
- 父子节点引入层级与生命周期问题（销毁/重建顺序），本文件里那些坑大多源于类似的隐式结构
- 组的成员是**数据**（id 列表），可以随时改，不依赖场景结构

代价是整组操作要遍历成员（几十个对象的循环，可忽略）。

### 整组变换的算法

以组锚点为心，**位置与缩放一起变**：

```
位置 = 锚点 + (原位 - 锚点) × g
缩放 = 基准缩放 × g
```

等价于「把这一组当一个对象缩放」，且不要求组是规则形状。
另有整组平移（组内位移相同、相对位置不变），用于「把这一组挪到别处」。

| card_back_1 | 36 | `box_level_1` |
| card_back_2 | 26 | `box_level_2` |
| card_back_3 | 16 | `box_level_3` |

每个牌堆一个盒子区（而不是共用一个 `offstage`），这样「搬进牌堆」可以用
zone 直接指定，不必列出 36 个 id。

### 新原语

**showbox** —— 显示/隐藏一张整幅图：
```json
{ "action": "showbox", "picture": "media/box.png", "on": 1 }
{ "action": "showbox", "on": 0 }
```
- 图片**正对相机**并居中（不是像卡牌那样平躺 —— 竖图平躺会被压扁并跑到画面底部）
- 挂在播放器自己下面，**不是** animRoot；换节重建画面时随 ClearActors 销毁，
  所以"隐藏"不需要在数据里额外写
- 第一节的牌桌本来就是空的，不需要隐藏牌桌

**move 的 group 模式** —— 一组建件**同时、同长**地各自飞向目标：
```json
{ "action": "move", "group": true, "from": ["box_level_1"], "zone": "deck_level_1" }
```
- 逐件错开会把一整摞牌拉成扇形；同步移动才保持"这一摞"的整体感
- `group: true` 时 `take` 缺省 = **该 zone 全部**（曾缺省为 1，一摞只飞出一张）

### 踩过的坑

| 现象 | 原因 |
|---|---|
| 盒面后画面全空 | 曾用 `animRoot.SetActive(false)` 隐藏牌桌，盒面消失时忘了打开 |
| 一摞牌只飞出一张 | `group` 模式下 `take` 仍缺省为 1 |
| 高亮自检失败 | 牌堆已改为"第二节才上桌"，自检要先跑完 001.1 |

## 树的第一子节点 = 先介绍的那个东西（2026-09）

**原则**：树里谁排第一，取决于**讲解顺序**，不是"某类组件有特殊地位"。
先讲发展卡，三摞牌就是第一个子节点；若先讲宝石，宝石就是第一个子节点。

**推论（要守住的）**：搬运、分组、展示这些机制**不能对牌有特例**。
牌堆能整组从盒子搬到桌面，宝石堆、贵族、玩家持有区也必须能用**同一条代码路径**做到。

### 为守住这条原则做的两件事

1. **每类组件各自的盒子区**，理由相同：
   - 牌堆本来自带模板（card_back_1/2/3），但**宝石共用一个 `gem` 模板**（靠 palette 区分），
     不分成 `box_gem_diamond` 等就没法用 zone 指定"搬这一堆"。
   - 所以现在：`box_level_1/2/3`、`box_gem_diamond/.../box_gem_gold`。

2. **`SelfTestGroupMoveGeneric`** 用同一条 `move + group:true` 分别搬宝石和牌堆，
   证明机制没有对牌特殊化：
   ```
   PASS 同一套整组搬运可用于宝石：box_gem_diamond 7 → 供应堆 7
   PASS 牌堆用同一机制搬进桌面：deck_level_1=36
   ```

### 为什么值得写这些坑

这套动画系统的复杂度都花在"状态、分组、搬运"上。如果某一类组件走了特例分支，
以后换成"先讲宝石"就要再写一份。原则是：**换讲解顺序不该改机制**。

## 入口状态总是从根解（2026-09）

**规则**：播放任意 cue 前，画面都从**树根**解出来（根画面 → 沿 entry 链重放到目标前一条），
**没有「顺序播放就沿用当前画面」的快捷路径**。

那条捷径看起来只是省一次重放，但它让两条路得到不同画面：

| 操作 | 结果 |
|---|---|
| 按右跳到下一条 | 从根解 → 盒面消失 |
| 顺序播到同一条 | 沿用当前画面 → 盒面还在 |

用户就是这么发现的（"按右盒面消失、往回两次又出现"）。**同一个位置，两条路必须一致。**

代价是每次换 cue 多一次重放（毫秒级），换来的是可预测性。

### 根画面

`stage.board.default_picture`（例如 `media/box.png`）是树根的默认画面。
它必须在**入口状态应用完成后**才应用 —— `AdoptStateFrom` 会 ClearActors 重建画面，
在它之前显示盒面会被这次重建销毁（我踩过一次）。

### 断言

`SelfTestJumpMatchesSequential`：对前若干条 cue，分别用「直接跳转」和「从根顺序播到它」
求入口状态，要求盒面可见性一致：

```
bg.intro.*          跳转=True  顺序=True    ← 第一节显示盒面
setup.cards.001.1   跳转=True  顺序=True    ← 盒面还在，牌堆从中飞出
setup.cards.001.2   跳转=False 顺序=False   ← 盒面已收
```

### 顺带

`Sprite.Create` **不给 sprite 命名**，所以「当前显示的是哪张图」必须自己记
（`currentPicture`），不能靠 `sprite.name` —— 我曾经因此让盒面在交接时被当成"无图"。

## 【待办】编译器 + 入口状态快照（用户已确认要做，暂缓）

### 现在是怎么解入口状态的（运行期）

跳到第 N 条 cue 时：

1. `ResolveEntryCueId(N)` 沿 `entry` 声明解出祖先链（不写 `entry` = 继承上一条有动画的 cue）
2. `ApplyEntryState` 用一张**草稿播放器**从 `stage.initial` 起，沿链把每条 cue 用
   `Seek(时长)` 推到终态（**只改数据、不建画面**）
3. `AdoptStateFrom` 把结果整体交给正式播放器，再从 0 播第 N 条

这是**正确**的，也是毫秒级；但 cue 数到几百条、或依赖链很深时会变成不必要的开销。
用户问过"是不是把前面 34 条都过一遍"——按链走，不是 34 条，但确实是"过一遍"。

### 要做的优化：离线编译 + 快照

```
编译器（离线，一次）：
  对每个 cue，按它的 entry 链算出**入口状态**，写进 runtime
运行期（跳转）：
  读快照 → 直接用，零重放
```

快照要包含（即当前"入口状态"的全部内容）：

- 每个 item 的 `ZoneId` / `Order` / `Flipped`
- 三摞牌堆等 stack zone 的**实际张数**（厚度由它算）
- 当前根画面（`stage.board.default_picture` 或 cue 覆盖后的图片路径）
- 需要的话还有 `EntryAnchor` / `EntryFrom`（影响后续"从盒子飞出"的起点）

### 为什么顺带解决了视频导出

**两者需要的是同一个东西：每条 cue 的起始快照。**

- 有快照 → 每条 cue 可以**独立起播**（任意切换、任意跳转都是常数时间）
- 有快照 → 每条 cue 可以**独立离线渲染成视频**（起始画面已知，不需要重放）
- 分支（"可以抽一张 / 不可以抽两张"是兄弟）在编译期就固化成数据，
  运行期/渲染器都不需要理解树的结构

### 实现提示

- 编译器的算逻辑就是现在 `ApplyEntryState` 的离线版本，**接口不用改**
- 入口状态的语义必须保持"从根解"，不能退回"沿用当前画面"
  （那条捷径导致过"跳转与顺序播放画面不一致"）
- 现在的运行期机制**作为对照实现保留**，方便编译结果与它逐条比对

## 特写取景（camera 字段，2026-09）

事件可以带 `camera` 指定取景：

```json
{ "action": "wait", "camera": "showcase", "camera_padding": 1.6 }
{ "action": "wait", "camera": "board" }
```

- 写 zone id → 把镜头对准该 zone 的格位包围盒（特写）
- 写 `"board"` 或留空 → 回到整桌取景
- `camera_padding`：留白倍率，**越大视野越宽、物体越小**。
  在「这是发展卡牌」的特写里实测：1.4→48%、1.6→49%、1.8→47%、2.0→43%，
  所以取 **1.6**。注意它不是线性的（格位包围盒与 card 自身世界尺寸并不相等），
  **调这个值要用实测扫描，不要只靠推算**。

特写开关在 `Trigger` 里统一处理（所有动作路径都生效）。

### 为什么需要它

整桌取景下（ortho ≈ 2.79）一张 63×88mm 的卡只占画面约 24%，讲"这是发展卡牌"时太小。
特写把 ortho 降到 ~1.0，卡占到约 49%。

## 用名称和位置区分，不要靠颜色（2026-09 用户裁决）

讲解"三种卡背"时，**靠名称 + 位置区分**：

```
sample_back_1 = 一级 → showcase_1（最左）
sample_back_2 = 二级 → showcase_2（中）
sample_back_3 = 三级 → showcase_3（最右）
```

**位置即身份**：同一张卡每次出现在同一位置，观众靠位置认级别。
校验器强制这条：`sample_back_N` 若被放到别的 `showcase_M` 会直接报错。

### 为什么不用染色

我一度给三张卡背加 `tint` 来"一眼可分"，用户反馈"像加了一层滤镜，颜色不对劲"——是对的：
染色等于给画面糊一层色，把卡背画作弄脏了。

而且**根本没这个必要**：三张卡背扫描图本身的平均色差异就很大——

| 卡背 | 平均色 | 主色 |
|---|---|---|
| 一级 | (0.35,0.45,0.26) | 绿 |
| 二级 | (0.52,0.41,0.24) | 黄 |
| 三级 | (0.35,0.40,0.50) | 蓝 |

（渲染时它们看起来都偏蓝，是缩放后的视觉印象；原图差异是明确的。）
`tint` 机制已整体撤除，避免有人再误用。

### 排查时踩的坑

我在"为什么渲染出来都偏蓝"上耗了大量轮次，反复用像素采样验证，结论反复自相矛盾
（导出贴图是绿/黄/蓝，渲染像素却是同一组蓝）。**用户是对的：应该停止纠结工具，改用
名称+位置这种不依赖视觉判断的方案。** 教训：当验证手段本身变得不可信时，
先换一个不依赖它的方案，而不是继续加探针。

## 两个"状态漏复制"的坑（2026-09，用户报的乱码与牌消失）

### ① 洗混时的 NaN —— `Mathf.Pow(负数, 小数)`

`sin(kπ)` 在 k=1 处会因**浮点误差**得到极小负数（~-1e-8），而
`Mathf.Pow(负数, 0.45)` 在数学上无定义 → **NaN**。

NaN 一旦写进 `Transform.localPosition`，Unity 每帧报同一个错，
并且这一摞牌**不再被渲染**（看起来像"消失"，后续 cue 也修不回来）。

修法：底数先夹到非负 `Mathf.Max(0f, Mathf.Sin(...))`。
**教训**：任何 `Mathf.Pow` 的底数都要先确认非负。

### ② 发完牌后消失 —— `hide_until_animated` 是**模板级静态**标记

它只能表达"这一**类**组件还没出场"。但可见性判断每帧都在跑，
一旦场景重建（换 cue 时 `ApplyEntryState` 会重建画面），
**已经发出去的牌又被当成"没出场"而归零透明** —— 用户看到"12 张牌全消失"。

修法：加**每件**的 `ZoneItem.Shown`，出场（move/fade）时置 true；
判断改为 `hide_until_animated && !Shown`。

### ③ 反复出现的同类错误：新增字段漏进复制清单

这已经是**第三次**了（`hide_until_animated`、`from_zone`、`tint`，现在是 `Shown`）。
有两处复制清单，**新增字段必须两处都加**：

| 位置 | 作用 |
|---|---|
| `EffectiveTemplate` | 实例色板与模板不同时克隆模板 |
| `AdoptItemsFrom` | 入口状态交接时复制每件 |

漏掉的后果各不相同（有的表现为牌不可见，有的表现为染色丢失），都不好查。
**新增字段时先搜这两个地方。**

## hide_until_animated 已删除（2026-09）

### 它原本是干什么的

模板级布尔：让这一**类**组件"在被动画带出来之前完全不可见"。
唯一用途是那 12 张待发市场牌——它们由 cue 12 的 `start.set` **预先摆在各自牌堆位置**，
不隐藏就会在洗混前叠在牌堆上，看起来像牌堆厚了好几层。

### 为什么删掉

它是**旧模型（对象必须预先存在）的遗留**。现在有了 `create`：

```json
{ "action": "create", "template": "market_card_1_emerald", "palette": "card_level_1",
  "zone": "card_market", "count": 1, "slot": 0, "flip": true }
```

发牌时**直接创建到市场格位**，待发的牌根本不存在 → 不需要"藏起来"。
`start.set` 也不再预置市场牌。

**它还是上一个 bug 的根源**：可见性每帧都要判断，而它是**模板级静态**标记，
场景一重建（换 cue 会重建）就把已发出的牌重新隐藏（用户报的"发完12张牌后消失"）。

### create 补齐的两个能力（顺带）

| 字段 | 作用 |
|---|---|
| `slot` | 创建到指定格位。缺了它只会追加到末尾，发牌摆不成 4 列网格 |
| `flip` | 出场时翻到正面。与 move 的翻转共用 `FlipFromYaw`，但**新建组件从 0° 起翻、走满一圈回到 0°**；若沿用 move 的 `(from, from+180)` 会停在 180°，把正面贴图镜像掉，终态看起来仍是背面 |

### 现在的可见性模型

1. **还没出场** → 对象**不存在**（`create` 之前没有它）
2. **已出场** → 正常渲染
3. `ZoneItem.Shown` 只用于"预先存在、之后被动画带出来"的少数情况

不再有"建出来但藏起来"这个中间态。

## 牌堆是真牌，发牌是真搬运（2026-09 用户裁决）

**用户的原话**：「那 40 张的牌堆是应该真的由 40 张牌组成的，发牌，就是把最上面那张真的翻过来，
移动到右边，这样才对。而不是靠什么在展示前隐藏起来的这种方式。」

### 正确的模型

```json
// 牌堆：真的是 40 张牌（只是背面朝上；牌堆里的牌在发出去之前不知道是哪张）
{ "action": "create", "template": "card_back_1", "plain": true,
  "zone": "deck_level_1", "count": 40 }

// 洗混：把这 40 张真的搓一遍
{ "action": "shuffle", "zone": "deck_level_1" }

// 发牌：搬走最上面那张、边飞边翻面，翻过 90° 时换面成它真正的那张牌
{ "action": "move", "from": ["deck_level_1"], "take": 1,
  "template": "card_back_1", "zone": "card_market", "slot": 0, "flip": true,
  "to_template": "market_card_1_emerald", "to_palette": "card_level_1" }
```

发牌后牌堆**真的**从 40 减到 36（`SelfTestDealSync` 逐条断言 40/30/20 → 36/26/16）。

### 为此新增的两个原语

| 原语/字段 | 作用 |
|---|---|
| `create` 的 `plain` | 不指定色板。一摞牌在发出去之前**不知道是哪张牌**，整摞同色板即可 |
| `move` 的 `to_template` | **翻过 90° 时换面**："翻开才知道它是哪张"。这是 `swap` 的自动版 |

`swap` 原语也保留了（手动换面），但目前发牌用 `move` 自带的换面。

### 踩过的坑

| 现象 | 原因 |
|---|---|
| 发到市场的牌一直是卡背 | 翻转条件写的是 `ev.flip && actor.BackSprite != null`，而**牌堆的牌没有 back_image**（它的正面就是卡背图），整条翻转+换面都没发生 |
| 牌堆张数翻倍（40→80） | `create` 被触发两次（先解入口状态再载入）。现在 `create` **幂等**：只补齐差额 |

### 仍未做（用户明确暂缓）

**"真正定义 40 张牌分别是什么、按固定顺序排列"** —— 用户说：
「要想真的定义40张牌，就要知道这40张牌分别是什么，再把它们按固定顺序排列起来，
这在当前场景下没有必要。但不代表这个需求本身没用，以后早晚会用得上，那时用上再说」

将来要做时的入口：`create` 已支持逐张指定（`template` + `palette` + `slot`），
牌堆可以用 40 条 `create` 逐张摆出确定的牌序；那时 `shuffle` 与"抽最上面一张"
需要按真实牌序语义处理（现在的 shuffle 只是视觉抖动，不改顺序）。

## 12 张真牌 + 空白牌凑数（2026-09 用户方案，已实施）

**用户的原话**：「其实我们根本不需要真的定义40张牌，只需要定义12张左右的牌，
就能让牌堆看上去像是有好几十张牌一样。前4张是正常的牌，后面都用空白卡面……
正所谓欺骗的艺术，但这样做的好处在于**翻开一张牌是个天然的行为**。」

### 实现

```json
// ① 先建真牌 —— 占据牌堆顶（order 0..3），所以会先被发出去
{ "action": "create", "template": "market_card_1_emerald",
  "palette": "card_level_1", "zone": "deck_level_1", "count": 1 }
// ② 再补空白牌凑够张数 —— 它们永远发不出来
{ "action": "create", "template": "blank_card_1",
  "palette": "card_level_1", "zone": "deck_level_1", "count": 36 }
// ③ 发牌：搬走最上面那张并翻开
{ "action": "move", "from": ["deck_level_1"], "take": 1,
  "template": "market_card_1_emerald", "zone": "card_market", "slot": 0, "flip": true }
```

**关键**：`PickFront` 取 **`Order` 最小**的那件 = 牌堆顶。所以**真牌必须先创建**
（占 order 0..11），空白牌排在其后。

### 为什么这个方案好（用户说的"天然"）

- 真牌**一开始就是它自己**（真卡面 + 卡背都在）→ **不需要换面**
- 于是 `swap` / `move.to_template` / `SwapTo*` **整套都删掉了**
- 发牌就是"搬走最上面那张并翻开"—— 一个动作，没有任何生成代码
- 空白牌只是让牌堆看上去有几十张，它们永远不会被发到市场

### 踩到的坑

牌堆里混着**多种模板**（真牌 + 空白牌），所以发牌的 `move` **必须写 `template`**
指定取哪张牌 —— 否则 `PickFront` 可能把空白牌发到市场上（校验器会警告这一条）。

## 【已解决】40 张牌到底是哪些牌

### 问题

要做到"40 张真牌里真的发出 4 张"，就必须知道**这 40 张分别是什么牌**。
一局璀璨宝石的一级牌堆有 40 张、二级 30 张、三级 20 张，共 90 张不同的牌，
每一张有各自的费用与分数。**素材里只有 5 张卡面扫描图**，我们并不知道完整牌表。

这也正是现在这个矛盾的根本原因：

- 牌堆里的牌在发出去之前**不知道是哪张** → 所以整摞只能同色板
- 发到市场时才用 `to_template` 换面 → 但**只有 5 张卡面可选**，

## 翻面 = 换面，不旋转（2026-09 已修）

**根因**：`card_back_*` 模板原本只有一张贴图（它的"正面"就是卡背扫描图），
于是"翻转"只能靠**旋转同一张贴图** —— 旋转 180° 必然产生**镜像**（用户看到的"镜像卡背"）；
再加上"转到一半换贴图"，前半程显示的又是卡面。换一条 cue 时场景重建、旋转复位，
镜像就"突然恢复正常"（不是修好，是被重置掩盖）。

**修法**：

1. **牌堆里的牌只有卡背**（`card_back_N` 的 `face_image` = 该级卡背，`back_image` 为空）——
   牌还没翻开，无所谓是哪张牌
2. 发出去时 `move` 的 `to_template` **换成市场卡模板**，那一面就是真卡面
3. 翻转采样**按"朝上/朝下"决定显示哪一面**，`localRotation` 恒为 `identity`：

   ```csharp
   bool faceUp = clip.Item == null || clip.Item.Flipped;
   var backSide = clip.Actor.BackSprite != null ? clip.Actor.BackSprite : clip.Actor.FaceSprite;
   clip.Actor.Renderer.sprite = faceUp ? clip.Actor.FaceSprite : backSide;
   ```

4. `SelfTestDealSync` 加了断言：市场牌与牌堆牌**都不许被旋转**（旋转 = 镜像）

**教训**：一张牌的两面应当由**两个贴图**直接切换。用旋转去表达"翻面"是错的 ——
它翻的是**同一张图**，必然镜像。旋转只有在**两面都在**（真正的双面渲染）时才有意义。

## 【已解决】翻转的实现方式（2026-09 用户实机截图）

### 用户看到的现象

- **cue 12 中途**：发出去的是**卡面朝上**的牌，而牌堆还是卡背；有一张显示的是
  **左右镜像的卡背**（"Splendor" 反写），像是翻到一半
- **cue 13 一开始**：那些镜像的卡背**突然恢复正常**

用户的判断（正确）：**如果牌堆真是 40 张牌、发牌就是把最上面那张自然地翻过来，
就不可能出现这两种现象。** 出现它们说明实现里有一堆补偿动作。

### 真实原因（我查出来的）

牌堆用的 `card_back_*` 模板**只有一个贴图**（它的"正面"就是卡背扫描图，没有独立的背面）。
于是我的"翻转"实际做了三件互相打架的事：

1. 把**同一张卡背图**绕 Y 轴转 180° → 必然看起来是**镜像的卡背**
2. 转到一半（超过 90°）时**换贴图**成市场卡面 → 于是**前半程显示的是卡面**
3. 换一条 cue 时场景重建、旋转复位到 0° → 镜像"突然恢复正常"（不是修好，是被重置掩盖）

### 根因与本该有的做法

**一张牌的两面应该由两个贴图直接切换表达**，而不是"一张图 + 旋转 + 中途换图"。

- 牌堆里的每张牌：一面是卡背、另一面是它的真卡面
- "翻转" = **显示另一面**；不需要旋转，也不该产生镜像
- 旋转只在需要"看到翻的动作"时才有意义，且那应是**真正的双面 3D 翻转**（两面都在）

所以明天讨论的不是调 flip 的参数，而是**重新定义牌的两面怎么表达**。
现在的 `flip` / `swap` / `to_template` 三个机制是在模拟一件本该自然的事，
这也是这套实现"一团乱麻"的来源。

### 这也和"40 张牌是什么"是同一个问题

不知道牌堆里每张是什么牌 → 就无法给每张牌准备"它的真卡面" →
只能整摞共用一张卡背图 + 发出去时临时换图 → 于是需要各种 trick。
**把"每张牌是什么"定下来，翻转自然就简单了。** 两件事应当一起解决。

## 分支：共享父状态 + 牌堆顶不同（2026-09 已验证支持）

**用户提出的场景**：「如果抽到了红色牌，可以加入手牌；抽到蓝色牌则必须塞回牌堆底」。
这是一个**两条兄弟 cue 共享同一个父 cue**、但**牌堆顶那张牌不同**的场景。

### 结论：支持，而且不需要新机制

每条 cue 的入口状态都是**独立**按 `entry` 链从根解出来的，所以：

1. **共享父状态**：两条兄弟声明同一个 `entry`（那个父 cue），各自重放都会得到**相同**的牌堆
2. **让顶牌不同**：在各自的开头用 `move` + `slot` 把不同的牌**换到牌堆顶**（order 0）
3. **抽牌**：`PickFront` 取 `Order` 最小那件 = 牌堆顶 → 抽到的就是各自摆上去的那张

实测（`SelfTestBranchDifferentTopCard`）：

```
PASS 分支A（抽红）抽到 market_card_1_ruby
PASS 分支B（抽蓝）抽到 market_card_1_sapphire
PASS 两条兄弟分支抽到不同的牌 —— 共享父状态、但牌堆顶不同
```

### 关键机制：zone 内换位是支持的

`ZoneStore.MoveToAt` **支持同 zone 换位**：先把该件从原格位释放，再抢占目标格位；
若目标格位已被别人占，**占用者被挪到下一个空位**（它的格号变了，但它本来就是"没被指定过"的）。

注意 `MoveTo`（不指定格位的那条路）对同 zone 会**直接返回** —— 换位必须用
`MoveToSlot` / `MoveToAt`（即事件里写 `slot`）。

### 这套模型为什么能成立

因为**牌是个体、格位是地址、抽牌取 order 最小**：
"牌堆顶是哪张"就等价于"谁的 order 最小"，而 order 可以被事件改。
所以"让不同分支抽到不同的牌"不需要任何新原语，只需要改顺序。

### 测试依赖

`SelfTestBranchDifferentTopCard` 依赖三条临时 cue
（`branch.shared.001` / `branch.red.001` / `branch.blue.001`），
它们**不在正式 runtime 里**。跑这条测试前需要先把它们注册进 `full.runtime.json`。
若要长期保留这条测试，应改成"自建场景"（不依赖外部 cue 文件）。

## 状态契约与对账工具（2026-09，用户提议）

而"谁在哪个 zone、几件、朝上还是朝下"是**数据**，可以用程序精确比对。

两条链路互不写对方。）

### 契约结构

```jsonc

  "kind": "animation_contract",
```

### 关键设计决定

1. **契约里只放语义状态**，不放坐标/缩放 —— 那些是从 zone+格位推出来的表现层，
   写进去只会因为改布局而误报
2. **`kinds` 用语义名**（`一级绿`、`宝石红`），工具负责翻译成引擎的

3. **契约只声明它关心的 zone**。没提到的 zone（宝石盒、贵族）不算差异 ——

   "无关区域有没有被动过"是**不变量**的职责
4. **`entry` 应当由工具采样父 cue 的出口自动填**，不要手写 ——
   手写的只是"我以为的父状态"，父 cue 错了它会跟着错，跨 cue 对账就失效

## 为什么对账没抓到「朝向」两个问题（2026-09 用户验收）

## 牌堆外形与翻转（2026-09 用户定义）

### 牌堆错开模型（最终，2026-09，用户三次纠正后）

**底部 8 张各自错开，第 8 张往上的全部重合**（按 `order` 算，order 0 = 最下面）：

```csharp
float lift = Mathf.Min(slot, maxVisible - 1);
x += lift * display.dx;   z += lift * display.dz;
```

**判据（这才是"发牌看不出变少"的真正条件）**：
> **发牌后，没被取走的那些牌坐标完全不变。**

实测：`发牌后未被取走的牌坐标完全不变（变化的 0 张）`。

我前后错了三次，每次都把"错开"锚在错误的一端：

| 写法 | 后果 |
|---|---|
| `visible = Clamp(total,1,max)`，按可见层数错开 | 发一张少一层 → 越发越薄 |
| `lift = min(capacity-1-order, max-1)`（从顶部锚定） | 顶部 8 张重合、下面错开 → 一摞看不出台阶 |
| `lift = min(total-1-order, max-1)` | 张数一变整体平移 |
| **`lift = min(order, max-1)`** | ✅ 底部错开、其上重合，取走重合块里的牌外形不变 |

**教训**：我两次用自己的假设写断言（"顶部错开"、"跨度不变"），
于是断言"通过"但没实现用户要的效果。**断言必须对着用户描述的模型写，不能对着我的实现写。**

### 翻面：压扁-展开，不用旋转（2026-09 用户要求）

用户报"翻出来的正面卡牌都是镜像的，左右反了"。

**根因**：把一张平面贴图绕 Y 轴转到 180°，屏幕上就是**左右镜像**。
真实卡牌翻过去不镜像，是因为实体牌的两面是两个不同的面；我们只有一张平面贴图。

**修法**：用 2D 里表达翻牌的标准手法——**压扁-展开**，全程不旋转：

```
0 → 0.5：横向收缩到 0（牌"立起来"侧对镜头），显示背面
0.5 → 1：横向展开回原宽，显示正面
squash = max(|1 - 2k|, 0.02)   // 不要压到 0
```

断言：市场牌**没有被旋转**（旋转即镜像）、缩放已恢复原值。

### 牌堆错开模型（早期记录，已废弃）

**要点：错开量必须用 `capacity` 算，不能用当前张数。**

```csharp
int maxVisible = display.max_visible > 0 ? display.max_visible : 8;
int deckCapacity = zone.capacity > 0 ? zone.capacity : Mathf.Max(1, CountInZone(zoneId));
int fromTop = Mathf.Max(0, deckCapacity - 1 - slot);
float lift = Mathf.Min(fromTop, maxVisible - 1);
x += lift * display.dx;   z += lift * display.dz;
```

"第几格错开多少"是**固定的**（只跟 capacity 有关），与还剩几张无关：

- 靠近顶的格（lift 小）永远重合在一起
- 越往下错开越多，到第 maxVisible 格封顶
- 更下面的格全部落在**同一个位置**（重合块）

于是从顶上发牌时，可见外形**完全不变** —— 被发走的那几张本来就在重合块里。

实测：40 张与 36 张的跨度都是 `0.1120`，错开层数都是 8，
**牌堆顶那 5 张的坐标完全一致**。

**踩过的坑（三次）**：三次都保留了同一个共同点 —— **错开层数随张数变化**。

| 写法 | 后果 |
|---|---|
| `visible = Clamp(total, 1, max)` 再按可见层数错开 | 发一张就少一层 → **越发越薄** |
| 按 `order` 从底部锚定（`layer = min(slot, max-1)`） | 同上：张数一变整体就平移 |
| 按 `fromTop = total-1-order`（用当前张数） | 仍薄：发出的牌不在重合块里，抽走就少一层 |
| **按 `deckCapacity-1-order`** | ✅ 固定外形，"发 7 张只剩一张"的问题消失 |

用户的原话最准确：「发出的那4张牌，其实是连带着另外一部分牌是重叠在一起的。
只有最底部那8张牌是错开的，这样发出4张牌，牌堆的样子也不会改变。现在这个牌堆的话，
如果发出7张牌，牌堆看上去就只会剩下一张，然后这一张特别耐发，这是不对的。」

### 一条容易说错的结论（用户纠正过）

我一度写成"**布局不该依赖还剩几张**"——**这是过度概括，是错的**。
"张数 → 形状"是完备函数，用张数算完全合法。

准确的表述是：

> **不是"依赖张数"错，而是"让错开层数依赖张数"错。**

两种模型都依赖张数，差别只在依赖哪一个量：

```
张数 → 形状（错开层数固定，只有高度/位置变）   ← 用户要的，看不出变少
张数 → 形状（错开层数也变）                     ← 之前的，变薄明显
```

**可推广的判断标准**：不是"用不用张数"，而是
**"发牌后可见外形会不会变"** —— 任何会随发牌而改变的量，都不该进入牌堆外形。

### 牌堆错开模型（用户原话）

> 假如这一堆有20张牌，那应该是最下面一张牌放在那里，然后倒数第二张牌错开一点，
> 盖在最下面那张牌上，倒数第三张牌再错开一点盖在倒数第二张上，以此类推，
> 然后倒数第8张牌一直到倒数第20张牌，**一点都不错开，重合在一起**，
> 这样才能起到一个发出一张牌，但牌堆看起来没变少的效果。

实现：错开量按 **order**（0=最下面）算，封顶在 `max_visible - 1`：

```csharp

z += layer * display.dz;
```

- 第 8 张往上的牌全部重合
- 底部 8 张逐层错开且间距恒定

### 翻转是 0°→180° 的连续过程（用户要求）

> 「翻开并移动」的这个动画看起来不够美观，翻转，或者翻开，应该是一个 0°到180°的过程，
> 而不是在移动过程中突然变成了另一面。

```csharp

```

### 【最终】牌堆外形：按"距顶容量"锚定（2026-09）

**真正有效的判据是"轮廓厚度"**，不是"某张牌自己的坐标"：

```
40张: 厚度=0.112  台阶数=8
38张: 厚度=0.112  台阶数=8   ← 发牌中
36张: 厚度=0.112  台阶数=8   ← 发牌后，完全不变
```

```csharp
int deckCapacity = zone.capacity > 0 ? zone.capacity : Mathf.Max(1, CountInZone(zoneId));
int fromTop = Mathf.Max(0, deckCapacity - 1 - slot);
float lift = Mathf.Min(fromTop, maxVisible - 1);
```

**为什么必须"距顶"而不是"距底"**：发牌取的是**离顶最近**的牌。
所以形状必须由离顶最近的那几张决定 —— 取走它们，外形才不变。
按 order 从底部锚定时，取走的正是形状最外层的牌，轮廓立刻缩短（实测 0.112→0.080→0.048）。

## 牌堆模型（用户定义，2026-09 定稿）

### 叠放与发牌顺序

用户对牌堆的完整描述：

> 先把一张牌放在桌上，它是 order 39，作为牌堆的最下面一张牌存在。
> 再把一张牌盖在 order 39 的左下一点点，作为 order 38，它是倒数第二张牌，

> 倒数第 8 张牌上，不再有任何偏移，一直到 order 0。

> 第一个被发走的肯定是 order 0。——**order 0 是牌堆顶，先被发走**。

所以：

| | |
|---|---|
| **牌堆顶（先被发）** | `order` **最小**（0） |
| **最下面（最后被发）** | `order` 最大（capacity-1） |

### 位置公式

```csharp

z += lift * display.dz;    // display.dz = -0.016（偏上）
```

`order 0..7` 逐层错开形成台阶，`order 8` 及以上全部重合在 order 7 上。

发牌从 `order 0` 开始，而 order 0..7 在**重合块**里 —— 发走它们不影响台阶。
要发到 order 8（第 9 张）才开始动到台阶。**不需要任何"保持形状"的代码。**

```

```


### 根因 2：位置计算里读 `CountInZone` 造成自引用

`ComputeZonePosition` 曾经调用 `CountInZone(zoneId)`，

**自引用**（严重时无限递归、Unity 静默崩溃，日志只打一半）。

**规则：位置计算只准读 `zone`（配置）与 `order`（参数），绝不读任何"当前有几张"的状态。**

### 最终公式（按容量锚定，不可改）

```csharp
int deckCapacity = zone.capacity > 0 ? zone.capacity : 8;
int fromBottom = Mathf.Max(0, deckCapacity - 1 - order);
float lift = Mathf.Min(fromBottom, maxVisible - 1);
```

**为什么必须锚容量、不能锚实际张数**：发牌从 `order 0` 开始，若锚实际张数，
牌一被发走"距底"就变小 → 台阶被吃掉（实测 40张8层 → 36张4层）。
锚容量则是固定映射 → 发走任意张，其余牌的台阶位置都不变。


## 【已修】高亮不能暂停，而洗混能（2026-09）

用户："cue11 播放高亮动画时按空格暂停，高亮动画不会停住；对比之下 cue12 的洗混动画能停住。"

**根因是两套机制**：

| 动作 | 机制 | 暂停表现 |
|---|---|---|
| `shuffle` / `flip` / `scale` / `fade` / `groupScale` | **时间采样片段**（`clip`，`Seek(t)` 的纯函数） | 暂停即停 ✅ |
| `highlight` 单件（`PulseActor`） | **协程** `RunTween(ScalePulseRoutine)`，靠 `Time.unscaledDeltaTime` 自己跑 | 暂停照样放完 ❌ |

**修法**：`PulseActor` 改走时间采样 —— 直接复用 `HasGroupScale`
（它本来就是"以某点为锚点整组缩放、去程+回程"），把锚点设为该牌自身位置，
等效于**原地呼吸**，不必再造第三种脉冲机制。

```csharp
var clip = ClipAt(actor.Item, actor, synthetic);
clip.HasGroupScale = true;
clip.GroupCenter = actor.LivePosition;   // 锚点 = 它自己 → 原地放大
clip.GroupGrow = grow;
```

**验证方法（可复用）**：暂停的语义就是"**不再调用 `Seek` 时状态不变**"。
`TraceHighlightScale` 采样后**不再 Seek** 再读一次，两次必须相同：

```
[Hl] t=1.10 采样后=0.0974 暂停后再读=0.0974 一致
```

**规则**：任何"随时间推进的视觉"都必须做成 `Seek(t)` 的纯函数（片段），
**不要用协程** —— 协程与时钟无关，于是暂停、跳转、倒放都会不一致。

### 脏动画的定义

> **某一帧上，"已经存在的状态"和"当前的取景/层次"不匹配。**

它必在两处发生：**跨 cue 边界**（取景是隐藏的延续状态）、
**同帧内多个事件**（顺序决定中间态）。

### 根子：我在写"步骤"，不是在写"每一帧长什么样"

步骤之间那段时间会发生什么，我没写，它就自己发生了。
**"同时发生" = 同一个 `at`**；只要把两件事放在同一个 `at`，中间态就消失了。

它当时报出两条**真实的隐藏依赖**，修法都是**显式声明**：

```json

```

**规则：凡是"改变画面内容"的动作，都必须与"改变取景"的动作同时或在其之后；
承接来的取景要显式写出来，不要靠推断。**
