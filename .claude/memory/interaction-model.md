# 交互模型与 Runtime 目标

## 核心决策

第一阶段 Runtime **不追踪游戏状态、不使用计算机视觉**。

- 程序掌握全部结构化规则（ontology / concepts / flow）
- LLM 只负责：理解语言、识别涉及的概念/行动/条件、组织语言
- 对依赖状态的问题，LLM 向客人反问所需状态，然后由程序做规则判定

## 问题归纳

绝大多数客人问题可归纳为：**解释某个概念/行动/触发器的条件与效果**。

典型处理路径：

1. 识别意图与涉及的概念
2. 查询对应 action / trigger / condition 的定义
3. 判断是否需要当前状态
   - 不需要：直接给规则性回答
   - 需要：向客人反问具体状态项
4. 若客人提供状态，程序做最终判定
5. LLM 用自然语言组织答案

## LLM 与程序分工

| 工作 | 负责方 |
|---|---|
| 理解客人自然语言 | LLM |
| 识别涉及概念/action/condition | LLM（在受限工具集内） |
| 查询结构化规则 | 程序接口 |
| 规则判定（yes/no） | 程序 |
| 把结构化结果讲成人话 | LLM |
| 从客人回答中提取结构化状态 | LLM |

## 当前阶段不做

- 摄像头 / 图像识别
- 实时游戏状态追踪
- 手牌 / 私有信息读取
- 主动推荐最优行动（避免扩大 LLM 推理空间）

## 当前阶段先做

- 自然语言 → 概念识别
- 规则查询接口（读取 ontology / concepts / flow）
- 状态需求反问
- 给定状态后的规则判定
- 单次回答内的多轮工具调用

## 和项目整体的关系

这一层位于 Rule DSL 之后、Tutorial Tree 之前，可视为 **Runtime / Intent Interface**。Splendor 作为首个游戏，用其 `concepts.json` / `flow.json` 验证这套模型。后续游戏复用同一 Runtime，只换 JSON 配置。

**Why:** 明确 LLM 与程序的边界，防止项目早期滑向「让 LLM 理解全部规则并追踪状态」的复杂路线。
**How to apply:** 任何设计讨论先问：这个事实程序能否从结构化规则中得出？如果能，就不交给 LLM 推理；如果不能，考虑是否应反问客人而非直接猜测。
