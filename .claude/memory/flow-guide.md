# 流程向导（Flow Guide）

## 状态

- 2026-09-22 用户定名并确认方向：**动画制作告一段落后，下一个项目做「流程向导」**。
- 本文记录产品定位与交互模型，不写实现排期。

## 一句话定义

不是「陪客人打一局游戏」，而是把规则流程变成一份可交互的检查清单 / 向导：

> **AI 掌握流程状态，玩家掌握棋盘事实。**

AI 不需要知道棋盘上实际有什么，只需要知道流程走到哪一步；条件真假由玩家回答或选择。

## 核心原理：状态分层

不需要统一的实时游戏状态，而是把「状态」拆开：

| 状态类型 | 谁负责 | 例子 |
|---|---|---|
| 流程状态 | 程序 | 第几个时代、第几个阶段、当前玩家、第几轮、当前 pipeline/guide 节点 |
| 条件状态 | 玩家回答 | 贵族是否到访、终局条件是否满足、行动前提是否满足 |
| 决策状态 | 玩家选择 | 激活模组 / Reset、选择哪个行动或选项 |
| 计分状态 | 玩家报数 + 程序计算 | 各计分类别每人数量、总分与平手判定 |
| 棋盘布局/资源状态 | 默认不获取 | 宝石实际数量、模组位置、牌堆顺序、隐藏信息 |

这个分层是流程向导能绕开实时状态的根本原因。

## 交互形态

程序维护流程游标，LLM 只负责把当前节点翻译成自然语言。典型对话：

> AI：现在是第 1 时代，阶段 1「新卡牌」。请翻开 1 张事件牌和 5 张研究牌。完成后告诉我「完成」或「跳过」。
>
> AI：现在进入阶段 4「行动阶段」。第一位玩家请选择：**激活模组**，还是 **Reset**？
>
> 客人：激活模组。
>
> AI：你激活哪个模组？迁移、生产、建造、研究……
>
> 客人：迁移。
>
> AI：迁移需要检查以下前提：……你是否满足？
> 选项：**是 / 否 / 不确定 / 跳过**。
>
> 客人：不确定。
>
> AI：那我们先解释这个条件怎么判断。……

关键：

- 条件判断用「是 / 否 / 不确定 / 跳过」委托给玩家；
- 「不确定」进入现有规则问答，解释完回到同一流程节点；
- 程序自己记 player_index、phase_index、era、loop 次数，不依赖棋盘。

## 为什么比「带玩一局 / 影子对局」更稳

- 不要求棋盘状态同步，不需要 CV，也不需要客人输入完整局面；
- 对复杂游戏价值最大，例如 Civolution 的 4 个时代 × 8 个阶段、终局计分轨；
- Splendor 这类流程简单的游戏可以自动压缩，不强行拉长；
- 只要有流程结构（`flow.json` / pipeline / condition），就有机会跨游戏复用；
- 与现有规则问答天然互补：它记住「走到哪」，问答负责解释「怎么判断」。

## 三种产品模式（可叠加）

1. **流程向导（Tier 0）**
   - 零棋盘状态；
   - 只问是/否/选项；
   - 负责带完整局流程；
   - 本 idea 的主体。

2. **按需判断（Tier 1）**
   - 客人问「我现在能不能做这个」；
   - AI 只问当前判断所需的最少状态；
   - 程序给出规则判定。

3. **影子对局（Tier 2）**
   - 每一步行动都经过 AI；
   - AI 维护完整影子状态；
   - 可给「你现在可以买哪张」这类状态相关建议；
   - 是更高阶、输入更重的可选模式。

## 终局计分助手

「协助我进行算分」是流程向导里价值最直接的一块。

以 Civolution 为例：

- 终局计分本来是沿 `final_scoring_area_hex` 逐格推进的流程：9 个类别格 + stage partition + point bonus，共 11 个 slot；
- AI 可以逐格说明规则、向玩家收集数值、计算小计、维护总分；
- 最后按规则处理平手判定并宣布胜者；
- 也可以先让客人自己算一格，AI 复核，兼顾教学与防错；
- 这类交互不依赖实时状态，天然适合现在这套系统。

## 设计坑与原则

1. **不要直接遍历引擎级 `flow.json`**
   - `flow.json` 里有很多自动结算节点、内联 pipeline、局部步骤；
   - 需要一层面向人的 **Guide 投影**：只暴露玩家真正要做决定 / 检查 / 操作的节点。

2. **不要把每个微条件都弹给玩家**
   - 按阶段和动作做 checkpoint；
   - 选择某个行动后，再展开该行动的详细前提。

3. **「跳过」语义要拆**
   - 可选步骤：做 / 不做；
   - 条件判断：满足 / 不满足 / 不确定；
   - 暂时跳过：先继续，回头再处理；
   - 不能共用一个模糊的「跳过」。

4. **程序控游标，LLM 只负责措辞**
   - 与项目原则一致：程序确定性，LLM 负责理解与表达；
   - 不让 LLM 自己决定流程走到哪。

5. **支持快进与跳转**
   - 下一步 / 跳过本阶段 / 直接到某阶段 / 从头讲 / 别问了直接播报；
   - 否则流程向导会变成另一种形式的循环确认。

6. **流程向导默认不做最优决策**
   - 它只负责流程、条件与操作；
   - 策略建议属于可选的 Tier 1 / Tier 2。

7. **玩家回答可能错**
   - 流程游标要允许回退、重来、跳到指定节点；
   - session log 可保留流程假设，便于纠偏。

## MVP 建议

优先级上先做真正有复杂流程价值的游戏，而不是 Splendor 这种流程本身很短的：

1. **Civolution 顶层 8 阶段循环**：时代、阶段、行动阶段轮转、阶段结束条件；
2. **Civolution 行动阶段子流程**：选择行动后展开前置条件与操作 checklist；
3. **Civolution 终局计分助手**：按 11 个 slot 逐项结算、维护总分、平手判定；
4. 用 Splendor 做简单回归用例，验证流程游标、是/否/跳过、回退等机制。

真正的工程关键不是 prompt，而是一层面向人的 `guide` 投影：哪些节点要问、问什么、选项是什么、下一步去哪。
