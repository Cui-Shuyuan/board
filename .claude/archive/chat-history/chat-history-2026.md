所以我建议把判据从自愿性换成决策点的宿主：

▎ Action = 流程把控制权交给玩家的转移点：流程树运行到某个节点，向玩家开放候选空间，玩家用 declaration 选择一个分支（含空分支）。
▎ 效果内选择 = 事件结算向玩家索取参数：trigger 流水线执行到 select_target 步骤，向玩家索取输入才能继续。玩家没有发起权——事件不来，永远轮不到他选。

自愿性只是流程决策点的常态特征，不是本质。两边都有"可选"和"被迫"的情形：菜单可以坍缩到只剩一个分支（被迫的 action）；效果内也可以问"要不要"（自愿的参数）。用自愿性划分，这两个案例都会串味；用宿主划分，全部归位。

2. 跳过（pass）算 action 吗？

分两种：

- 主动 pass（有合法行动但选择不行动）→ 是 action。它是流程菜单中的一个合法分支，declaration 内容为空。"不行动"也是一个分支，同样改变游戏状态（回合权转移）。建议把它建模为 flow 层 action_phase 的隐式候选（默认值），而不是每个游戏在 concepts.json 里重复定义一个 pass action。
- 被迫跳过（候选集为空）→ 不是 action，是 trigger。玩家没有任何决策，规则接管流程。你们的 skip_turn 已经这么建了，完全一致。

也就是说"跳过"这个词在游戏口语里混合了两种东西，宿主判据恰好把它们干净地分开。

Declaration 是旧架构的副产品

Declaration 之所以存在，是因为当时的架构是「trigger 自己监听世界，等待被触发」。在这个架构下，玩家的选择必须物化成一个实体（declaration），trigger 才有东西可监听——condition 写成「declaration 合法」，意思是"我在等有人宣告我"。

但你现在指出的才是自然架构：激活模式有两种，各有分工：

1. Call 模式（直接点燃）：action 选中 → action 直接点燃它绑定的 trigger。火球术就该这样——「打出火球术」这个动作本身就是原因，trigger 是被点着的，不是自己察觉的。让 trigger 维护一个「是否有人打出火球术」的 condition，是把因果关系倒置成监听关系，平白多了一层间接。
2. Listen 模式（监听状态边沿）：trigger 自己维护纯 state 谓词的 condition，边沿跳变时自激活。盔甲必须这样——你们 7-30光环讨论里已经证明过这个论证：如果让攻击动作负责点名触发盔甲，它就得枚举头盔、护盾、防弹衣、盾牌……这正是进场枚举错误，和离场枚举错误对称。防御装备集合是开放的，攻击动作不可能也不应该知道全部监听者。

所以正确的结论不是"trigger 取代 action"或"action 取代 trigger"，而是：action 用 call，被动效果用 listen，declaration 这个中间层在两个模式里都不需要了。Call 模式下它是冗余（action 自己就是宣告）；Listen 模式下它根本不出现（盔甲没有 declaration）。

答案：边沿/电平二分，从 content 层提到点火层

2026-07-30 的光环讨论里，你们发明了这对工具：instant_content 按边沿评估（假→真瞬间执行一次），continuous_content 按电平 现在把同一对工具上提到点火层，action 和 trigger 的全部差异即刻穷举：

- Trigger = 边沿点火的可执行规格：condition 按边沿评估，假→真的瞬间规则自动点燃它。边沿不等人——规则必须立即执行，所以 a
- Action = 电平点火的可执行规格：condition 按电平评估，为真期间持续开放，玩家在窗口内选择是否点燃、何时点燃，并顺手填入 target/cost 的参数。电平留出了决策的时间窗——所以点火者可以是玩家。

condition、cost、target、content、options——全部成员共享，一个新字段都不需要。你举的三个例子完美落位：「支付2块钱打出一张牌」cost ✓；「已打出5张牌则不能再打」condition（电平评估时为假，菜单中不亮）✓；「选择一位玩家拿取他1块钱」target ✓。

于是整个家族坍缩成一张图

可执行规格 = condition + cost + target + content (+ options)
│
├── 边沿点火（规则自动）= trigger
│   └── + options / 玩家视角 = effect
│
└── 电平点火（玩家决策）= action

<action> 正式地 extends <trigger>，override 只有一条：condition 的评估模式从边沿改为电平，点火者从规则改为玩家。就像 <e了 options。差异确实轻微——轻微到只有一个维度，和 trigger/effect 之间的距离完全同款。

免费掉下来的四个推论

1. content 槽装 action 自动合法：action 是 trigger 的子类，<trigger> | <content> 的槽型本来就包含它。卡牌授予行动，零特能装 action"的类型危机彻底消失。
2. 决策字段不是新成员：就是 target 和 cost 的参数槽，由玩家在点火时填入，而不是由规则在结算中填入。「选模组、放骰子」= 玩家填充的 target + cost。
3. precondition 和 condition 是同一个槽：边沿评估时它叫 condition（点火），电平评估时它就是菜单可用性（把门）。之前纠结igger 的 condition 同型不同角色"——现在角色差异被评估模式这一个参数完全解释。
4. actor 字段彻底蒸发：不需要声明——点火者的身份就是 actor。边沿点火 ⇒ 规则；电平点火 ⇒ 玩家。

顺带：整个谱系里只有一个杂交种

两个子维度——评估模式（边沿/电平）× 点火者（规则/玩家）——通常联动（边沿没法等人，电平才能等人），但有一个例外：may trigger = 边沿评估 + 玩家确认。它是两维度分离的唯一标本，之前我们给它找的各种位置（optional 标记、裂口格子）现在都清楚了：它就是「边沿点火，但 content 执行前要过一道玩家确认」的 trigger。全谱系只此一格，其余所有案例两个维度全部重合。
