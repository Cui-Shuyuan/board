## 1. 背景

基础问答已经跑通，结构化规则文档也足以支撑 LLM 编写新游戏。下一阶段的工作重心从「继续批量写规则文档」转向「讲规动画的自动制作」。

核心目标不是让 LLM 实时生成动画，而是把结构化规则、口播稿、TTS 音频、动画动作和素材编译成一份静态数字资产。客人播放时只做确定性播放，不调用 LLM 生成动画。

## 2. 核心决策

1. **口播稿是主，动画是次。** 动画只负责配合口播节奏和分区，不反过来决定或修改口播内容。
2. **口播先行，TTS 冻结，动画后置。** 口播稿定稿并生成 TTS 后，音频时长就是动画的硬边界。
3. **一份规则事实，多个讲解版本。** quick / full 共享组件、资产和动作行为，不共享口播文本。
4. **运行端不跟踪历史状态。** 播放期间只维护当前播放单元；任意跳转通过编译期生成的「起始画面」实现。
5. **LLM 只填动画参数，不写新播放代码。** 动画收敛为固定原语，播放器只执行原语。
6. **不做 authoring 界面。** 制作以 JSON 数据、schema、validator 和 Unity 播放为准，LLM 直接写数据。
7. **试点游戏为《璀璨宝石》。** 以用户提供的 full 版口播稿为标杆，先做 full，再抽出 quick。

## 3. 内容版本：full 与 quick

### full

- 定位：规则全覆盖，面向想深究的客人、店员或「老学究」。
- 特点：背景、例子、例外、总结都可以保留，时间较长。
- 当前作用：作为后续所有游戏的口播稿标杆和数据拆解基准。

### quick

- 定位：桌游店默认首讲版本。
- 目标：让客人用最短时间先玩起来；没讲到的规则由客人随时打断提问，问答模块兜底。
- 原则：只讲「不开局就会卡住」的内容，例如设置要点、回合可选行动、胜负条件；细节、例外、背景、例子默认省略。
- 产生方式：full 先跑通，再从中提取 `core` 内容并重写口播。quick 不是把 full 加速朗读，而是重新组织讲法。

### 两个版本的共享关系

- 组件、版图、slot、sprite、动作行为共享。
- 口播文本和音频不共享。
- 动作内容优先复用；若 quick / full 音频时长不同，则按各自 TTS 时间轴分别编译播放时间。
- full 独有的细节动作可以单独增加；quick 可以不触发这些动作。

## 4. 数据分层

建议逐步演进为五层，源数据与运行产物分离：

| 层 | 内容 | 负责人 |
|---|---|---|
| L0 规则层 | `concepts.json` / `flow.json` | 已有，程序 |
| L1 口播脚本层 | 播放单元树、narration、source_refs、版本标记 | LLM 草稿 + 用户裁决 |
| L2 动作库层 | 可复用的语义动作步骤，如发牌、拿宝石、购买、保留、贵族结算 | LLM 实现 + 用户视觉 review |
| L3 资产层 | 版图、slot、sprite、音频 | 用户扫描/拍摄 + 程序处理 |
| L4 编译产物 | 运行时 tutorial 数据，含每个播放单元的起始画面和时间轴 | 确定性编译器，无 LLM |

源数据里不手写起始画面；起始画面由编译器离线生成。运行时只读取 L4。

## 5. 播放单元与拆分原则

- 中间层是 `group`，只用于导航和章节归组，不是打断/重播单位。
- 叶子节点才是播放单元，每个叶子带口播、音频和可选动画。
- 叶子按 **1～3 句口播**切，不按规则小节切；一个完整规则小节通常拆成多个叶子。
- 每个叶子挂 `source_refs`，能追到 `flow` / `concepts`；背景、组件介绍、例子等 flow 没有的内容可以标规则书或人工审核。
- 每个叶子尽量只承担一个可教学的点；太长的说明性段落要拆成多个叶子。

示例：Splendor 的「3.1 拿取宝石」可以拆成：

1. 拿三枚不同颜色；
2. 同色两枚的条件；
3. 不能故意少拿；
4. 10 枚上限与弃回；
5. 宝石公开。

full 保留全部；quick 将来可以只留核心并重新合并成更短的口播。

## 6. 任意跳转与静态资产化

产品目标：客人可以像看视频一样任意跳转到任何章节，不要求顺序播放。

数据实现：

- 编译器根据完整动作时间轴，离线计算每个叶子开头所有 sprite 的完整画面状态。
- 编译产物为每个叶子保存「起始画面 + 本节时间轴」。
- 运行时只需加载当前叶子的起始画面并从 0 播放，不维护全局历史、不需要回放前序章节。
- 洗牌等随机效果必须确定性化（固定种子或预生成结果），保证每次跳转画面一致。

这不是运行时状态机，而是把状态前移到编译期的静态资产化。

## 7. TTS 与动画时间契约

固定制作顺序：

1. 口播稿定稿；
2. TTS 生成每个叶子的音频；
3. 冻结音频并测量每段真实时长；
4. 生成或调整动画时间轴；
5. validator 校验时间轴不超出音频时长；
6. Unity 播放、截图、视觉迭代。

规则：

- 动画时间不够时，优先调整动画速度或动作设计；如确需更多时间，必须在 TTS 冻结前增加留白。
- 音频一旦冻结，不再为了动画修改时间轴。
- quick / full 各自冻结自己的音频；动作内容尽量共享，时间轴按版本独立编译。
- 若两版音频时长完全一致，可以复用同一条时间轴；否则分别生成。

## 8. 动画工具化

- 沿用现有 8 个动画原语：`move` / `flip` / `rotate` / `scale` / `fade` / `highlight` / `shuffle` / `wait`。
- LLM 只输出原语事件和必要参数，不在 Unity 里为单个动画新写协程。
- 为每个游戏维护动作库：同一语义动作只实现一次，quick / full 复用。
- LLM 生成动画时只获得当前叶子相关的 sprite / slot 目录和口播文本，不获得整款游戏全部上下文。
- 尽量提供默认值，减少 LLM 填参；validator 负责引用、时长、冲突检查。
- 视觉问题通过 Unity 截图反馈迭代，只改参数、坐标和素材，不改数据结构。

## 9. 打断问答

- 客人打断时，播放器暂停音频和动画。
- 问答只携带当前叶子上下文：当前叶子 id、路径标题、当前叶子口播全文、source_refs。
- 不传播放秒数，不依赖「说到第几个字」，避免半句话语义不完整。
- 后端问答仍走现有工具查结构化规则。
- 回答结束后，播放器重播当前叶子，从该叶子的起始画面和时间轴 0 秒开始。
- 当前叶子只有 1～3 句，重播成本低，优于从打断点续播。

## 10. 试点：璀璨宝石

- 标杆原稿：`doc/splendor/口播稿.md`（full 版，本地资料，git 忽略）。
- 已拆出 full 版时间轴口播稿：`games/splendor/tutorial/full.lrc`，并按实际 TTS 时长进一步细分为 109 个播放单元、16 个导航分组。
  - 细分规则：优先按标点切，目标单 cue ≤40 中文字；实际 TTS 最长 cue 约 8.45 秒，避免 15 秒以上重听。
  - 每行格式为：`[mm:ss.xx][id:...][ref:...]台词`。
  - 已完成 full 版 TTS：`games/splendor/media/tts/full/` 下 109 个 mp3 + 109 个字级 subtitle.json；`full.tts.lrc` 已回写为 `timing=tts`。
  - 已给大部分播报单元挂 `flow:` / `<concept>` / `rulebook:` 引用。
  - 格式说明见 `tutorial/README.md`；校验/解析见 `scripts/validate_timed_script.py`。
- 先做 full，先跑通结构，不急于做 quick。
- 当前状态：TTS 音色与前 3 条已试听确认，full 版 109 条已全量生成；下一步进入组件扫描、slot 标定、程序解析/加载、动画生成、Unity 播放和打断问答接线。

## 11. 分工

- 用户：规则口径、叶子边界、组件扫描、视觉方向、最终 review。
- AI：口播稿拆解、动画动作和参数、compiler / validator、Unity 播放器、视觉调参。
- 程序：编译、起始画面生成、确定性播放，运行时不调用 LLM。
- 用户对动画实现零基础不影响流程；用户只需用自然语言和截图反馈「哪里不对」。

## 12. 暂不做

- 不做 authoring 图形界面。
- 不做运行时 LLM 生成动画。
- 不为单个动画新写 C# 协程。
- 不先做 quick 再补 full；本阶段先以 full 建立标杆。
- 不在音频冻结后反向修改时间轴。

## 13. 下一步

1. 基于 `full.tts.lrc` 确认最终播放单元与音频边界。
2. 进入动画会话：组件扫描、slot 标定、程序解析/加载、动作库 schema、编译期起始画面和 Unity 播放。
3. quick 版和 `core / extended / flavor` 标记留到 quick 阶段。
