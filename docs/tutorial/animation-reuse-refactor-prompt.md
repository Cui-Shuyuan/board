# 给 DeepSeek V4.1 Flash 的动画架构与生产管线重构任务

你是这个仓库的架构与实现负责人。请直接阅读仓库、设计并实施下面的重构，完成代码、数据迁移、验证和文档。不要只给建议或停在方案阶段。先写简短设计和执行计划，再按可验收阶段推进；普通实现选择自行决定，不必逐项等待确认。

## 1. 项目目标与授权范围

这是我的个人桌游讲规项目，尚未用于生产。未来会通过成熟工作流程大量接入不同桌游。Splendor 只是桌游教学的 Hello World，用来探索架构和制作管线，不能成为通用引擎的隐含前提。

当前 full 和 quick 都经过人工浏览和调整。我们希望保留这些已有教学成果，同时解决它们重复定义局面、动作、镜头的问题。最终应能用一套经过确认的教学素材，编排长版、短版以及未来其他版本。

本次允许破坏性调整源格式、目录、内部接口和必要的编译产物格式；不需要旧格式兼容、双读双写、过渡适配器或历史版本迁移支持。完成一次当前数据迁移即可。复用仍然合适的现有编译和播放器能力，是工程选择，不是兼容要求。若改变产物协议，同步更新所有当前消费者。

授权范围是讲规动画的源模型、素材复用、装配编译、校验、增量构建、相关播放器接线和制作流程。不要顺便重写规则问答后端、整个 ontology 或 Android 产品界面，不建设云平台、素材商店、多人编辑器或通用游戏模拟器。

不需要为每一款未来游戏提前实现机制。需要证明当前架构不会把卡牌、五色宝石、两名玩家、12 个市场槽位、full/quick 两种版本写死。

## 3. 核心设计：分离事实、动作、表现和编排

下面是语义边界，不是要求建立四套复杂框架。请选择最小、清晰、可以机器验证的数据结构，允许相关内容放在同一个素材文件中，但必须区分职责。

### A. 教学示例与局面

定义一个教学例子中明确的对象身份、归属、位置、面朝向、顺序、资源或轨道数值，以及必要的命名角色和阶段。例子属于具体游戏，不属于 full 或 quick。

规则真值继续引用现有游戏规则和组件资料。示例只描述一次具体演示的选择与状态，不复制一套规则定义。例如“这个例子买卡 X”是示例事实，“此类卡如何付费”是规则。

需要区分组件类型/图片模板与具体实例：同种工人或筹码可以有多个实例，不能把 Splendor 的真卡唯一性误当成所有对象模板都只能出现一次。角色引用与实体身份应稳定，不能用显示名称或数组下标充当公共接口。

场景是离线教学数据；随机结果使用确定的预设结果或种子，不在播放时随机抽取，保证跳转、重播和断点恢复一致。

### B. 可复用动作片段

定义发生什么，以及入口条件、状态读写范围和结果。片段内使用局部角色，例如行动玩家、目标组件、来源区域、目的区域，调用处绑定到具体示例对象。

动作片段可以由现有状态原语构成。不要为了这个重构再造一套完整规则执行语言，也不要把所有动作细分成只有一个字段的文件。优先抽取具有教学意义、能够独立验证的单元。

动作的结果由唯一的状态变更序列产生；声明的后置条件是断言，不是另一套手工维护的状态真值。需要阶段快照时，从初始局面和动作确定性生成。合法性计算优先复用已有规则能力；暂时只有游戏专属检查时，明确放在该游戏校验边界，通用层不要伪称能验证所有游戏规则。

### C. 镜头与表现素材

定义怎样展示动作或局面：机位、构图、飞行动画、高亮、指示、文字、放大镜等。应能绑定角色、区域和语义部位，例如组件的费用区、玩家资源区，而非直接写死 Splendor 对象。

这里的“镜头素材”不是一段固定秒数的视频。现有 stage 的命名 shot 仍表示机位，不要与可复用的整段演示混淆。已有 `clips` 若表示纯视觉插值，也不要悄悄改为规则动作。

表现不能私自决定付多少钱、买哪件组件、移动到谁名下或拿哪位贵族。同一个动作可以有不同表现；只需复用局面的地方，不强制复用整个动作；只需复用表现的地方，也不强制绑定一个固定局面。

### D. 教程编排与旁白

track/section/cue 负责教学顺序、旁白、素材调用、时间绑定和分支选择。full/quick 是普通 track 数据，不是编译器里的两条特殊代码路径。

共享素材不能反向引用某个 track 的 cue ID、旁白 beat ID 或绝对音频时间。一个 cue 可以调用多个素材；一个完整示例可以包含多个明确阶段供不同 cue 使用，但不要因此违背项目“一 cue 讲一件事、一个教学动作不随意拆成两条 cue”的约定。

保留便捷的一次性内联内容入口，用同一解析与校验链处理；不要强迫每个只出现一次的字幕或镜头都成为独立资产。真正共享的内容必须只有一份权威定义，展开产物中的复制不算源重复。

## 4. 复用接口必须明确

设计并实现实际可用的 schema 和验证，不要只写伪字段。至少明确以下语义：

1. 素材的稳定 ID、作用域、引用路径和依赖解析。游戏数据与跨游戏通用素材分层；无需为未证明通用的内容提前建设全局库。
2. 角色/参数声明、类型、必填项、默认值、允许绑定的对象或区域能力。未知字段、缺失参数、无效引用、循环依赖、角色类型不匹配应尽早报错。
3. 调用实例的独立命名空间。同一素材在同一个 cue 或不同 cue 多次使用时，局部锚点、标注 key、临时对象 ID 不得碰撞；需要共享的真实实体身份必须保留。
4. 简单可解释的组合规则。禁止无限层继承、任意 JSON 深合并和依赖隐式覆盖优先级的配置迷宫。
5. track 可以绑定表现、旁白和合法参数；不能通过随意 patch 改掉共享示例的核心事实。改变购入对象、付款、获得对象或终态，应显式选择不同示例/语义变体。角色化动作的参数和已冻结示例的事实要区分。
6. 展开后的事件有来源映射：能追溯到素材文件、局部步骤、调用位置及 track/section/cue。错误消息应带这条链，而不是只报生成 JSON 的行号。

## 5. 状态衔接是核心，不得退化为复制 events

至少区分以下两种使用方式，并有明确字段或结构表达：

- 连续承接：使用当前局面，验证动作前提，保留未涉及的对象与属性。前提不满足时失败，不能静默补牌、补钱或换对象。
- 独立举例：明确进入一个预设教学局面，与当前故事分支隔离，出口是继续这个例子或显式回到某个命名阶段。用户应通过现有或必要的过渡理解正在切换例子。

不要让素材依赖“某条 full cue 的退出状态”。复用命名示例阶段或明确契约，并由各 track 绑定。若上一个片段与下一个片段的状态不一致，应报告差异，或使用明确声明且合法的过渡，不能自动修补到看起来正确。

省略展示不等于省略状态变化：quick 可以不特写某个结算，但所需逻辑结果仍应在正确节点发生。省略演示过程必须显式声明，不能让卡牌、资源或分数无说明地跳变。

错误示范必须隔离，并声明预期违反的规则；不能全局关闭检查，或让错误分支成为正常流程的隐含父状态。沿用并改进现有 demo/negative 能力，不复制第二套相近机制。

守恒、唯一性、所有权、合法区域等是可声明的约束。不是所有游戏的所有数值都守恒：可再生资源、得分、消耗品和固定实物需按各自模型验证。隐藏、移出镜头或 offstage 不能绕过约束。

## 6. 时间模型：相同示例，不同节奏

共享片段使用语义节点或局部时间，例如开始、支付完成、组件到位、结果确认。调用处把它们绑定到该版本的旁白锚点或显式局部时间区间。音频锚点解析和 TTS 字级 timing 尽量复用现有能力。

必须区分可伸缩的停顿/高亮与需要最小时长的移动/翻转/切镜头/阅读时间。不要简单给 full 全局乘一个速度系数当 quick。

明确动作因果顺序、必要的完成等待以及允许重叠的纯视觉步骤。同一实体的冲突写入、非法重叠、负时长、未知锚点、动作超出窗口、字幕或音频切点错位应有确定性检查。

所给时长不足时，默认报出缺少多少时间、来自哪个素材调用。允许作者显式选择紧凑表现、减少可选展示或延长画面停留；不允许自动截断动作、偷偷改变音频速度或静默增加教程时长。已有 `hold_after_audio` 等行为要统一纳入实际播放时长模型，避免新增两套互相冲突的时钟。

不需要实现通用约束求解器。简单的有序步骤、锚点绑定和时长边界即可，只要规则清楚且检查完整。

直接跳 cue、section 跳转、回退、重播、问答打断后恢复，都必须与从头正常播放到相同位置得到一致的状态和画面。不能依赖“必须先播放共享素材一次”这种运行时副作用。

## 7. 构建和增量失效

推荐路径是：源素材与编排 → 解析引用/绑定/状态与时间 → 现有或改进的中间表示 → runtime/compiled → Unity。具体文件名由你决定，但源与产物必须分清，播放端保持确定性，不运行模型。

依赖追踪必须包含间接引用、绑定参数、舞台、语义部位、表现配置和相关编译器/schema 变化。修改共享素材，应找出所有受影响的调用者，而不只重编当前 track。

分别管理文本/音色/TTS 设置变化和纯动画变化：只改镜头或共享局面，不应重新合成未变的音频；文本或有效音频参数变化时，不得错误复用旧 timing。沿用有效的项目 TTS 约定，先确认实际配置，不擅自更换音色。

提供可实际调用的命令，支持全量校验/构建、检查产物是否过期、查看共享素材影响的 track/cue，以及展开结果和来源。可以扩展现有 CLI，不要求另造一套命令体系。失败不得把半成品当作最新成功产物。

## 8. Splendor 迁移要求

首先扫描当前 full/quick，做一份简短复用清单，分类为共享局面、共享动作、共享表现和版本独有内容。不要只按 JSON 字符串相似度判断语义，也不要追求固定百分比的复用率。

已观察到的线索，请以最新源验证：

- 初始市场的十二张牌和三个后续补位模板，在两版的 stack 配置中已经相同，但各写一份。
- 单贵族示例中，两版存在相同的四红三黑牌组，购买同一张黑卡并拿取同一位贵族。full 可能额外继承之前购买的白卡，导致实际付款与 quick 不同。
- 多贵族选择的购牌、拿取对象或前情可能不同。不要仅凭说明文字判断，要检查实际事件和状态。

迁移顺序：先用初始市场做一条可编译、可验证的完整链路，再处理贵族示例的状态与时序，随后覆盖清单中其余明显适合复用的内容。不能只做两个演示样例就宣布整次重构完成。

本次默认以保留已审阅的教学语义为准。素材抽取可以改变组织形式，但不能偷偷改变规则、旁白含义、教学对象或节奏。需要保留前情差异时，显式建模局面变体，共享能够共享的动作和表现，不要靠海量 override 冒充同一个例子。

对于没有教学必要的差异，可以统一为一个共享示例，但必须记录前后事实、影响的旁白和所有下游阶段，并完成对应 QA 与视觉验收。涉及用户现有规范要求审核的新 cue 或实质教学内容变更时，先提供具体对比供审核；其余结构重构、保持语义的迁移和独立测试继续推进，不要让单个内容决策阻断全部工作。

迁移后所有当前 track 应走新源模型和同一条编译链；没有复用价值的内容可内联。旧权威源、废弃读取分支和失效文档应清理，不能长期维护新旧两套真值。可以保留按现行约定忽略的构建产物和必要本地基线，不把历史备份做成运行依赖。

## 9. 用非卡牌夹具证明通用性

增加一个小型、明确标为虚构测试的游戏夹具，不是第二款真实游戏教程，不需要接入新媒体或调用 TTS。

例如：玩家把一名工人从待命区放到一个行动格，获得资源并推进分数标记。定义确定的简化规则和起终态，同一个例子使用详细与紧凑两种编排，绑定不同玩家/区域，并验证同种工人的多个实例不会被错误判重。

这个夹具必须走正式 schema、解析器、状态装配、时间绑定和编译路径；测试音频可使用显式固定的测试 timing。仅需极小的游戏专属声明/校验，不要修改通用引擎加入该夹具特判。它用于验证机制无关性，不用于声称覆盖所有桌游规则。

## 10. 验证与完成标准

测试重点是边界和行为，不是给每个函数写一条镜像测试。至少覆盖：

- 同一素材被两种编排引用，时长与机位不同，声明应一致的逻辑结果一致。
- 结果比较采用稳定的实体身份和语义状态，不比较自动生成的局部 ID 或秒数。若只保证部分状态相同，必须明确比较范围，不能跳过付款、补位等关键差异。
- 共享素材修改使全部直接/间接调用者失效；无关 track 不受影响；纯动画变化不使 TTS 失效。
- 多次实例化不串状态、不冲突局部锚点、标注和临时对象。
- 缺失引用、循环、非法绑定、状态前提不符、非法覆盖以及时间不足均有带来源的错误。
- 紧凑表现省略视觉过程后，状态结果仍完整；错误分支不污染正常分支。
- 连续播放、跳转和恢复在相同逻辑时间一致；对涉及播放器的变化运行相应采样/播放测试。
- 非卡牌夹具通过同一链路；不能只验证反序列化成功。

迁移前保存当前有效行为基线，迁移后比较关键入口/出口、动作顺序、对象身份、数量和时间边界。保持行为的部分应有回归证据，主动变更的部分应列出并重新验收。

复用现有编译、规则、守恒、身份、QA 和 Unity 采样检查；更新因新源模型需要调整的检查器，不能删除失败断言或跳过某条 track 来换取通过。Board API QA 是独立的规则检查辅助，不替代确定性断言或视觉验收；脚本只发送和留档，不批量自动生成问题冒充手写 QA。

QA 必须覆盖共享定义和实际调用上下文。共享动作合法，不代表所有参数和入口都合法。共享事实发生变化时，使相关调用的审核证据失效，不能仅因 cue 文件没变化就沿用旧结论。遵守现有要求同步更新手写问题；纯结构搬迁也要说明问题与新调用的对应关系。

运行与改动有关的完整检查，不能只测新增模块。对两条真实 track 完成编译和已有静态检查，并对抽取/改动的重点片段做 Unity 采样或截图检查。最终清楚区分自动检查、实际视觉检查和需要人工确认的项目。

如果 Unity、Board API、TTS 服务或设备不可用，记录执行过的命令、具体错误及剩余验收步骤，继续完成所有不依赖它的工作；不得把未执行报告为通过，不得宣称整个任务已经验收完成。

## 11. 必须交付可重复使用的制作流程

除了代码和 Splendor 数据，更新当前文档，并提供以后接入新游戏的作者指南与可复制最小模板，覆盖：

1. 依据现有规则和组件资料定义教学目标、示例角色及事实，明确哪些内容属于假设局面。
2. 先确定供不同版本共用的示例，再围绕这些事实编写各版旁白；不要分别生成两套互不相干的 full/quick 示例。
3. 定义动作的入口、出口、阶段及规则依据，编写最小合法性 QA；不要先堆原语再补叙述。
4. 绑定可复用表现与舞台；没有合适表现时新增小而明确的素材，不复制整个已有教程。
5. 用各版旁白/TTS 锚点安排时间，选择可读的表现密度并检查预算。
6. 运行确定性检查、规则 QA、采样和视觉验收；审核共享定义与版本调用两个层面。
7. 修改共享素材时查看影响范围、重编受影响调用并更新审核证据。

作者指南中给出一份实际可编译的小例子，以及用于经济模型的简短写作提示词：输入应包含已确定的示例事实和可用素材接口，输出使用这些引用；遇到缺失能力或时间不足时明确报告，不擅自发明新事实。

记录必要的动画调整日志，更新动画架构与当前入口文档。纯工具链和文档修改按现有日志约定处理，不虚构用户对画面的修改意见。

## 12. 执行与最终报告

按以下阶段推进，每一阶段都留下实际检查结果和简短进展：

1. 当前链路与重复分析、可靠基线、简短架构决策及 schema 草案。
2. 最小实现：共享市场 → 两版调用 → 产物与回归检查。
3. 状态契约、贵族例子、语义时间、引用实例隔离和非卡牌夹具。
4. 完成其余迁移、依赖/增量/QA 接线、消费者接线以及旧路径清理。
5. 全面验证、视觉检查、制作模板与文档收尾。

这不是要求建立五套临时实现；每阶段都应推进同一条最终架构。保持单个概念有一个权威定义，避免引入大量近义术语和多层插件接口。必要时维护一个简短进度文件方便上下文续接，记录已完成事项、下一步和真实阻塞，不把未完成事项写成成果。

最终报告说明：

- 最终数据关系和关键设计取舍，哪些旧结构已删除。
- 已共享的真实素材及 full/quick 调用位置，仍保留差异的内容及原因。

- 关键文件、可执行命令，以及与本次任务无关而保留的工作区修改。

不要只提交设计文档，不要把目录搬家或重复 JSON 移入 shared 目录当成完成。完成标志是：两条真实教程使用新的共享源和编排机制运行，非卡牌夹具证明核心没有绑定 Splendor，后续作者能够按文档重复完成这条制作流程。
