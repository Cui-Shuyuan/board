# 从口播与扫描件到 full / quick：制作流程 v0.1

2026-10-22。状态：**基于 Splendor 当前源与工具代码整理的试行版，尚未在第二款游戏端到端验证。**

本目录解决“让下一个 agent 如何开展制作”，具体 JSON 协议继续以现有作者指南、schema 和代码为准。它不替代编译器，也不把 Splendor 的镜头、游戏规则或 cue 数量变成所有游戏的模板。

## 直接使用

在仓库中的新会话发送下面这段，填入游戏和输入位置即可：

```text
请按 docs/tutorial/production/producer-prompt.md 制作讲规动画。

game_id：<游戏目录名>
口播稿：<路径，可以只有一份>
扫描件：<目录或文件列表>
本次目标：先完成 full/quick 教学设计和代表片段的可审阅分镜；cue 审核通过后制作双版本小样。

沿用项目已有视觉风格与教程音色。先从仓库查规则、组件资料和工具能力；
缺少的信息集中列出，只问影响当前阶段的问题。
这是探索中的管线，请记录哪些步骤有效、哪些仍依赖人工，不要为了证明流程完整而掩盖缺口。
可能有其他 agent 同时工作，修改前重新读取文件，不覆盖别人的变更。
```

如果本轮就要制作完整动画，把“本次目标”改为“完成 full/quick 全片”；已确认的口播、分镜和授权可附路径或会话依据。总控 prompt 会按阶段推进，不要求每个阶段都重新征求同意。项目已有的新 cue 审核约定仍适用，已有审核不用重做。

文件分工：

| 文件 | 用法 |
| --- | --- |
| [总控 prompt](producer-prompt.md) | 可整篇交给制作 agent，规定输入、输出、原则与推进方式 |
| [阶段 prompt](stage-prompts.md) | 同一 agent 分阶段执行，或在接续会话中指定某个阶段；不是要求启动多个 agent |
| [仓库接入与核验](repository-adapter.md) | 当前路径、命令、工具边界和 Splendor 取样依据；执行时核实 |

## 输入与输出的边界

用户的主要输入是**口播稿和扫描件**。规则数据、组件尺寸、软件工具、音色配置属于项目已有上下文，agent 应先查找，不应要求用户重新填写一大套技术表单。

两类输入本身也有边界：扫描图能证明某张牌写了什么，不能证明整套游戏规则；单独裁切的图片能证明长宽比，不能可靠证明实物毫米尺寸。如果仓库也没有相关证据，就列为缺口。可以继续做不依赖这些信息的部分，不能把猜测写进已确认事实。

默认交付的是 BoardAI 内可播放、可跳转、可重播的两条课程：源 JSON、处理后素材、TTS/字幕、runtime、compiled、固定时间轴、cue-timeline 和验收证据。MP4 是可选审片输出；当前流程不假设已有通用视频导出器。发布到生产服务是单独操作。

只有一份稿时，保留原稿并提出 full/quick 分配方案；有两份稿时，保留两者的教学意图，核对矛盾。不得未经说明重写口播以迁就已有动画素材。

## 推荐推进顺序

```text
输入盘点与能力核实
  → full/quick 教学覆盖 + 代表片段分镜
  → 代表组件处理 + 示例事实 + 状态契约
  → 双版本小样：真实 TTS → 动画 → plan → 实际播放
  → 按 section 扩展全片
  → 双轨完整验收与交付
       ↑ 每轮反馈回到最早出错的源层
```

先做代表片段，而不是一口气写全片 events。建议小样选择一个完整核心行动：看清条件 → 执行动作 → 看见结果，覆盖真实零件、规则状态、镜头与声音同步。30–60 秒只是起始预算，不是硬指标。full 版能展开因果，quick 版能用同一事实简洁讲清；必要时各用数条 cue，但不要把同一个完整动作切碎来凑数量。

全片制作不强制“先 full 后 quick”或反过来。先确定共同教学事实，再按 section 做双轨对应检查，能更早发现 quick 删掉了必要前提、full 示例与 quick 不一致等问题。

## 交接记录保持轻量

建议在 `docs/tutorial/productions/<game>/production.md` 维护一个制作记录；可审阅分镜放同目录 `storyboard.md`。这些是本流程提出的**制作文档**，不是播放器新增协议，不要塞进 runtime JSON。

制作记录至少包含：

```text
输入版本：文件、版本/哈希、游戏版次、规则来源
已确认范围：口播、分镜、样片、用户确认依据
本轮目标：一项可验收的结果
能力表：可复用 / 需配置 / 需补实现 / 无法执行
事实与资产索引：规则依据、组件来源、处理记录的位置
状态：planned / authored / built / reviewed / accepted
当前证据：track、section/cue、源版本、命令结果、截图/录屏位置
未闭环：失败 / 阻塞 / 未执行 / 不适用及理由
下一步：明确文件、片段与验收方法
```

`reviewed` 表示有实际审查证据，`accepted` 表示满足该阶段标准及适用的用户确认。不要把“有文件”标记为 accepted。音频、原始扫描、截图、采样、QA 日志按仓库约定保存本地、不入 Git；记录其路径和输入指纹。无需重复保存能由源文件计算出的全部状态。

## 本版沉淀什么，暂不沉淀什么

可以直接沿用的项目原则：源与产物分离；脚本先行；真实组件身份；动作与表现分离；共享示例；按口播锚点对时；确定性跳转；静态校验与视觉验收分别完成。

需要下一款游戏验证的流程假设：代表小样的最佳大小、full/quick 覆盖表是否足够、哪类动作值得抽成共享素材、扫描处理的通用程度。章节节奏、镜头数量和全片时长不写死。

每完成一个 section，记录一次“问题 → 根因 → 修正 → 复验”。区分：

- **内容问题**：事实、素材身份、状态或分镜错，修该游戏源。
- **流程遗漏**：agent 因缺少检查步骤而反复出错，修改对应 prompt。
- **工具能力缺口**：需要补通用能力或游戏检查器，写最小可复现案例；不能靠增加 prompt 要求假装已解决。
- **审美选择**：保留本次用户反馈及适用场景，先不自动推广成所有游戏的偏好。

下一轮优先用一款机制不同的游戏验证代表片段；若暂未选定，可只对照 Splendor 一段已接受内容检查流程能否表达它，不要重新生成或改动现有成片。只有实际跑通后，才能把本版标为“已验证”。
