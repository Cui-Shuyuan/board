# 分阶段 prompt

先使用 [总控 prompt](producer-prompt.md)。以下每个代码块都可作为后续消息直接发送；路径参数从制作记录和本轮任务取得。阶段之间通过文件与验收证据交接，同一个 agent 即可全部执行。

## A：输入盘点与教学分镜

```text
执行制作阶段 A：盘点输入并设计 full/quick，不先批量写动画 events。

1. 读取口播、扫描件目录、游戏版本、现有规则/组件数据和已有教程。
   实际查看代表扫描，不能仅凭文件名判断。记录缺图、身份不清、规则冲突、
   稿件缺失与尺寸不明；查仓库后仍缺的信息才询问用户。
2. 按 repository-adapter.md 检查真实工具能力。特别核对首次 TTS 初始化、
   当前音频组织、游戏 ledger/audit profile、身份检查覆盖、Unity 播放与采样。
   不把能传 --game 的脚本直接认定为游戏无关。
3. 识别目标观众及“看完能做什么”。建立 full/quick 教学覆盖表：
   规则点/依据、必要前提、full 的 section/cue、quick 的 section/cue、
   quick 省略内容及原因、独立开局是否仍有断点。
   只有一份稿时先保留原稿，再写另一版候选和删改对照；不得暗改原意。
4. 选一个能暴露制作难点的完整核心行动作为代表片段。
   给出 full/quick 两版分镜；其余章节先有覆盖表即可。
   每条 cue 写清教学问题、原文位置、口播/beat、入口局面、画面焦点、
   完整动作、结果停留、出口/分支回归、所需真组件和最小 QA。
5. 用“观众看到了什么证据”检查每句规则。仅显示口播全文或持续摆着桌面，
   不能自动视为完成演示；同时也不要为每句话强行增加动作。

输出：production.md、storyboard.md，包含覆盖表、能力缺口和代表片段。
完成标准：能逐条追溯原稿与规则；两版教学目标清楚；示例可合法成立；
每条 cue 可具体审核；没有用未核实假设支撑关键动作。

项目 .claude/memory/user-preferences.md 的现行要求是：
“新动画必须先由用户审核 cue（2026-10-02 用户要求）”。
如果这些 cue 尚未获准，先交付上面的具体分镜、必要资产预览与待确认差异，
再集中请用户审核；说明依据所在文件。已有确认或用户当次授权优先，不重复问。
审核前可继续资产盘点和独立的技术检查，不推进依赖未定分镜的大量动画制作。
```

分镜可以使用下面的轻量格式，不新增运行时字段：

```text
track / section / cue：
唯一教学问题：
原稿位置 → 本版口播 / beats：
规则依据与示例前提：
资产/实体身份：
入口：继承/命名快照/独立示例；已有资源与关键对象
画面：观众先看哪里；哪里需要特写；字幕/提示的安全区域
动作：对象从哪里到哪里；必要的中间状态；结果如何看清
出口：最终状态；下一 cue 接续点；假设分支恢复点
full/quick 共用什么、差异是什么：
QA：最小问题、预期结论、规则依据；或纯展示豁免理由
验收：关键帧、对应口播词、需要听审的边界
```

## B：扫描件 → 可用资产 → 教学事实

```text
执行制作阶段 B。先完成已定代表片段所需的真实资产与教学事实，再扩展资产池。

1. 区分资产类型：平面牌/板块、圆片/异形片、棋盘、立体件、通用背景。
   先查看现有工具的输入/输出和形状假设；不能拿 Splendor 圆形 token 算法
   批量处理方形板块，不能把旧 Resources 路径当成现行运行素材目录。
2. 保留原件；记录 source 文件/哈希、页或 bbox、旋转/校正/去底参数、
   输出路径、尺寸、正反面配对、身份与关键图案的人工读图结果。
   使用支持当前任务的实际图像工具；在需要时按环境要求读取图像处理技能。
3. 做原图与处理后图的对照，并放到实际舞台底色上检查：
   边缘/白晕、透明孔洞、浅色细节、数字/图标完整、方向、清晰度、比例。
   同类型抽取代表样本通过后再批量处理；最终检查全部实际使用素材。
4. 区分“贴图身份”和“物理实体身份”。实际有多份相同组件时允许同图多实体；
   唯一牌不能因复用贴图而多出一张。展示放大图不参与桌面实物计数。
   所有在镜头中可读的牌面事实必须与规则示例一致。
5. 优先读取 components 等已确认尺寸。扫描分辨率或裁切图比例不足以推出毫米。
   缺尺寸时可标明暂用估值做预览，不标为已确认；不要静默改公共世界比例。
6. 登记需强调的语义部位，例如费用、得分、行动图标；使用当前引擎支持的
   部位映射，不复制 Splendor cost_N 等特定布局作为新游戏默认。
7. 为代表行动确定合法且最简的具体局面：对象、人数、资源、顺序、前后状态。
   优先找到能用现有真实素材演示的例子；若给定口播指名某对象且缺扫描，
   明确列为依赖，不能随便换牌但保留原来的价格/台词。
8. 确定哪些事实/动作值得被 full/quick 共享，写 example/action 契约与
   游戏校验需求；先满足代表片段，不追求一次建成全游戏素材库。

输出：实际素材、来源与处理参数索引、对照预览、尺寸/身份登记、示例事实。
完成标准：每个使用资产可追溯且可辨读；示例事实相互一致；估值与待确认项
可见；后续能定位原扫描并重做处理；没有擅自生成规则相关牌面内容。
```

资产登记可使用表格；已有 registry/components 足以表达的字段应维护原文件，制作记录只链接，避免再建一份权威事实表。

| 资产 ID | 原图/区域及哈希 | 处理记录 | 输出 | 正反面/实体份数 | 尺寸依据 | 规则可读信息/语义部位 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `<id>` | `<source + bbox>` | `<命令或参数文件>` | `<path>` | `<mapping>` | `<来源或估值>` | `<字段及来源>` | `<待审/可用>` |

## C：双版本代表小样

```text
执行制作阶段 C：将已审核分镜做成 full/quick 两版真实可播放小样。

1. 先核对本轮分镜、QA、资产和规则的版本。为代表片段建立最小 section 源、
   base/stage、命名 shots、共享 example/action/presentation；两版各自编排。
   短小的一次性事件可内联，不提前搭建未用到的抽象层。
2. 在补齐规则检查能力后，把实际场景写入前后置条件。事件优先用现有原语；
   事件能编译不代表行动合法，take/pay 等名字也不自动保证游戏规则。
3. 制作正式 TTS：沿用已确认的 seed2 教程基线，明确 provider/voice/resource。
   按真实代码初始化音频输入和 manifest；先运行 dry-run，检查影响范围。
   不复制 Splendor manifest 冒充本游戏，也不伪造 duration/word timing。
4. 根据实际音频绑定 beats、素材 markers、anchor，设置有意义的动作与停留。
   明确镜头焦点，区分 world 与 screen 标注，按真实部位定位。
   时间不足时列出缺口，优先减少非必要表现或显式 hold；涉及改稿则给出差异。
5. 生成 runtime/compiled，建立并审核固定 audio-slices、timing-policy，
   构建 cue-timeline。验证音频源区间、字幕 offset、visual segment 与
   compiled 源时间的对应；不能只在整轨 runtime 兼容模式里播放成功。
6. 执行规则 QA、适用静态检查、Unity 状态采样，并查看/听取实际小样。
   若没有视听工具，保留可播放产物和待审项，不宣称看过或听过。
7. 每版至少验证：连续播放、直接进入正文 cue、跳到后续 cue、回跳重播；
   有客户端条件时验证问答打断后从 cue 内位置恢复。重点看首帧、动作中段、
   结果停留、镜头切换和 cue 边界；不能只看最后一帧。
8. 对比两版：共享动作的身份/数量/前后事实一致，quick 没有删掉成立条件，
   两种节奏都能看清动作结果，且字幕和旁白所指是画面中的同一对象。

输出：实际双版本小样、源文件、播放方式、关键帧/录屏、QA 与检查报告，
以及应继续沿用或调整的制作选择。
完成标准：已定片段事实正确、动作清楚、声音同步、两版独立可播，
直接跳入/重播结果一致。小样未通过时先修这一段，不铺开整片 events。
```

## D：扩展全片

```text
执行制作阶段 D：沿用已通过小样，按 section 小批扩展 full/quick。

1. 从覆盖表选择下一批教学内容，先完成其文字分镜和最小 QA。
   补齐尚未完成的 cue 审核，不重复审核已经确认且没有实质变化的部分。
2. 只新增本批需要的资产和示例；检查 library 后复用或抽取真正共同的动作。
   full/quick 的不同前提/终态要显式 example/variant，不能藏在复制的 events 中。
3. 分别维护两轨状态链与章节入口。quick 即使略去 full 某段，后续局面也必须
   有明确来源；不能依赖被省略的 full cue 或历史播放副作用。
4. 按小样链生成真实媒体和编译产物。仅更改表现时复用未变声音；
   改文本/音色/有效合成参数则重新生成相关媒体与时间，不只改字幕。
5. 每个 section 验收本段及前后边界；更新 shared 后用 impact 找出两轨所有
   调用者，重建并复验受影响范围。未受影响的已确认部分不反复重做。
6. 每条动画调整追加项目要求的变更日志，运行日志检查。
   制作记录保留已验收与失效状态，不把一次旧截图沿用为新源的证据。
7. 两轨全章覆盖后各自从头播放；全局检查教学顺序、术语、身份、镜头风格、
   总时长和节奏。quick 必须单独观看，不能靠“刚看过 full”补足缺失解释。

输出：两轨完整源与媒体、更新后的覆盖/验收表、剩余缺口。
完成标准：没有未交代的状态跳变、遗漏必需教学点或不明素材身份；
所有实际 cue 都有验证状态，不能只验证编写过的几个示例。
```

## E：独立验收与交付

```text
执行制作阶段 E。以审查者视角重新核对产物，不用“由自己编写”作为正确依据。

1. 固定待验收的输入/源/媒体版本；发现并发修改则只让其影响范围证据失效。
2. 源与结构：检查两轨解析、编译新鲜度、素材契约、引用和全程 cue 覆盖。
3. 规则与状态：核对规则来源、Board API 留档、独立 ledger、跨 cue 审计、
   组件身份、负例/假设分支和恢复点；记录每个 checker 真正检查了多少内容。
   缺失 checker 记阻塞，零匹配不能算通过。不适用必须有针对本游戏的理由。
4. 视觉：逐 cue 检查首帧/关键动作/终帧以及章节接缝，核对可读性、遮挡、
   比例、对象一致性、标注跟随、无脏帧和结果停留；配合连续播放检查动态问题。
5. 声音：逐句听审读音、首尾字、拆句处、停顿、字幕同步、口播与动作指向。
   不能仅凭 wave duration 或自动边界分析判定听感。
6. 播放：full 和 quick 各完整播放一次；检查直接跳转、回退、重播、暂停恢复，
   并在目标客户端检查章节导航与问答打断恢复。区分 Editor 与真机证据。
   确认实际加载了 cue-timeline，而不是静默落入旧兼容模式。
7. 交付：检查 plan 所引用音频/图像/字幕/compiled 均存在；需要本地打包时
   构建 manifest/release 并检查依赖。不要仅为生成 manifest 就宣称已经发布。
   不覆盖已发布不可变 release，不自动部署生产或上传媒体。
8. 汇报通过/失败/阻塞/未执行/不适用与理由。缺少关键证据时交付候选版，
   不宣称最终验收完成；继续能独立完成的修复。

最终交付：两条课程的入口和实测时长、源目录、媒体与产物清单、
覆盖表/验收报告、可重建步骤、已知限制、需要用户查看的具体片段。
```

验收表推荐以 cue 为行，避免每个检查只写一句“通过”：

| track/cue | 源版本 | 规则/QA | 状态/身份 | 视觉证据及时间点 | 听审 | 跳转/恢复 | 状态/问题 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `<id>` | `<hash>` | `<结果/覆盖>` | `<结果/覆盖>` | `<文件 + 时间>` | `<结果>` | `<结果>` | `<状态>` |

## F：根据反馈修改与接续

```text
执行制作阶段 F：处理当前反馈，或从制作记录恢复任务。

1. 先读取 production.md、相关源文件和最新 diff；确认用户指的是哪个版本、
   track、cue 和时间位置。若反馈足够明确，直接定位，不再索要重复信息。
2. 将问题定位到最早出错的一层：规则/口播、素材、示例状态、分镜、声音边界、
   时间绑定、编译或播放。记录现象、预期和可核验的原因。
3. 提出最小修正并实施已授权部分；事实或教学含义发生变化时先更新文字与 QA。
   共享素材修改用 impact 查全部调用者；不要只修用户当前看到的那条 track。
4. 根据影响范围重新生成/复验：文字或声音变化失效 timing；
   身份/动作变化失效规则与状态证据；构图变化失效视觉证据；
   公共播放器变化需两轨播放回归。保持不相关素材和他人改动。
5. 追加动画变更日志。更新制作记录中的问题状态、证据版本、未完成项与下一步。
6. 判断本次是否暴露了 prompt 的遗漏；若是，给出旧指令 → 新指令 → 此次证据。
   单次审美反馈留在本游戏；工具缺口转为明确实现任务；不把所有失败都归因于
   模型“没有认真遵守”，也不无止境追加宽泛的自检口号。

输出：修正文件、具体前后效果与复验依据、仍待解决的内容；
若只完成了候选修正，说明下一次该看哪段，不把候选写成已确认。
```
