- **模型请求区间**：HttpClient LogicalHandler 开始 POST，到后续第一条 ChatOrchestrator 日志。通常为 reasoning、tool calls、纠偏、evidence 或 final。包含远端排队、网络、输入处理、推理、输出生成、响应反序列化及少量日志开销。不能再细分为纯思考/纯生成。
- **工具区间**：编排层 tool calls 到 execute_plan result；同轮多工具依次计量。包含工具执行和少量日志/编排开销。新版虽有单独 tool timing，旧版没有，因此两版使用一致区间口径。

## 4. 模型实际在处理什么

运行配置与报告记录为 `deepseek-v4-flash`、`Thinking=low`；代码发送 `reasoning_effort=low`，不是关闭思考。本次没有改变模型或思考配置。

日志中 reasoning 文本显示以下几类工作。这里是行为摘要，不将模型自述当作完整内部计算记录：

1. **语言理解和查询规划**：用户问的是定义、设置、获得还是结算；应选哪个 relation；是否拆多个 query。
2. **候选消歧和再次确认**：读候选说明，选择准确 ID，保持 relation/intent 重新查询。这通常不需要复杂规则推演，但仍要一次模型往返。
3. **协议与证据状态协调**：判断是否可以停止、是否仍有 pending、多余 query 是否要确认。有些明确重复行为来自程序要求。
4. **规则解释与现场条件判断**：将查到的文字条件应用到用户问法；当前接口返回规则结构和说明，并非对所有自然语言问题都直接返回最终判定。
5. **没有匹配对象时凭记忆猜测**：尤其在未知组件/歧义题中，模型会不断尝试相似图标、颜色或能力，再生成新查询。这不是设计期望的职责。
6. **表达组织**：将事实压缩为简短中文、数字汉字化等。已删除的数量重写还人为增加了此类工作。

## 5. 对设计原则的结论与后续顺序

“模型负责语言理解与表达”不等于完全没有语义判断：口语对象和规则节点之间仍须消歧。但当前系统把查询计划、候选选择、证据是否充分、失败恢复和结束时机都交给了同一个模型循环，职责已经超过两次简单的语言转换。特别是程序误判证据或澄清状态时，模型会花时间补救内部流程。

后续优化应优先解决通用程序行为：

1. 证据提取正确覆盖局部 slot 等正式结果，避免已确认却仍 pending。
2. 区分“需要回答规则”“需要澄清指代”“未查到”“不再需要的 query”，使合法澄清和显式终止查询成为协议中的正常出口。不要用“答案含问号”等文本正则替代状态。
3. 收敛首轮多余查询；有高可信证据时减少重复确认，但不直接取消证据来源验证。
4. 对无关候选/未知对象建立有界停止路径，避免通过模型记忆反复猜测补齐。
5. 再针对相同职责和题集测试 `low` 与 `disabled`；不能直接关闭思考并假定语义消歧、工具格式和答案质量不会下降。

这批修订没有改变候选协议纠偏、服务部署、模型配置，也没有新增游戏数据特判。
