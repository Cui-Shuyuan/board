# 问答后端性能优化：关键词检索

本轮只检查和优化后端程序开销；模型、提示词、工具协议、调用次数、
召回阈值与排序算法均未调整。运行中的 API 没有重启，优化尚未部署。

## 发现与实现

请求内的查询向量和关键词计算已经由 `RetrievalRequestContext` 复用，
但不同关键词和后续请求仍然重新枚举全部概念、逐个定位详情并遍历 JSON。
复杂游戏中这一过程产生大量临时对象。

`RulesSearchService` 现在在规则快照内缓存不可变搜索材料：概念摘要字段、
媒体副本以及各个 JSON 字符串值。每版规则/服务实例最多建立普通和 ontology
两份材料，Lazy 保证同一份材料并发只构建一次。缓存不保存用户问题或答案。

匹配仍使用原来的大小写比较方式、概念顺序和 ID 查找语义；字符串保持
独立，避免把两个字段拼接后误命中。返回值重新构造，避免调用方修改污染
其他请求。规则变化时，新快照自然重建材料；进行中的旧请求继续使用旧版。

## 回归与限制

- 后端 Release xUnit：279/279 通过，零失败、零跳过。
- 新增测试覆盖字符串边界、非字符串/属性名不匹配、返回值及媒体隔离、
  并行查询、ontology 限定、新规则生效与旧快照保持一致。
- 首次构建搜索材料会增加缓存占用，并集中执行概念读取；本次没有测量
  冷启动、缓存常驻字节、多用户压力或实际含向量检索的端到端改善。
- Debug 构建输出被现有 API 进程占用；改用 Release 验证，没有停止该进程。

## 其余值得测量的后端环节

1. **本地查询向量推理**：`EmbeddingService.Embed` 同步执行 ONNX。
   请求内已有复用；需分别测量首次/稳定态推理与并发时的 CPU 饱和度，
   再决定线程数和有界调度，不能直接把所有推理放进 Task.Run 并无限并行。
2. **Qdrant 元数据往返**：每次 `SearchAsync` 先调用 `ListAliasesAsync`。
   可评估请求内共享一次别名快照，但应保留版本固定与热切换契约；
   目前未测量该往返占比，也未引入长期别名缓存。
3. **问答语音合成**：`TtsService` 每次创建临时文件并启动 Python 子进程。
   若体验指标是“多久听到回答”，应单独测量进程启动、服务端合成与回传，
   再评估常驻 worker 或原生客户端。这与文字答案返回速度是不同阶段。

这些方向均属于后端实现，不需要减少模型思考或工具调用轮数；本轮只对
已完成等价性验证的关键词检索优化宣称收益。
